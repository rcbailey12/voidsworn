Issue 2030 Leg Brief: AAA Design Pack
    Screen 1: SHIPYARD WITH THE SHIPS
    (a) Design
    Layout. The shipyard screen splits into two regions. The left 62 percent of the viewport is the 3D bay. The right 38 percent is the detail panel, which is the existing text card evolved, not replaced. A thin horizontal strip along the bottom (height 64 px) holds the ship roster as small selectable thumbnails (rendered from the same 3D models at a fixed angle, 56 by 56 px each, with a 2 px ember-orange border on the selected one).
    3D Bay. The selected ship sits in a dry-dock cradle. The camera is locked at a three-quarter elevation (about 22 degrees above the horizontal plane), distance roughly 14 units from the ship origin. The ship rotates slowly around its vertical axis at 4 degrees per second. The player can drag horizontally to override rotation; on release, the ship eases back to auto-rotation over 1.2 seconds. Lighting: one warm key light (color hex 2A1A0E, intensity 1.4) from upper-left at 40 degrees, one cool fill (hex 0E1A2A, intensity 0.5) from the right, and a dim ember-glow rim light (hex 3D1F0A, intensity 0.3) from below to match the game's palette. The bay floor is a dark grated platform with faint orange seam lines, consistent with existing flagship podium art. Background is a very dark gradient (hex 0A0A0F to 141018) so the ship silhouette reads clearly.
    The 3D model used here is the same scene resource the game already loads for the flagship podium and fleet portraits. No new art pass is needed. The ship renders at its true scale. If a ship class is very large (dreadnought), the camera distance increases to 20 units so it fits; if very small (corvette), distance drops to 10.
    Detail Panel (right side). This keeps the existing card structure. Top to bottom:
    Ship name (font: the game's existing display face, 22 px, color F2E8D8) and class tag (14 px, color 8A7A6A, uppercase).
    Hull bar: a horizontal bar 280 px wide, 14 px tall. Fill is ember-orange (hex C45A20). A thin tick at the current hull value. Damage shown as a darker red segment (hex 6E1A1A) to the right of the fill. Numeric label "47 / 60" in 12 px monospace at the right end of the bar.
    Stat lines, each on its own row, 16 px font, 26 px row height: Shields (single number, no facing), Armor, Speed, Turn Rate, Evasion. Each row has the stat name left-aligned and the value right-aligned.
    Weapon list: one line per mounted weapon, 14 px, showing weapon name and the section it is mounted in (prow / mid / engines), e.g. "Lance Battery [Prow]".
    Lieutenant line: name, callsign (new, see Screen 3), and XP as a small progress bar 120 px wide.
    Refits line: comma-separated list of installed refit modules, 13 px, color 9A8A7A.
    Hover Previews. This is the core new interaction. The three action buttons (Repair, Mk II, Decommission) sit at the bottom of the detail panel, each 120 px wide, 36 px tall, with the existing dark-ember button style. Refit slots and the "New Hull" option appear as a small grid of icons (40 by 40 px) below the refits line.
    When the player hovers any of these (Repair, a specific Mk II upgrade, a specific refit, or a New Hull swap), the detail panel enters preview mode. The stat values that would change get a colored delta appended. Green (hex 5ABF5A) for improvement, red (hex BF3A3A) for worsening. Format: the current value, then an arrow glyph, then the new value, then the delta in parentheses. Example for a Repair hover: "Hull: 47 / 60 -> 60 / 60 (+13)". Example for a Mk II weapon upgrade: "Lance Battery [Prow] -> Lance Battery Mk II [Prow], Damage 14 -> 18 (+4)". For a New Hull swap, every stat line that changes gets the delta, and lines that stay the same dim to 50 percent opacity so the eye skips them.
    The 3D model also reacts: if the hover is a Repair, the damage textures on the ship (scorch marks, breached hull plates) fade to clean over 0.6 seconds. If the hover is a New Hull, the model cross-fades to the new hull mesh over 0.8 seconds. If the hover is a refit that adds a visible external module (say, a prow-mounted ram), that module mesh fades in.
    On mouse-out, all previews revert over 0.3 seconds. No click is needed to preview; clicking commits and opens the existing confirmation dialog.
    Edge cases.
    A ship at full hull: the Repair button is greyed out, hover shows nothing, tooltip reads "No damage to repair."
    A ship with no available Mk II upgrades (all weapons already at Mk II, or the upgrade has not been researched this run): the Mk II button is greyed, tooltip explains why.
    A ship that is the flagship: the Decommission button is hidden entirely, since the flagship cannot be scrapped.
    Only one ship in the fleet: the roster strip shows one thumbnail, Decommission is greyed with tooltip "Cannot decommission your last ship."
    A refit that would disable a system in a section that is already damaged: the preview shows the refit delta in green but also a small warning icon (16 px, amber) next to the affected section line, with tooltip "This section is already damaged; the refit bonus will not apply until repaired."
    Very long weapon lists (six or more weapons): the weapon list area scrolls vertically within a 140 px tall region.
    (b) Least sure decision
    The cross-fade between hull models on New Hull hover. I am specifying 0.8 seconds and a simple opacity blend, but if the two hull meshes have very different silhouettes, the blend may look muddy. A possible alternative is a quick scale-down of the old hull and scale-up of the new one. I cannot judge this without seeing the actual mesh counts and poly budgets. I would flag this for a 30-minute art test before locking it.
    (c) Biggest risk
    Performance. The shipyard now renders a full 3D ship with dynamic lighting, plus a roster strip of thumbnail renders. If the fleet has eight ships and the game is already pushing draw calls in battle, the thumbnail strip could stutter on lower-end hardware. Mitigation: render thumbnails once when the shipyard opens, bake them to a texture atlas, and do not re-render them unless the fleet composition changes. The main bay ship is the only live 3D viewport.
    Screen 2: SHIP STATE PLATE ON THE BOARD
    (a) Design
    Plate geometry and placement. Each ship on the battle board gets a plate anchored to the ship's position in world space, projected to screen space by the camera. The plate sits above the ship model, offset upward by the ship's bounding-sphere radius plus 1.5 units, so it clears the tallest mast or antenna. At the standard battle camera distance of 170 units, the plate renders at approximately 148 px wide and 88 px tall on a 1080p target. The plate is a dark ember rectangle (hex 12101A at 88 percent opacity) with a 1 px border (hex 3A3040). It is not a floating tooltip; it is always visible for every ship in the fleet and every enemy ship. Enemy plates use the same layout but with a thin red left-edge stripe (3 px, hex 8A2020) to distinguish allegiance.
    Plate contents, top to bottom.
    Row 1 (top, 18 px tall): Ship name, left-aligned, 11 px, color D8D0C4. For enemy ships, this is their class and a number, e.g. "Raider 3." Right side of this row: a small section-loss indicator area (see below).
    Row 2 (20 px tall): Hull bar. 130 px wide, 8 px tall. Fill is ember-orange. Background track is hex 1E1A24. Numeric overlay "47/60" in 10 px monospace, centered on the bar.
    Row 3 (14 px tall): Shield bar. 130 px wide, 6 px tall. Fill is a cool blue-white (hex 7AAACF). Single number to the right: "12". This is ONE pool. There is no facing, no arc, no directional indicator. If the shield pool is zero, the bar is empty and the number reads "0" in a dim color (hex 5A5A6A). If a shield generator in a section is disabled (see section rules), the shield bar gets a small diagonal-stripe overlay to show it is not regenerating, and a tiny "no regen" tag (8 px) appears.
    Rows 4, 5, 6 (each 12 px tall): The three hull sections, listed as Prow, Mid, Engines. Each row has the section name on the left (10 px, color 9A9A8A) and a status on the right. Status is one of:
    "OK" in dim green (hex 4A7A4A), meaning all systems in that section are functional.
    "DMG" in amber (hex BF8A2A), meaning the section has taken damage but is not yet destroyed.
    "LOST" in red (hex BF3A3A), meaning the section is destroyed.
    When a section is LOST, the row expands slightly (from 12 px to 16 px) and shows the actual disabled systems in 9 px text, pulled from the ship's current state. This is not generic flavor. The data source is the ship's weapon array, engine config, and shield generator list. Examples:
    Prow LOST on a ship that had a Lance Battery and a Point Defense turret in the prow: the row reads "LOST: Lance Battery, PD Turret."
    Mid LOST on a ship whose shield generator is in the mid section: the row reads "LOST: Shield Gen."
    Engines LOST on a ship with two engine blocks: the row reads "LOST: Engines (speed 0, turn 0)."
    If the disabled system list is longer than the plate width allows, truncate with an ellipsis and show the full list in a tooltip on hover. The plate itself does not expand further.
    Overlapping marks solution. This is the critical problem. When two ships are adjacent (their screen-space bounding boxes overlap or are within 20 px of each other), the current system draws selection rings, pins, and brackets that cross and become unreadable.
    The fix has three parts.
    First: offset plates. When two plates would overlap on screen, the plate of the ship closer to the camera stays at its default position. The plate of the farther ship shifts upward by the plate height plus 6 px. If three ships overlap, the third shifts up by two plate-heights plus 12 px. A thin 1 px connector line (hex 3A3040) runs from the shifted plate down to the ship's anchor point so the player can trace which plate belongs to which hull. The shift is recalculated every frame based on camera position. At distance 170, typical fleet spacing means this triggers for at most two or three ships at a time.
    Second: selection marks. The selected ship gets a flat ring on the ground plane beneath it (radius = bounding-sphere radius times 1.1, color hex C45A20, 2 px line, no fill). This ring is drawn at the ship's feet, not around its body, so it does not collide with a neighboring ship's ring. If two ships are so close that their ground rings overlap, the ring of the non-selected ship is suppressed entirely; only the selected ship shows a ring. The targeted enemy (the one the player is about to fire at) gets a bracket: four corner brackets in hex BF3A3A, each 10 px, at the corners of the ship's screen-space bounding box. Brackets are drawn only on the targeted ship, never on the selected friendly ship, so the two mark types never compete.
    Third: pins. Waypoint pins and order pins are drawn at the ship's plate position, not at the ship's body. Since plates are already offset to avoid overlap, pins inherit that offset. The pin is a small diamond (8 by 8 px, hex D8D0C4) with a 1 px drop line to the plate.
    Edge cases.
    A ship with all three sections LOST: the plate shows three red LOST rows with their system lists. The hull bar reads 0. The ship is effectively a wreck. The plate stays visible until the wreck is removed from the board, then it fades out over 0.5 seconds.
    A ship with zero shields but the generator intact: shield bar is empty, number reads "0", no stripe overlay (regen is still working, the pool is just depleted).
    A ship with zero shields because the generator is destroyed: shield bar is empty, number reads "0", stripe overlay present, "no regen" tag present.
    Camera zoom: if the player zooms closer than distance 100, plates scale down proportionally (minimum 70 percent of base size) to avoid occluding the ship models. If the player zooms farther than 250, plates scale up to 130 percent and the section detail rows collapse to just the section name and status letter (P, M, E) to save space.
    More than 12 ships on screen: plates for enemy ships beyond the 12 closest to the camera are hidden. Friendly plates always show. A small counter in the HUD corner reads "+3 enemy ships off-plate."
    (b) Least sure decision
    The vertical stacking offset for overlapping plates. It works for two or three ships, but in a tight melee with five ships clustered, you get a tall stack of plates with connector lines that could look cluttered. An alternative is to hide all but the selected ship's plate when more than three overlap and require the player to click individual ships to see their plates. I chose stacking because the brief asks for always-readable state, but I am not confident five-deep stacks will look clean.
    (c) Biggest risk
    The per-frame plate repositioning and overlap detection. With 12 ships, each needing a screen-space projection, overlap check, and potential offset recalculation, this runs every frame. In Godot this is cheap for 12 objects, but if the game ever scales to 20 or 30 ships in a battle, the overlap resolution becomes an O(n-squared) check. Mitigation: run the overlap check every third frame and lerp plate positions to their targets over two frames to hide any jitter. Flag this for the engineering leg to confirm the ship count ceiling.
    Screen 3: CAPTAINS AND ADMIRALS
    (a) Design
    Portrait banner. The banner is a horizontal strip that slides in from the right edge of the screen. It is 320 px wide and 72 px tall. It positions itself in the upper-right quadrant, specifically anchored at (viewport width minus 330 px, 90 px from the top). This keeps it clear of the selected ship (which is typically center-screen), the fire controls (bottom-right), and the fleet status (top-left). It never covers the center 60 percent of the screen.
    The banner contains, left to right: a 56 by 56 px painted portrait (from the existing admiral portrait set, or a new captain portrait set in the same style), a 2 px ember border around the portrait, then a text block. The text block has two lines. Line 1: the speaker name and rank, 14 px, color F2E8D8. Line 2: the message, 12 px, color B8AFA4, wrapping to a maximum of two lines. If the message exceeds two lines, it truncates with an ellipsis; the full text is available in the battle log.
    The banner slides in over 0.3 seconds (ease-out cubic), holds for 3.5 seconds, then slides out over 0.3 seconds. Total screen time: 4.1 seconds. It does not pause the game. It does not capture input. The player can click through it, select ships, and fire weapons while it is visible. If a second banner event fires while one is showing, the current one slides out in 0.15 seconds and the new one slides in. No queue longer than three banners; if four events fire in rapid succession, the oldest is dropped.
    Banner triggers and their content:
    Hail from an allied captain: portrait of that captain, name, message text (e.g. "Prow section lost, weapons offline. Falling back to grid C4.").
    Admiral command: portrait of the admiral, name, command text (e.g. "All ships: converge on Raider 2.").
    Section loss on a friendly ship: portrait of that ship's captain, name, a short line (e.g. "Engines gone. We are drifting."). The specific lost systems are not repeated here; the plate in Screen 2 handles that. This banner is the emotional beat.
    Kill confirmation: portrait of the captain who scored the kill, name, line (e.g. "Target destroyed. Good shooting, crew.").
    Captain identity on the ship card. The existing ship card (in the shipyard from Screen 1 and in any fleet overview) currently shows a lieutenant name and XP. This expands to:
    A 32 by 32 px captain portrait (painted in the same style as admiral portraits, but at lower detail since it is smaller). Positioned to the left of the name line.
    Captain name, 14 px.
    Callsign, 12 px, in parentheses after the name. Format: "Cmdr. Elara Voss ('Wraith')." Callsigns are drawn from a per-class pool at ship creation. They are cosmetic and do not affect mechanics.
    One trait line, 12 px, color 9A8A7A, below the name. Examples: "Aggressive: +10 percent weapon damage, -5 percent evasion." or "Cautious: +8 percent shield regen, -5 percent speed." The trait is a single mechanical modifier with a small gameplay effect. It is assigned at captain generation and does not change during a run.
    XP bar, 120 px wide, 6 px tall, below the trait line.
    Captain identity in the fallen roll. The fallen roll (the record of lost ships, accessible from the run timeline) currently lists ship names. Each entry now shows:
    The captain's 32 by 32 px portrait, desaturated to 40 percent.
    Ship name and class.
    Captain name and callsign.
    Cause of death (see Screen 4 killmail).
    A short epitaph line, 11 px, italic, color 7A7068. This is generated from a small template pool keyed to the captain's trait. Example for an Aggressive captain: "Went down firing." For a Cautious captain: "Held the line to the last."
    Data sources. Captain portraits: a new set of 20 to 30 painted portraits in the admiral style, stored as individual PNG files at 128 by 128 px (downscaled at runtime to the needed size). Callsigns: a string table of 40 to 60 entries, tagged by tone (aggressive, steady, cunning, grim). Traits: a fixed list of 8 to 10 traits, each with a name, description, and stat modifier pair. Assigned randomly at captain generation, no duplicates within a fleet.
    Edge cases.
    The player has no captains yet (start of a new run, flagship only): the flagship captain is pre-generated. The portrait, callsign, and trait exist from the first frame.
    A captain is promoted (XP threshold): the portrait does not change. A small chevron icon (10 px, gold hex C4A020) appears next to the name to mark the rank-up. No banner fires for promotion; it is logged silently.
    The admiral portrait set does not have a portrait for a specific event (e.g., a generic fleet-wide alert): use a fallback icon, a 56 by 56 px ember-colored ship silhouette, in place of a face.
    Multiple section losses on the same ship in quick succession (prow and engines lost within one second): one banner fires for the first loss. The second loss updates the plate in Screen 2 but does not fire a second banner, to avoid spam.
    The player mutes or disables banners in settings: the banner is suppressed entirely. All events still log to the battle log text feed.
    (b) Least sure decision
    The trait system. Giving each captain a mechanical trait (the +10 percent damage, -5 percent evasion style modifier) adds a small stat layer that the current game does not have. It is a minor addition, but it touches the stat resolution code and could interact with refits, Mk II upgrades, and section losses in ways that need balancing. I am not sure this belongs in this screen's scope or should be deferred. The portrait, callsign, and visual identity are clearly in scope. The trait is the part I would most readily cut if the schedule is tight.
    (c) Biggest risk
    Portrait asset volume. The brief calls for painted portraits for every captain plus the existing admirals. If the fleet can have up to eight ships, and captains are unique per run, the player needs at least 20 distinct portraits to avoid obvious repetition across a multi-run session. Commissioning or painting 20 to 30 portraits in the established style is a real art pipeline cost. If the art team cannot deliver, the fallback (procedurally tinted silhouettes) will look cheap next to the existing admiral portraits and break visual cohesion. This is an asset dependency, not a code risk, but it is the thing most likely to slip.
    Screen 4: AFTER-ACTION REPORT
    (a) Design
    Replacement of the VICTORY panel. The current end-of-battle panel (summary paragraph, salvage-one-wreck choices, XP lines) is replaced by a full-screen report. The background dims to hex 0A0A0F at 92 percent opacity. The report panel is centered, 780 px wide, 540 px tall, dark ember panel style (hex 141018, 1 px border hex 3A3040). It is scrollable if content exceeds the height.
    Top section: battle outcome header. 48 px tall. Left side: "VICTORY" or "DEFEAT" or "WITHDRAWAL" in 28 px display font, color F2E8D8 for victory, BF3A3A for defeat, BF8A2A for withdrawal. Right side: battle duration in minutes and seconds, 14 px, color 8A7A6A. Below the header, a 1 px divider line (hex 2A2430).
    Per-ship report rows. One row per friendly ship that participated. Each row is 64 px tall. Columns, left to right:
    Ship name and class, 14 px, left-aligned. 180 px wide.
    Captain name and callsign, 12 px, color 9A8A7A. 140 px wide.
    Kills: integer, 16 px, centered. 60 px wide.
    Damage dealt: integer, 14 px, color C4A020. 90 px wide.
    Damage taken: integer, 14 px, color BF5A3A. 90 px wide.
    Captain XP earned: "+14 XP" format, 12 px, color 7AAACF. 80 px wide.
    Status: "SURVIVED" in green or "LOST" in red, 11 px. 70 px wide.
    If the fleet has more than six ships, the rows scroll within a 384 px tall region.
    MVP designation. The ship with the highest composite score (kills times 100 plus damage dealt minus damage taken times 0.5, all as tuning starting points) gets a small star icon (16 px, gold hex C4A020) next to its name and the label "MVP" in 10 px. Only one MVP per battle. In case of a tie, the ship with more kills wins. In case of still a tie, the first ship in fleet order wins.
    Salvage section. Below the ship rows, a divider, then the salvage-one-wreck choices. This keeps the existing mechanic. Each wreck is shown as a small card (140 px wide, 80 px tall) with the wreck's ship class, a hull integrity percentage, and a "Salvage" button. The player picks one. This section is unchanged in logic, only restyled to match the panel.
    XP summary footer. At the very bottom of the panel, a single line: total fleet XP earned this battle, 14 px, color 7AAACF. Below it, a "Continue" button (160 px wide, 40 px tall, standard ember button style) that closes the report and returns to the run map.
    Killmail card on the run timeline. The run timeline is the existing horizontal progression view. Ships that were lost during the run are marked on it. Clicking a lost ship's marker opens a killmail card, a small popup (300 px wide, 180 px tall) anchored to the marker. Contents:
    Lost ship name and class, 14 px.
    Captain name and callsign, 12 px.
    "Killed by:" line, 13 px, naming the enemy ship (class and identifier, e.g. "Raider 3") and the specific weapon that dealt the killing blow (e.g. "Heavy Torpedo, prow mount").
    Turn number of the killing blow, 11 px, color 8A7A6A.
    A small 48 by 48 px thumbnail of the enemy ship class (from the same 3D model renders used in the shipyard roster).
    The captain's epitaph line (from Screen 3), 11 px italic.
    The data source for the killmail is the battle log's damage event stream. The last damage event that reduced a ship's hull to zero records the source ship ID and the weapon ID. This data must be captured at the moment of destruction, not reconstructed afterward.
    Edge cases.
    A battle where no friendly ship is lost: the status column reads "SURVIVED" for all rows. The salvage section is hidden (no wrecks to salvage from the player's side; enemy wreck salvage is handled separately if the existing mechanic includes it).
    A battle where all friendly ships are lost (defeat): every row reads "LOST." The MVP star is still awarded (the ship that dealt the most damage before dying). The Continue button reads "Accept Defeat" instead of "Continue."
    A ship that was destroyed and then somehow re-engaged (if the game has a mechanic for that, such as emergency repairs): the status reads "RECOVERED" in amber.
    The killmail for a ship destroyed by a section loss rather than direct weapon fire (e.g., engines destroyed, ship drifts into a hazard): the "Killed by" line reads the hazard name and "hazard" as the weapon type.
    The player closes the report without picking salvage: the salvage choice is forfeited. A confirmation dialog appears: "Leave without salvaging? This cannot be undone." Yes / No buttons.
    Very large damage numbers (over 999): format with a comma separator, e.g. "1,247."
    (b) Least sure decision
    The MVP composite formula. I proposed kills times 100 plus damage dealt minus damage taken times 0.5, but this is arbitrary. A support ship that tanks enormous damage and keeps the fleet alive might deserve MVP more than a ship that sniped one kill. I do not know if the design council wants MVP to be purely offensive or to value survivability. The formula is a tuning starting point as stated in the holds, but I want to flag that the weighting will need playtesting.
    (c) Biggest risk
    The killmail data capture. The game's current damage event stream may not record the specific weapon ID and source ship ID at the moment of a hull-zero event in a way that persists after the battle ends. If the battle log is cleared or compressed at battle end, the killmail has no data to read. The engineering leg must confirm that the last-damage-event record is written to the persistent run state, not just the transient battle scene. If it is not, this feature requires a save-system change, which is more invasive than the UI work suggests.
    Strongest Objection to the Brief
    The brief asks for four screens that all add visual and data complexity, but it does not mention the battle log or any text feed. Screens 2, 3, and 4 all depend on structured combat data: which section was lost and what it disabled, which weapon fired which shot, which captain said what and when. The current game may log some of this, but the brief treats it as if the data already exists in a clean, queryable form. If the battle log is a flat text string or a sequence of unstructured events, then every one of these screens requires a data-layer refactor before any UI work begins. My objection is this: the brief should have included a fifth deliverable, a combat event schema, defining the exact fields (timestamp, ship ID, event type, section ID, weapon ID, source ID, target ID, damage value, result) that every system writes and every screen reads. Without that schema, four different developers building four different screens will make four different assumptions about the data shape, and the integration will be painful. I would add that schema task as a prerequisite and sequence it before any of the four screens enters production.
