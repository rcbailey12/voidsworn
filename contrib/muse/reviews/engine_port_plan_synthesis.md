## Part 2. Golden-file test design (both legs agree on the invariants; tolerances and scenario lists merge)

Invariants, both legs, adopted without change:

- Oracle: Node sim3d.js untouched, plus battle.js and core.js as the Node side. A small Node runner loads the sim, a scenario file, steps the sim, and writes per-turn state. The Godot side runs a headless harness in the rules language. If C# wins the spike, the harness needs a dotnet build step first; the exact headless C# invocation on 4.7.2 is UNSURE and is a spike task.
- Test 0 (Qwen, adopted): before any golden, the ported PRNG emits its first 1000 draws from seed 1001 on both sides and the lists must be identical. The JS PRNG's algorithm and location are UNSURE from the evidence; finding them is spike work. No golden runs until Test 0 passes.
- Hash: SHA-256 over canonical integer-only state per turn (keys sorted, fixed separators, sets sorted by stable id). Integer fields have ZERO tolerance: any hash mismatch is a fail, full stop. Float fields are compared separately, field by field, and never enter the hash. If a float difference changes an integer outcome in the same or a later turn, the test fails on the integer field; the float tolerance does not excuse an integer divergence.
- State hashed per turn (union of both legs' lists): scenario id; seed; turn index and phase; RNG seed and draw counter; credits and every resource; both rosters (hull ids sorted, per-ship HP/hull/armor/shield/heat/ammo, module ids, admiral ids, status effect ids and integer durations, destroyed or retreated flags); active boons and relics as sorted id lists; battle events (actor id, target id, damage, crit flag, kill flag); encounter choice; meta flags; objective scores, control points, encounter flags; resource counters, campaign roster ids, injury counters, boon/relic/module inventory counts; any integer position or range bucket produced by quantizing a float position before a rule check. Excluded: node paths, instance ids, object pointers, dictionary insertion order, frame times, wall-clock times, FPS, particle counts, camera state, audio playhead, UI animation state, shader parameters, raw float positions and velocities.
- Physics and float positions are presentation unless they feed a rule. If a rule check uses position, range, or facing, quantize that value to a fixed integer grid in both Node and Godot before the check. Rule outcomes must live outside the physics solver, because Godot's own docs warn physics is not deterministic regardless of engine (DeepSeek cite, title-only, re-check required). If the spike shows the sim state is integer or quantized only, the float tolerance applies to nothing and the report says so (both legs agree on this escape clause).
- Drift policy (Qwen, adopted): the Node oracle is frozen. If a golden fails, the Godot side is wrong until proven otherwise; any intentional rules change is made in Node first, re-baselined, then ported. This feeds A3 as drift cost per change.
- The .bat (both legs, merged below): Windows 10, PowerShell 5.1, double-click, user never types. It sets its own working directory to the repository root, runs the Node oracle stage, runs the Godot headless harness stage (with a dotnet build step first if C# wins), runs a single Node comparator, writes a report file, prints one summary line in color, and waits for a keypress so the window never vanishes. A missing Node or Godot executable prints a plain message naming the missing program, not a stack trace. PASS looks like: a green line with the scenario count, all turns matched, 0 mismatches, and the report path, then "Press any key", exit code 0. FAIL looks like: a red line with the first mismatch in plain form (scenario, turn, field, expected, actual, and whether it was an integer exact check or a float tolerance check), plus the count of failing scenarios, then "Press any key", exit code 1. The report lists every mismatch (capped at 50 in the DeepSeek leg) and states the tolerance at the top.

Float tolerance, merged (chair recommendation, not leg agreement): the legs state the same rule with different granularity. DeepSeek gives a per-field-group table: positions 1e-3 absolute and 1e-5 relative above 1.0; velocities 1e-4 absolute and 1e-5 relative above 1.0; facing and aim angles 1e-4 radians; normalized directions 1e-4 absolute; UI and effect scalars 1e-3 absolute. Qwen gives a single 0.0001 absolute per scalar for all continuous fields. The synthesis adopts DeepSeek's table as the detailed proposal, because it distinguishes field groups, and notes Qwen's single value as consistent in scale for positions and velocities but coarser than DeepSeek's angle and direction tolerances. Opus confirms the table at the spike; the invariant both legs share is what matters: integers exact, floats bounded and outside the hash, and no tolerance at all if the sim state turns out integer-only.

Scenario suite, merged (chair recommendation, not leg agreement): the legs agree on six scenarios with fixed seeds starting at 1001, committed to the repo and read identically by both sides, but define them differently. DeepSeek: duel 1v1 (1001, 12 turns), squadron 3v3 (1002, 12), fleet 10v10 (1003, 10), stress 40 ships (1004, 5, matching the A2 stress count), campaign run (2001, 5 encounters), meta progression (3001, fixed progression). Qwen: S1 baseline battle (1001), S2 admirals/boons/relics (1002), S3 modules and waves (1003), S4 30-turn campaign run (1004), S5 full campaign with encounters and meta (1005), S6 edge cases: retreat, defeat, empty choice (1006). The synthesis adopts the union as the proposed suite (duel, squadron, fleet, stress, campaign run, meta, edge cases) with fixed seeds from 1001, and leaves the exact fixture list to Opus at the spike. The invariant is fixed seeds plus integer hashing plus Test 0, not either leg's exact scenario names.

Runner implementation, merged (chair preference, not leg agreement): both legs satisfy double-click plus pause plus plain messages, but differ in machinery. DeepSeek: the .bat runs the stages directly and uses PowerShell only for a preflight file-exists check. Qwen: the .bat launches PowerShell with -NoProfile and -ExecutionPolicy Bypass pointed at a .ps1 holding all logic, with a golden_config.txt holding the node.exe and Godot 4.7.2 paths that Opus fills once. The synthesis recommends DeepSeek's simpler shape (fewer moving parts, no execution-policy bypass) with Qwen's config-file idea adopted (one file holding the two executable paths, filled once by Opus, never edited by the user unless the window tells them to). The .bat location differs trivially between legs (tools/ versus repo root); Opus picks one. Qwen's .ps1 approach is tagged UNSURE for PowerShell 5.1 compatibility until Opus runs it; that tag stands whichever shape wins.

## Part 4. What carries over unchanged (both legs agree; Qwen adds two specific traps)

"Unchanged" means content is preserved. Format conversion is allowed. A content change is not allowed without an explicit review. Each row says what unchanged actually means and what must be re-validated after the move.

- data.js tables as JSON. Unchanged: same tables (ships, weapons, admirals, boons, relics, modules, encounters), same keys, same numbers, moved by a mechanical Node conversion script, no hand edits. Re-validate: every file parses in Godot; every row the Node sim and the Godot rules both read; admiral perk effects (fx) and Command definitions; any value the golden tests hash; number precision for integers and floats; null versus missing keys; array order where order matters; duplicate ids; required fields. Qwen trap, adopted: Godot parses all JSON numbers as float (Qwen cites the JSON class doc and a GitHub issue lead, both checkable, neither chair-verified), so the loader re-types integer fields and a table-by-table SHA-256 checksum is compared against the source tables; any value above 2^53 would lose exactness, none expected in game tables, verified by the checksum step. DeepSeek's general "number precision" validation is the same requirement stated less specifically.
- sfx files. Unchanged: the decoded audio bytes are byte-identical to the base64 payloads in sfx_data.js; no re-encoding, trimming, normalization, resampling, or gain changes; the same clip ids map to the same audio. Format conversion allowed: base64 strings become WAV or OGG files plus a manifest (Godot imports WAV, Ogg Vorbis, and MP3). Re-validate: decode count matches the base64 count; duration, sample rate, and channel count match the decoded source; checksums match the decoded bytes; every sfx id in sfx.js has a manifest entry and a file; playback routing and bus assignment; loop points, volume, and routing lived in sfx.js logic, which is a rewrite, so every sound is re-tuned by ear against the Babylon build; the actual formats inside the base64 are UNSURE. Licence question stays OPEN, exactly as recorded (see below).
- Hull assets via glTF. Unchanged: the same Blender-authored kit, exported as GLB (the kit path), feeds Godot without re-authoring; authored geometry, UVs, material assignments, hardpoint and pivot placement, and naming stay identical. Re-validate: materials and shaders re-scope from Babylon materials to Godot materials (metallic and roughness, emissive, transparency, double-sided flags, texture channels); LODs generated on import (Godot auto-generates mesh LOD for imported glTF scenes by default, DeepSeek cite, title-only, re-check required; the docs warn automatic LOD can occasionally introduce rendering issues, especially in skinned meshes); VRAM-compressed baked maps; pivot, scale, and orientation; hardpoint empties and animation clips; per-hull import check; PBR materials will not look identical to Babylon's renderer, so every hull is compared against the A2 blind stills; whether any GLB uses Babylon-specific extensions is UNSURE; the current export state of any specific hull is UNSURE because the pack does not state it. A hull-by-hull visual check against the Babylon reference stills is required.
- sim3d.js. Unchanged in Node; it is the balance oracle. No format conversion; it is not ported as a file, its logic is rewritten in Godot (step 4). Re-validate: Node version and CLI flags; fixture output shape; any change to sim3d.js is a rules change, not a port change, and must be reviewed as such.
- head.html and voidsworn-3d.html. They do not carry over as Godot artifacts. head.html is replaced by project settings naming the main scene. voidsworn-3d.html stays untouched as the Babylon fallback during the port and is replaced by the Windows export only at cutover, which is a separate decision after step 10. Re-validate at cutover: export preset, window size, input map, icon, startup scene.
- Also carried (Qwen, adopted): the golden scenario and seed files become shared project data (new, but engine-neutral), and the Node toolchain stays installed for the oracle and the extraction tool for as long as the golden suite runs.

The sfx licence question is OPEN (both legs, same framing, adopted verbatim in substance): the field guide line 350 says sound files may not be handed to anyone else, while the public repo carries clips as base64 in sfx_data.js. FINDINGS R10 records Ryan's decision that the repo stays public and sound stays as is, Sonniss clips included. That records the sound decision, not a resolution of the licence text. This plan therefore carries sfx as "carries over in form, licence question stays open for Opus and Ryan". It does not present the sound as cleared, and it does not recommend re-encoding or redistributing the clips until the licence text is resolved. Extraction into standalone audio files changes nothing about that tension and must not be treated as resolving it. The question is engine-independent and must be carried in RESULTS.md and A3 either way. Flag for A3.

## Part 5. Staying on Babylon: the 8.20 to 9.30.0 move (both legs agree on the shape; the 9.0.0 question reconciled)

Framing (Qwen, adopted): Babylon guarantees no public-API breaking changes between minor versions; breaking changes land at major versions. The 8.20 to 9.30 move crosses exactly one major boundary, 9.0, so the break surface is the 9.0 changelog plus anything the team logged at minors. Babylon's own running lists are the Breaking Changes page, the What's New page, and the CHANGELOG.md. The 9.30.0 release itself is a patch-level release (both legs agree on this characterization).

Documented breakages and changes, reconciled:

1. 9.15.0, TC39 Stage 3 decorators (BOTH LEGS AGREE). Babylon moved from TypeScript legacy experimentalDecorators to standard TC39 Stage 3 decorators. Both legs quote the same scope: it only affects code that applies Babylon decorators such as @serialize or @expandToProperty to classes you author; code that merely uses Babylon classes is unaffected. The game ships plain .js files, so expected impact is none. Whether any build step in the repo uses decorators is UNSURE in both legs. Action: grep the code for decorators before the move.

2. 9.0.0 breaking entries (APPARENT DISAGREEMENT, RECONCILED: DIFFERENT PAGES). The DeepSeek leg reports that Babylon's Breaking Changes page lists no 9.0.0 entry (only 9.15.0 in the 9.x range, plus an 8.54.2 NPE texture block change and a pre-baseline 8.10.1 camera change). The Qwen leg reports two 9.0.0 breaking entries listed on Babylon's What's New page: "Remove WebGPUEngine dependency on Engine" and a thin-instances change adding ArrayBufferView. These do not contradict each other: the legs consulted different Babylon pages, and a What's New entry is not the same record as a Breaking Changes page section. The synthesis carries BOTH reports as "each leg reports, Opus re-checks against Babylon's own pages", and does NOT adopt either leg's page as the complete record. Impact of both 9.0.0 entries hinges on whether the game touches WebGPU or thin instances; both are UNSURE from the evidence (the fx layers could use thin instances; must be checked in code before the move). Action: grep the code for WebGPUEngine usage and thin instances alongside the decorator grep. Until that grep runs, the 9.0.0 break question is OPEN, not settled in either direction: neither "no documented 9.0.0 break" nor "two documented 9.0.0 breaks" may be quoted alone.

3. 8.54.2 NPE texture block change (DeepSeek only). Marked as a breaking change in the What's New entry for the NPE texture block. Only affects code that uses the Node Particle Editor texture block. The game's effects are custom fx3d, wfx3d, and vfx3d code, not NPE graphs, so likely impact is none. UNSURE until the effect code is checked for NPE usage. The Qwen leg does not mention this entry; its absence from the Qwen leg is not a disagreement, since the Qwen leg does not claim its list is exhaustive (its own "Not checked" section says only the items surfaced are sourced and the rest of the window is UNSURE).

4. 9.0 rendering surface changes that force revalidation rather than documented breaks (BOTH LEGS, same list in substance): clustered lighting, textured area lights, node particle editor, particle flow maps and attractors, volumetric lighting, Frame Graph now a fully realized v1 feature controlling the whole rendering pipeline, Gaussian splat overhaul, rebuilt inspector. Action (both legs): every lighting and FX scene in scene3d, fx3d, wfx3d, vfx3d, gfx3d is revalidated visually against 8.20 stills; whether the default pipeline's output actually changes for this game is UNSURE until compared. DeepSeek adds that these are opt-in features, so existing lights and materials should keep working unless the project enables them and changes its render path; that reasoning is adopted as a plausibility argument, not a guarantee.

5. 9.30.0 patch character and particle precedent (BOTH LEGS, consistent): 9.30.0 is a patch release focused on correctness, including a new WebGPU canvas tone mapping and color space option (DeepSeek) and particle correctness work (Qwen, secondary gamedev.net lead). Precedent that particle behavior can shift between minors exists (Qwen forum lead about 8.8.5 versus 8.9.0 behavior); specific 9.x particle breaks are UNSURE. The synthesis adopts the combined reading: 9.30.0 lists no breaking change in either leg's report, but particle behavior is a revalidation item, not an assumed-stable item.

6. Community-reported behavior changes inside the window, not on the official breaking-changes page (Qwen only, leads only, UNSURE): a BoundingBoxRenderer access change reported at 8.22.3 and a 9.16.x report. Action: smoke-check those APIs if the code uses them. DeepSeek's general "regression surface is large" point covers the same risk from the other side: even when no single API break is documented, rendering, materials, loaders, particles, and audio need a visual and behavioral regression pass against the 8.20 baseline. That regression pass is the real cost of staying on Babylon and moving to 9.30, not a long list of documented breaks.

7. Team risk framing for 9.0 (Qwen only, forum lead, UNSURE weight): "LOW-MEDIUM risk, most v8/v9 breaking changes don't affect the codebase". The synthesis carries this as a team-forum lead, not as evidence. It sits alongside DeepSeek's regression-surface point; both can be true at once (small documented break surface, large regression surface), and neither replaces the code greps in items 1 and 2.

Unchanged by the move, still true if Babylon wins (both legs agree):
