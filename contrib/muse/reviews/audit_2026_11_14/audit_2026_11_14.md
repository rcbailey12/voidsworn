### 4. Commit messages landing on main can still close issues; only PR bodies are guarded

- Evidence: .github/workflows/auto_pr.yml lines 38 to 47 rewrite closing words in body.md before any standing issue, and line 60 records issue 256 "was closed by merges twice on Nov 10". contrib/opus/LOOP.md (Known traps) records the unguarded path in the Board's own words: closing words "in any commit that lands on main" close the issue, and the Board's own commit 1429ca3 closed PR 320 that way. The chair's own check deliveries recorded 256 closed again by merged auto-PRs on Nov 12, before the body fix landed; no closure since, so the body fix is holding. Verified sub-point (Qwen response 1, finding 8): the refresh path at auto_pr.yml lines 88 to 92 greps for "(close[sd]?|refs) #N" when deciding whether to append a closing word, so a body carrying only "Fixes #N" gains a redundant "Closes #N" (cosmetic; both are closing words).
- OBSERVED for the mechanism. Blind Rey and DeepSeek (finding 2) converge; Qwen response 2 (finding 6) overstates the body side (intended closes are the mechanism's purpose) and is not adopted beyond the commit-message path.
- Why it matters: the standing check issue is the queue's spine; each accidental closure costs a manual reopen and risks a check brief being read as finished. Direct Board commits to main (FINDINGS, LOOP) are exactly the traffic the trap line warns about.
- Fix approach: a push-to-main workflow step that fails loudly when a commit message carries a closing word before a standing issue, or the same lint in the Board's commit path; fix the refresh-path grep to cover all six verbs. Rough size: S. Confidence: high on the mechanism, medium on how soon it bites again.

### 6. Runner model integrity: the guard is provider-scoped, the resolved model is not stamped, and the running copy is hand-synced

- Evidence: tools/pc/work_issue.bat line 53 applies WORK_MODEL only when the provider prefix matches ("%P"=="%Q" on the text before the first /), so a stale WORK_MODEL naming another model from the same provider (a sonnet id on the opus arm) passes silently; the file's own comment (lines 51 to 58) frames the guard as the WORK_MODEL trap fix. WORK_MODEL is also a documented deliberate override (the usage line), so the residual risk is accidental same-provider leaks, not the feature. HANDOFF section 0 records the operational step for the running copy as a manual copy of tools/pc/work_issue.bat to work217\tools "when no run is going"; no check compares the repo copy with the PC copy. LOOP.md (LATEST, Nov 13 07:00 UTC) records the cost of the original incident: three opus-arm runs executed on Kimi and died on its quota in 90 seconds.
- OBSERVED on the repo side; the PC copy's current state was not checked (INFERRED risk). Blind Rey (finding 5), DeepSeek (finding 5), Qwen both responses (finding 9 in each).
- Why it matters: a wrong-model run wastes the scarcest resource (the API credit window) and, worse, can produce plausible work from the wrong seat that review then has to unwind.
- Fix approach: stamp the resolved model into the run's result.txt and have the review step read it; warn in the runner when the resolved model differs from the arm default, whatever the provider; have the queue watcher verify the PC copy's hash against the repo copy before launching. Rough size: S. Confidence: medium.

### 9. checks.yml disagrees with itself in three small places

- Evidence: (a) The godot-parity job downloads Godot with "curl -sSL -o godot.zip" (no retry), while the godot-game job's identical download uses "--retry 3 --retry-all-errors" (both steps in checks.yml). A transient network failure fails the parity job before any rules check runs. (b) The fixture step runs on "if: ${{ !cancelled() }}" with no gate on the load step, while the load step's failure path writes "The Godot checks after this step were not run" into the step summary; the fixture step is plain Python and does not need the load, so the behaviour is defensible and the sentence is wrong. (c) The fixture step has no timeout of its own, and the godot-game job's named limits already sum to 1560 s (120 + 300 + 780 + 360, 26 minutes) before checkout, setup, download and import overhead, against the file's own claim that the limits "add up to under 27 minutes" so the job "is never cut off" by the 30 minute limit.
- OBSERVED. DeepSeek (findings 7 and 8) and Qwen response 2 (finding 8); chair-verified against the full checks.yml text, including the arithmetic.
- Why it matters: individually trivial; together they are how a gate's own documentation drifts from the gate, which is the failure mode this whole audit series exists to catch early.
- Fix approach: add the retry flags to the parity download; gate the fixture step on load success or correct the summary sentence; give the fixture step a timeout and restate the budget with the real numbers. Rough size: XS. Confidence: high.
