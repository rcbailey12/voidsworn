## 2. Findings

1. [BLOCKER] The unlockAll testing grant still executes at every boot. READ (pack): main3d.js line 11 runs the grant "unless an option is explicitly false", and the census confirms it is "a testing leftover" whose buy handlers have "no UI call sites". READ (pack slice): the settings handler for the toggle exists in campaign3d.js, but the sliced settingsHtml() renders no unlock row, so a normal player cannot turn the grant off. INFERRED: this is dead-and-dangerous, not residue: it silently defines the shipped progression, and the Oct 28 admiral leveling redesign replaces the ladder it unlocks.

2. [BLOCKER] The retired mobile layer is live code that can trigger on real PCs and override accessibility defaults. READ (pack slice): G.mobile is computed from "(pointer: coarse)" plus a small window dimension (scene3d.js line 4), and the boot sequence in main3d.js line 11 sets G.fxReduced=false when G.mobile is true and no explicit fxSet exists, and G.quality='medium' when no quality option is saved. READ (pack): the same flag drives battery frame skipping (scene3d.js line 52), texture and shadow budgets, and the touchWords text rewrite. INFERRED: a touchscreen laptop or handheld PC under the size threshold is a PC by the Oct 24 ruling but is treated as a phone, losing reduced-flash protection at boot. That is a live behavior defect for an edge class of players, not just dead weight.

3. [BLOCKER] The torpedo design comment contradicts the live constants in a file the Godot oracle copies. READ (pack slice): the comment at battle.js 531-535 says "10 harder 1 hex off, 25 harder 2 hexes off" and "Range 6 and the cooldown stay", while line 536 sets TORP_RING=[0,5,15] and the weapon row in data.js gives startorp r:5. READ (pack): the port "treats the browser code as its oracle" for parity checks. INFERRED: a porter or a parity-test author reading the comment implements or expects the wrong penalties and range; the constants are the live truth and the comment is the defect.

4. [FIX] NEXT.md retires its own gates in the header and keeps them in the body. READ (pack slice): the banner says "Phone and Pixel gates below are retired (PC-only)", and the same file's publish gate still reads "one battle on the Pixel for anything visual". READ (repo): the file still contains 5 "Pixel" mentions, PROGRESS.md 7, BACKLOG.md 5, matching the census counts exactly. INFERRED: a builder who skims to the gate list, which is the part of the file written as instructions, can block a publish on a retired device check.

5. [FIX] PROGRESS.md is stale operational guidance with no superseded marker. READ (pack slice): it points at a claude.ai artifact URL and a /home/claude working directory, and its status line reads "Last published build: Veteran AI, mobile map, onboarding". READ (pack): CLAUDE.md's start-here rules route builders to HANDOFF.md and the findings registry instead. INFERRED: nothing in PROGRESS.md itself tells a new builder it is history; followed literally it sends them to a dead artifact, a dead path, and a retired mobile target.

6. [FIX] The desktop base wording itself uses touch phrasing in places, independent of the mobile rewrite. READ (repo): the action-strip hint strings at ui3d.js:669 are written with "Tap a gold hex to move" and "tap Done with ship" as base text, and the TIPS objective entry in the pack slice says "tap the map chip under it". READ (pack): the census describes the base wording as desktop Click/Hover with Tap produced by the rewrite, which is true of the TIPS array's firing text but not of the hint line. INFERRED: the wording drift is in the source strings, so retiring touchWords alone does not make the desktop text consistent.

7. [FIX] The counted-flash merge window conflict is real in the record but narrower in the tree today. READ (pack): the census states the window three ways, "0.12 s in code, 0.33 s in a comment, 0.12 s in the doc". READ (repo): at this pin the Godot fx constant (fx.gd FLASH_WINDOW), the comment above flash_ok in the same file, and the fx API doc all say 0.12 s; no 0.33 flash comment exists in the current fx files. INFERRED: the live risk is no longer three disagreeing sources in the port; it is the surviving 0.33 recommendation in the audit record being mistaken for a spec. The cleanup is to mark that recommendation superseded, not to change the number.

8. [NOTE] startorp's evMult:2 is dead in live play, but the drift is local to that row. READ (pack): the census states the Ithar weapon trait "overwrites in live play, so the value only exists in no-trait simulations". READ (repo): the star trait in data.js sets evMult to 1.2, while the plain torp and htorp rows also carry evMult:2, where the field is live data used by the hit calculation and the weapon panel's "(slow)" badge. INFERRED: a blanket cleanup of evMult would break real behavior; only the startorp row's value is misleading, because the trait always replaces it for the one faction that fields the weapon.

9. [NOTE] ARC_NAME defines a Rear arc no weapon uses. READ (pack slice): ARC_NAME includes R:'Rear'. READ (pack): the census states no weapon uses it, under "a standing rule that guns never face backward". INFERRED: harmless in the browser; the only risk is a porter treating the full table as a spec and building rear-arc support the design forbids.

10. [NOTE] Pre-rename names persist in comments and doc headers. READ (pack): "code ids and many comments use the pre-rename faction names" while display names are the Sunward Crusade and Eclipse, and "ids never change" is the standing rule. INFERRED: low build risk, moderate readability risk; comments that read as prose should use display names or say "id" explicitly, and ids themselves must not be touched.

### 4. GODOT CONSEQUENCE

Most threatening to the port: the torpedo comment (wrong constants in an oracle file); the unlock grant and dead unlock economy riding along in copied campaign files; the mobile layer's behavior branches if they are parity-tested rather than excluded; and stale root docs steering a builder or a model agent before they reach the live plan. ARC_NAME's Rear entry and startorp's evMult are second-order oracle risks: a parity test that iterates the full tables will assert dead values.

Browser-only residue the port can safely ignore: the Babylon CDN load and the frozen shell; PROGRESS.md's artifact URL and working directory; the Pixel gates as verification steps; touchWords as a mechanism (Godot has its own input and text path), though the base strings it rewrites still need the wording fix in the shared text.

### 5. CLEANUP SHAPE

Smallest safe order, respecting the freeze (browser changes only where they fix something that breaks; data changes in the shared data file):

1. Oracle exclusions first, zero browser risk: mark the mobile branches, touchWords, the unlock grant, and the dead buy handlers as excluded from Godot parity expectations, so the port stops inheriting them while the browser question is decided.
2. Copied-guidance rewrites, zero runtime risk: fix the torpedo comment to the live constants; mark the 0.33 flash recommendation superseded; rewrite the phone comments in main3d.js.
3. Docs: add a superseded banner to PROGRESS.md or move it to an archive folder; strip the Pixel gate and build queue from NEXT.md, keeping the banner and the effects brief; archive BACKLOG's phone entries.
4. Shared data and shared text: annotate or remove ARC_NAME's Rear entry and startorp's dead evMult value in the shared data file; fix the "tap" wording in the base hint and tip strings.
5. The one genuine fork, decided explicitly rather than by default: the boot grant in the frozen browser. Turning it off is the honest fix for a confirmed testing leftover, but the browser build has no shop UI, so off means its LEGACY and admiral content becomes unreachable there; keeping it means the frozen build ships fully unlocked by design intent rather than by accident. Either answer is defensible; leaving it undecided is not.
6. Deferred until the browser build is retired: deleting the mobile layer and the dead handlers from the browser files themselves.

## 5. Questions for the designer

1. Should the unlockAll boot grant be turned off in the frozen browser build as a break-fix, or kept there (because that build has no shop UI and its content would become unreachable) while being stripped from the Godot side only? Stakes: every boot of the shipped build currently grants the full unlock set, and the port's starting state depends on which answer is chosen.
2. Is a one-line G.mobile=false override in the frozen build an acceptable break-fix, given it changes behavior only for the touchscreen and small-window PCs the retired layer currently misclassifies? Stakes: without it, that class of PC players keeps medium quality, frame skipping, touch wording, and reduced-flash forced off at boot.
3. May the stale root docs be deleted or archived outright (PROGRESS.md in particular), or must they stay in place with banners? Stakes: banners have already failed once as a control (NEXT.md's body kept its gates under its own banner), so the choice sets how much stale guidance the next builder or model agent can still follow by accident.
