## Question 2: what the three layers prevent, and what they do not

Layer 1 (Ryan's words, verbatim, timestamped, append only, written by whichever chat heard them, the same turn) prevents F1 outright: there is one list, both chats write it, and a later reader checks the list instead of a memory of a chat. It also kills the quote invention half of F5 and the "Im5 is my preference" class: a quote that is not in the log is not Ryan's words, and anyone can check in seconds. It gives F4's timers a premise to cite and be checked against.

One protocol must be added to layer 1 and layer 2 together (DeepSeek, adopted): the CONFLICT rule. When the log holds two Ryan quotes that conflict on the same fact and no later Ryan quote resolves them, the current truth page for that fact says CONFLICT, quotes both entries with their chats and times, and asks. It never resolves by restatement, by recency, or by R number. Under this rule the Sunward fighter page today would read CONFLICT, not "SF3 stands", and PR 776 would have been blocked by the page itself rather than by an outside check. Qwen's second response strengthens the same point into a state: CONTESTED as a first class blocking state that stops truth page writes and dispatch on that fact until Ryan's words arrive, and that outranks a green GitHub (PR 776 was green and wrong). Adopted.

Layer 2 (one short current truth page per topic, superseded lines removed, each line citing what it rests on) prevents the general form and most of F2 and F9, on one condition: status that GitHub holds must be demoted to pointers (question 9), or the pages become OPEN_WORK with better typography. With that condition, a correction lands in exactly one place, and a cold reader has exactly one live page per topic. One amendment to the Board's draft: lines rest on two kinds of evidence, Ryan's words (cite the log line) and artefacts (a check, a measurement, a build sheet: cite the file). Forcing every line to cite Ryan's words would fill the pages with stretched quotes, which is F5 in a new costume. Qwen's second response adds a mechanical version of the same guard, adopted: for typed facets (fighter, bomber, flagship, shape codes), the code in the line must appear literally in the cited quote or artefact. "SF3 stands" citing a morning calls summary fails it; the IM5 weakening fails it.

Layer 3 (the librarian) prevents nothing by itself; it catches. It catches F6 mechanically and completely. It catches F2 and F8 drift on a sweep cadence, hours instead of never. It flags F5 candidates (a rule shaped sentence with no words log citation) for ratification; it cannot decide them.

Not prevented by any layer: a worker who does not read the page (mitigated, not solved, by the entry document checks that already exist); a ruling Ryan gives outside both chats (the log only holds what a chat heard; the discipline is that a ruling counts when it is logged, which Ryan can enforce by saying "log that" anywhere); a chat forgetting to log (the backstop is the coverage check in question 3: every FINDINGS R row must resolve to a words log entry); and drift in the build artefacts themselves, which is the recipe and checks system's problem, not the memory system's. Qwen's first response adds one honest limit: the librarian's cadence cannot catch a conflict in real time; the cheap narrowing is a write time grep, when a chat appends a ruling, over the log's recent entries for the same topic names, flagging a collision before a worker starts. Adopted as a should, not a must: it costs one grep at the moment of writing.

## Question 3: what the librarian checks, and what it must never do

Mechanical checks, scriptable, run on every push and every sweep, extending contrib/opus/tools/doc_check_tests.js (the runner, run_all_checks.js, already picks up every *_tests.js file, and checks.yml already runs the suite on every agent branch push):

1. Every repo path named in the entry documents exists (already in doc_check; keep).
2. HANDOFF's FINDINGS range, if a range is still used, has its top equal to FINDINGS' newest R, no tolerance. Better: replace the range with a pointer and check the pointer resolves. (Flash would keep the tolerance of 3; the chair follows the blind leg, DeepSeek and both Qwen responses: exact, or a pointer.)
3. Every R number cited in RULEBOOK, factions.md, HANDOFF and LOOP exists in FINDINGS and is not marked SUPERSEDED without the citing line saying so.
4. Every verbatim quote attributed to Ryan in RULEBOOK, factions.md and the current truth pages matches a line in the words log exactly. This single check kills the F1 class at the point of writing, not at the point of damage.
5. Every R row in FINDINGS has at least one words log line behind it (a ruling with no words is flagged for the Board to source or strike, never silently kept).
6. Typed facets: a design code asserted in a truth page line (SF3, IM5, H10 and their kin) appears literally in the cited quote or artefact.
7. The generated open work page (question 4) matches GitHub: no row names a merged PR or a closed issue as waiting; hand edits inside the generated block fail.
8. Issue hygiene: a title naming a round or a design code while the branch or delivery notes carry a later round or a different code is flagged; each multi run issue has exactly one CURRENT BRIEF comment.
9. Running labels (question 9): any issue labelled running past its status comment's cap with no new commit AND no status comment update is flagged (DeepSeek's heartbeat amendment: a long job may not commit for hours, so the test is silence, not commits alone); any branch pushed in the last sweep window with no running label and no PR is flagged the other way; two running labels sharing one worktree or branch are flagged.
10. Timers: every registry entry cites a words log line or an R number that is still in force; a timer whose premise is superseded and not voided is flagged before its fire time; a timer whose target is a permission file (gpu_go.txt) may only be owned by the seat that owns the file.
11. Direct pushes to main touching files other than LOOP.md and FINDINGS (the R102 rule) are flagged in the sweep report. The three Nov 14 HANDOFF pushes would have been caught the same night. Longer term this belongs in branch protection, where it stops being a flag and becomes a fact (Qwen response 1).
12. Retired documents: every file on the retired list carries the NEXT.md style banner; entry documents and skills may not link to a retired file as live; a new root level markdown file that is not on a whitelist is flagged.
13. No em dashes in changed text (already in checks.yml; keep). The words log is exempt by design, since quotes are verbatim, and the check must know that or it will flag Ryan's own punctuation.

Judgment checks, for Muse, on the sweep cadence:

1. Citation support: sample the newest ten lines added to current truth pages and read each against its citation. A line whose citation does not carry it (the summary inversion class, F5's A18 and A19 case) is flagged with both texts quoted.
2. Rule hardening watch: scan LOOP and HANDOFF additions for rule shaped sentences ("always", "never", "stands", a named design called final) with no words log citation; list them for the Board to ratify, demote to notes, or strike.
3. Duplicate fact watch: when the same fact appears in two live pages with different values, file it as one flag with both citations.
4. Timer intent: read the timer registry against the words log; a timer whose premise cites a superseded ruling is flagged, and so is a timer whose intent no longer matches the words even when its citation still resolves.
5. Conflict wording: when two log entries differ, is it a reversal, a different scope, or a mis hearing? The librarian writes the question for Ryan, never the answer.

The librarian must never: decide, amend or strike a rule; edit Ryan's words (the log is append only; a correction is a new line citing the old); close an issue or a PR; merge anything, including its own fix up PR; change a label, a title, or a status comment (it flags those to the Board; see question 6 for why this is a hard mechanical limit, not a preference); rewrite history (FINDINGS rows, docs/archive, delivered reviews) except by the archive's own conventions; restate a fact it cannot cite; invent a citation to pass a check; widen its own token; or send Ryan anything directly. Its flags for Ryan travel through the Board or through Muse's normal reporting, in the batched form Ryan already asked for.

## Question 6: can Muse be the standing librarian

Yes for the judgment half, no for the nightly half, and the design should say so plainly instead of pretending otherwise. The constraint is in LOOP's own seats section: "RYAN STARTS EVERY MUSE RUN and Muse reads its briefs only on issue 256". Muse has no daemon. A librarian that runs nightly cannot be a seat that runs only when started.

There is a second, harder constraint the council surfaced and the chair adopts as decisive (Qwen response 2): Muse's token is a fine grained PAT scoped to this repo with Contents read and write only, injected by a surrogate. Contents access can push a branch. It cannot open a pull request, post or edit a comment, set or clear a label, or read check runs. So the librarian's outputs that live on GitHub's side (the fix up PR itself, the report comment, label flags) must be carried by a GitHub Actions workflow running on the repo's own GITHUB_TOKEN: Muse pushes a librarian branch (librarian/sweep-<date>) and a report file; the workflow opens the one PR and posts the report. The token must not be widened to buy the clock or the comments; the workflow already exists as a pattern (auto_pr.yml opens PRs from agent branches today, per checks.yml's own header comments).

So the split: the script carries every mechanical check, on push in CI (the pattern exists) and nightly on a GitHub Actions schedule, and it produces the state snapshot (open issues, PRs, labels, running comments) that the judgment pass reads. Muse carries the judgment pass at the moments Muse is actually started: at each hand over that involves Muse, and whenever Ryan starts a Muse session, the librarian skill's checklist runs after the script's report, before new work. That cadence matches how the failures actually bite: F1 and F5 bite at hand overs and rulings, which is when Muse is present.

Evidence Muse can do the judgment half: the Nov 6 audit (issue 706, 11 findings, merged via PR 711) and opus_check_770 and 776, which caught the SF3 record from the outside with exactly the citation tracing the librarian needs, and, on Ryan's personal side, a weekly reconciliation sweep that already runs this pattern against a different memory store (judgment led, short report, silence when nothing is found). Evidence of the limit, stated against myself: my board watcher state file corrupted itself on Nov 14 (F8), so any state the librarian keeps must be schema checked plain text in the repo, never a private JSON on one machine. If Ryan later wants a true nightly judgment pass, the honest route is a scheduled Muse run, which does not exist today; the script's nightly report is designed to be the input that makes a started Muse's pass fast when it happens.

## Question 7: the librarian itself, concretely

**(a) How it runs.** Three triggers. On every push to an agent branch: the mechanical suite, inside the existing checks.yml standing checks job (no new infrastructure; run_all_checks.js picks up new *_tests.js files by name). Nightly: a GitHub Actions scheduled run of the same suite in sweep mode (it reads all live pages, not just the diff), which regenerates the open work page, checks timers and running labels against the API, and, when there are mechanical fixes, pushes them to a librarian branch for the workflow to open as the sweep's one PR. At each hand over: whoever hands over runs the judgment checklist (the Board in its run step 7 rewrite, Muse when started), because a hand over is when stale state does its damage; HANDOFF section 0 cites the sweep id and time so a stale hand over is visible. Seat: the script on Actions for the mechanical half (cost: minutes of CI time, no model tokens, no seat's quota); Muse for the judgment half when started (cost: one read of the script's report plus the sampled pages). Nothing in the design needs Ryan to start the mechanical half, ever.

**(b) How it works.** Inputs, in read order: the words log (newest month first); the contested list (facts currently marked CONFLICT or CONTESTED); the current truth pages; RULEBOOK; FINDINGS (newest R rows, full file for citation lookups); open issues and their CURRENT BRIEF comments; open PRs and checks; running labels and status comments; the timer registry (question 8); LOOP's Known traps (read only, for context). Checks in order: (1) layer 1 integrity (append only, fields present; fail here and stop, since nothing downstream is trustworthy, per Qwen response 2); (2) the mechanical suite of question 3; (3) words log coverage (every FINDINGS R has a log line); (4) quote fidelity and typed facets across live pages; (5) status pointer checks and the generated page's freshness; (6) judgment sample (question 3). Output: one fix up PR per sweep at most, opened by the workflow from the librarian branch, containing only mechanical fixes, each commit message naming the check that produced it; and one short report, posted by the workflow, in three parts: fixed (in the PR), flagged for the Board (record conflicts short of Ryan, rule hardening candidates, label and title items, since the librarian cannot touch those itself), flagged for Ryan (only genuine ruling conflicts, the SF3 and SF4 class, and contested facts blocking dispatch). Hard limits: as question 3's never list, plus: it never edits the words log except to append; it never touches docs/archive; it never opens a second fix up PR while one is open; it stops and reports if its own checks disagree with each other, rather than picking a winner.

**(c) Skills and tools.** A skill file, .claude/skills/librarian/SKILL.md (a fourth skill, so doc_check's entry list grows by one, as Qwen response 2 notes), holding: the three layers and which is immutable; the input read order; the check list, split blocking versus warning; the judgment checks; the fix up whitelist and the never list; the report format; the citation forms (words log id, or artefact path); the contested protocol; and the branch handoff to the workflow, since the token is Contents only. The Board's and Muse's seats both read skills from the repo (three skills already live under .claude/skills/ and are named in doc_check's entry list), so one skill file serves every seat that runs the judgment half. Tools: tools/librarian_tests.js as a new *_tests.js beside doc_check_tests.js, reusing its patterns; the quote fidelity, label and timer checks are plain GitHub API reads plus text search, the same operations the Board's board check already runs ("gh api REST, never GraphQL", LOOP run step 2). The LLM wiki pattern's three verbs map cleanly: ingest is the words log discipline (same turn capture) plus the generated GitHub block; query is the current truth pages (compiled, cited, one home) reached through HANDOFF section 0; lint is this librarian. No new platform, no database, no service: files, CI, and one skill.

**(d) How every other agent works with it.** Two things per seat, no more. Every seat that hears Ryan rule: log the words the same turn, verbatim, with the chat named. Every seat that starts or ends a job: the running label and status comment are set or cleared in that same step, by the runner or dispatch script wherever one exists, by the starting seat where none does. Everything else (briefs as CURRENT BRIEF comments, single R citations, pointers not restatements) is a habit the librarian's checks enforce after the fact, so the per turn ask stays at two.

## Question 8: the always on agents article, mapped

The article (Anthropic, "Building always-on agents", linked by Ryan Nov 15, 2026) names five primitives: event inbox, timers, memory, permissions, outbox. Mapped onto this repo and its seats:

**Event inbox.** The article: one durable list, one active worker per inbox, deduplication by source id, the inbox as source of truth. We have: GitHub issues as the job queue, issue 256 as Muse's inbox specifically, and the LOOP lock as the one worker convention. Missing: an inbox for Ryan's words. His rulings arrive in two chats, each chat keeps its own record, and the same ruling arriving twice in different forms (F1) is not detected as a duplicate because there is no shared list to deduplicate against. Worth adding: yes, the words log is exactly this primitive, and it is the cheapest item in the whole design. GitHub stays the jobs inbox; do not build a second queue beside it (Qwen response 2). One active worker per item is the running label of question 9.

**Timers.** The article: timers live in their own durable store, split into one off follow ups and recurring schedules, and fire into the inbox. We have: the Board's send_later check ins, Muse's scheduled jobs on Ryan's side, and gpu_go.txt as a one line state file. Missing: a registry (no single list of what is scheduled, why, and on what premise), the follow up versus schedule split, and any premise check at fire time. The 07:30 GPU trigger (F4) is a follow up that outlived its premise and behaved like a schedule; the Kimi quota retry is a schedule that outlived its seat (F4). Worth adding: a timers page in the repo (id, kind, fire time or cadence, premise with its citation, owner seat, status including voided and voided by), read by the librarian; and a rule that a follow up dies when the ruling it cites is superseded, and a seat cancel kills its timers in the same act.

**Memory.** The article: store only what cannot be looked up again; where another system holds the fact (its example is an issue tracker), store a pointer; user instructions in their own file; a curation pass ("dreaming") that replaces outdated entries; save key facts before compaction or a new session. We have: R251's one home doctrine is this, stated before the article arrived; FINDINGS as history; docs/archive as labelled old memory. Missing: enforcement (the doctrine is prose, the breaches are F2, F9 and the general form), pointers instead of copies for GitHub held facts (question 9), and the curation pass itself, which is the librarian. The Board's thread resets (a fresh Board thread from Nov 15, 00:00 UTC) are compaction events; HANDOFF section 0 is the manual save before reset, and the design formalises it: no thread reset without a section 0 rewrite, already the habit, made a checklist line. Workers get the same rule in miniature: resume fields written before a cap or a compaction (question 5). Not worth adding: any search or vector layer over FINDINGS; 305 KB of plain text with R numbers is already the index (Qwen response 2).

**Permissions.** The article: a credential store outside the agent's environment (a proxy injects credentials), auto mode classifiers for higher risk actions, deferred tool calls that pause a run until the user answers. We have the strongest fit of the five: Muse's GitHub access runs through a scoped fine grained token injected by a surrogate, so the credential never sits in the agent's environment or in any file (set up Nov 14, 2026, scoped to this one repo, Contents read and write); approval cards are deferred calls in everything but name; R75 and the branch naming rules scope what each seat may write. Missing: mechanical guards for process permissions, as F7 shows (R102 breached three times in a day, no alarm), and a structured deferred state: today a held question is a prose line in LOOP ("Waiting on Ryan"), and the SF3 hold shows the failure mode of a deferred call answered by the seat that asked it. Worth adding: branch protection for the R102 files, and CONTESTED (question 2) as the deferred state, cleared only by a words log entry. Keep Muse's token narrow; the workflow holds the GitHub side scopes (question 6). A full auto mode classifier is not needed while no seat runs fully autonomously (Qwen response 1).

**Outbox.** The article: a run ends by sending, by deciding nothing needs sending, or by deferring; message volume is tuned with evals; start quiet and earn attention. We have: LOOP's run step 6 ("Tell Ryan only when something lands or needs him: two lines and one image") and PushNotification for unattended runs, which is the start quiet discipline in local words. Missing: delivery verification. On Muse's side, a scheduled reminder was twice marked delivered by the scheduler while no user visible message existed (Sep 23, 2026, recorded in my AGENTS.md); the fix was to verify against the actual message record before calling anything delivered. Worth adding: the librarian's own report counts as delivered only when posted; any seat reporting "Ryan has been told" names the message, not the intention; one report per sweep and one consolidated question list per hand over (the 13:35 UTC LATEST line, which mixes GPU, Kimi, Codex and job moves in one paragraph, is the local example of volume without structure). A formal volume eval is overkill; the flag count of question 7(e) is the cheap version.

Net: of the article's gaps the Board listed, all four hold up under the evidence (no single inbox; no timer registry; LOOP and HANDOFF copying GitHub state; no restart proof record of in flight workers, F8). The one addition the chair presses, which the article implies and the Board's list does not: deduplication is a property of the inbox, not of the reader. F1 was not two people failing to communicate; it was two inboxes with no shared id space for the same event. The words log fixes the id space.

## Question 9: one source of truth, and where "running" lives

The Board's answer holds up: the repo is the one source of truth for every seat; inside it, each fact has exactly one home; facts GitHub tracks live only in GitHub; the status files point and never restate; "running" is a label plus one status comment edited in place, set by whoever starts the job in the same step, cleared when the job reports. The evidence supports each part: F2 is what restating costs, F8 is what unrecorded running state costs, and the runner setting the label itself is the right call because the seat closest to the work is the only one that reliably knows the moment it changes (the same reason the chat that hears Ryan's words writes the log line).

Four amendments, each tied to a failure above, three of them from the council:

1. **CONTESTED outranks green (Qwen response 2, adopted as the headline amendment).** GitHub being correct does not make the design fact correct: issue 769 says SF3, PR 776 was all green, and the fighter was disputed. A pointer only system would have told every worker "SF3, all green". Contested and deferred must be first class states, recorded on the truth page and the issue, that block dispatch on that fact even when every check is green. A wrong line already on main is fixed forward with a marker, not silently reverted, since main cannot be rewritten.
2. **The registry is machine written, or it rots like the ledger did.** The status comment's fields are mechanical only: seat, machine, folder or worktree, branch, started, cap, last commit sha, heartbeat time, waits on, how to resume. Whoever starts a job sets the label and comment through the runner or a dispatch script wherever one exists; a chat typing them by hand is how OPEN_WORK happened (F2, F7). The librarian cross checks the sha against the branch head each sweep; a mismatch is a flag, not a judgment call. A comment is not a lock (Qwen response 2): the label is the claim, set first, then re read; two claims on one worktree or branch fail the check.
3. **Caps on the pointer files, enforced by the check.** HANDOFF section 0 stays at about a page because doc_check learns to count it; LOOP's LATEST roll up rule (about 15 lines, already in R251) gets the same mechanical treatment. Pointers creep back into prose unless something counts. The generated open work page carries its timestamp and a generated marker, and dispatch never reads it.
4. **The librarian's own hands are tied by its token, so its flags route correctly.** Labels, titles and comments are the Board's and the workflow's to change; the librarian flags them (question 6). The predictable break is a job whose starter forgets the label entirely; the reverse check (question 3, item 9: recent branch pushes with no label and no PR) catches most of it, and the fix is a flag to the Board, never the librarian guessing a status comment into existence.

What breaks, honestly stated: the words log discipline in a chat that is mid crisis (a ruling given while a run is failing will sometimes not be logged the same turn; the coverage check, question 3 item 5, is the backstop, and an unlogged ruling is recoverable precisely because FINDINGS still quotes it); two chats appending within minutes of each other (the SF3 and SF4 gap was about six minutes; the write time grep narrows the window, the sweep closes it, and Ryan knowing both chats log to one file lets him self correct in the moment); and GitHub as the status home means a GitHub outage blinds every seat at once, which is acceptable because the same outage already stops merges, checks and deliveries today.
