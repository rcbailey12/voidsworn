# Red team audit: QA engineer leg (blind Rey, Oct 30, 2026)

Seat: QA engineer, defect hunting and release readiness. Evidence: the QA pack (saves and persistence audit, event free-exit eval, wave 3 deep QA pack, drift synthesis, open checks, findings-to-tests ledger, core.js excerpt), plus direct code reads in the local clone and the filed harness, cited by file and line where used. Findings are ranked by severity for this seat.

## Findings

1. **The cutover still deletes every browser save, and what exists to prevent it is a fixture set for an importer nobody has built.** OBSERVED. The saves audit's BLOCKER stands at this pin, and direct read confirms it in the port's own code: godot/campaign/campaign.gd carries the decision in a comment, "browser saves are not carried over", and a grep over godot/**/*.gd finds no reference to the browser key voidsworn.v1. The 26 importer fixtures filed in wave 5 verify a converter's inputs and outputs, but no converter ships in the tree for them to verify against. Cost: on cutover day, all of META (renown, unlocks, mastery, favour, stats) and every in-progress run is lost, and QA cannot test a data path that does not exist. A BLOCKER with test fixtures and no implementation is still a BLOCKER.

2. **The shipped build cannot reproduce a new player's game, because the unlockAll testing grant is on by default and cannot be turned off in the UI.** OBSERVED at main3d.js:11: "if(o.unlockAll!==false){ for(const k in LEGACY) META.unlocked[k]=true" and every admiral is granted in the same breath. The pack adds that the toggle handler never removes granted unlocks and the settings panel has no unlock row. Cost: every real session runs fully unlocked, so the designed progression (renown ladder, admiral unlock order, doctrine gating) is the one configuration that has never been exercised by actual play, and every save written carries the grant forward into the import decision in finding 1. QA has no shipped configuration in which to validate the new-player experience at all.

3. **Closing the tab mid-battle is a free, unlimited retry of the identical battle at full strength.** OBSERVED mechanics: battle state is never serialized (saveRun clones RUN only), the pagehide handler at main3d.js:20 only logs a battle_abandon event and saves local, hull damage is written back only in finishBattle, and the per-node seed rebuilds the same battle from the start on return. INFERRED consequence: a player losing a fight can close the page, reopen, and replay the same battle with an undamaged fleet, as many times as they like, at zero cost. In a game whose contract is that losses are permanent and generational, the easiest exploit in the build is the browser's close button, and any player can find it by accident.

4. **The regression suite is red by design, so it cannot gate anything.** OBSERVED at findings_tests.js:9, "exit 1 while any pinned defect is unfixed", and line 507 exits 1 whenever any test fails; at the pin, 40 of 48 tests fail. The ledger frames this as the point, and as a defect ledger it is excellent. As a test program it has no green baseline: a 41st failure, a brand new regression in a fixed area, is indistinguishable from the 40 expected ones without reading every message. Nothing in the pack shows the suite wired into a build, push, or release step. Cost: the project's best defect asset produces no pass or fail signal anyone can act on, exactly when the Godot port most needs a gate to copy behavior against.

5. **The harness cannot load the layer where the worst defects live.** OBSERVED at game_loader.js:41: "const files = ['data.js', 'core.js', 'battle.js']". campaign_run.js and campaign_meta.js are never loaded, which is why 41 of the ledger's 125 findings sit at TESTABLE-NOT-WRITTEN and why the importer fixtures README repeatedly routes around functions described as outside the loader's reach. Cost: events, rewards, the Nemesis, end-of-run, and save-adjacent campaign logic, the layer containing findings 1, 3, 6, and 7, has the thinnest automated coverage in the project, and every future campaign fix lands without a regression net unless the loader grows first.

6. **The ruled free-exit guarantee has two different definitions in the project's own checks, and the shipped data fails both.** OBSERVED. The eval's definition (always enabled, plus a forbidden-effects list) fails 7 of 33 events, haven included. The ledger's EVT-5 test (findings_tests.js:133) defines free more narrowly, result keys limited to cred and xp, and checks only events carrying a fight option; it fails on haven too. The other six eval failures (storm, reactor, squall, mutiny, scout, saboteur) have no regression test under either definition. Cost: when the port implements the ruling, whichever oracle the implementer picks, the other one can still fail afterward, and six events are covered by neither. A guarantee with two non-matching oracles is not yet a guarantee.

7. **Save repair deletes ships silently, with no itemized record a player or support could use.** OBSERVED from the saves audit: repairRunIds drops unknown ids across relics, inventory, fleet ships, ship mods, captain perks, and the pending reward; "deletes that ship, its captain, its perks and its fitted refits". The player sees one toast with counts, the repair fields are then deleted, and the run is re-saved; the only per-ship record is a raw JSON no UI reads. OBSERVED at core.js:49, SAVE_VERSION is 2 with only a v1 to v2 step and generic default filling, so there is no migration chain to catch a rename. INFERRED: the first future change that renames a data id converts directly into unrecoverable, unlistable player losses, and nobody can reconstruct afterward what any given player lost.

8. **The one forensic artifact finding 7 depends on is write-once per profile.** OBSERVED at core.js:117: the raw repaired copy is stored only under the guard "!localStorage.getItem(STORE_KEY+'.repaired')". A first repair event consumes the slot forever; a second, different corruption or repair later in the profile's life keeps no raw copy of the save that failed. Cost: the artifact support would ask for is guaranteed absent precisely in the repeat-failure cases, which are the cases that most need diagnosis. The saves audit flagged this as untraced; the direct read confirms the guard does exactly that.

9. **A map generation guarantee is broken in about 2 percent of maps, and the code comment asserts the opposite of the code.** OBSERVED in core.js genSector: the comment reads "the column before the rest stop always offers an elite", while the conversion looks for a battle or event node to convert and silently does nothing when the column rolled neither. The wave 3 sweep measured 84 of 4,500 maps failing (1.87 percent); the ledger's compact sweep W3-1 fails on 25 of 900. Cost: the failure is silent, seed-dependent, and invisible to a player, who simply never sees the promised step-up fight; and because the browser files are the port's parity oracle, the broken guarantee and the false comment both travel unless the port is told otherwise.

10. **The retired mobile layer still executes at boot on real PCs and overrides an accessibility default, with no test watching it.** OBSERVED at main3d.js:11, in the same boot block as finding 2: "else if(G.mobile) G.fxReduced=false" and "else if(G.mobile) G.quality='medium'". The drift synthesis establishes that the mobile flag derives from pointer type and window size, so a coarse-pointer desktop in a small window qualifies, and grades this the drift item's most serious finding. INFERRED from the ledger's scope: no test in the findings suite covers boot flag behavior, so nothing stops this class of residue from returning after cleanup. Cost: an edge class of desktop players gets reduced flashes forced off and quality forced down before they have touched a setting, and it happens in the one code path every session runs.

## Verdict

NOT READY FOR CUTOVER: the browser build is well instrumented for a frozen build, but its data story fails QA, with every player save deleted at the Godot cutover, the progression configuration real players run never validated, and a regression program that is red by design and blind in the campaign layer. The single most important attack: finding 1, the saves BLOCKER still stands, and the wave 5 fixtures test an importer that does not exist yet.

## Not checked

- Mid-battle stuck states: the pack's "no softlocks" result covers map structure and battle setup legality, and battle termination only indirectly through 0 timeouts in 216 bot battles. No dedicated probe that a started battle can always be won, lost, or abandoned was in the evidence, so this seat cannot confirm the headline beyond its actual scope.
- Live cloud behavior: the stamp reconciliation, the malformed-cloud branch, and the storage-full path in saveLocal were read, never exercised; cross-device outcomes are untested in this evidence.
- The Godot build itself: battle scene persistence, the career profile store, and whether any Godot-side test program exists were outside the pack.
- Human play: every pilot in the evidence is the game's own bot. Retry-by-closing (finding 3) is established from code mechanics, not from an observed player session.
- Save size and performance over long profiles: META.tel is capped, but RUN.map, fleet, and fallen growth across a long-lived profile were not measured in the pack.
- Whether the findings suite runs anywhere automatically (CI, push hook, release checklist): the pack contains no evidence either way.
