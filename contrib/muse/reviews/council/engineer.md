# Council Audit: Software Engineer Lens (Architecture and Tooling)

Auditor: Software Engineer, red team council of five.
Basis commit: `4fa29bd Add files via upload` (output of `git log --oneline -1` in `~/workspace/voidsworn-repo`, run at the start of this audit).
Scope read: `build.py` in full, `head.html`, `main3d.js`, `core.js`, `AGENTS.md`, `CLAUDE.md`, `HANDOFF.md`, `BACKLOG.md` including section 4c, `docs/ship_pipeline/README.md` and `AUDIT_SYNTHESIS.md`, plus surveys of all 18 concatenated JS files and the Python tooling (`smoke.py`, `gallery.py`, `loadprobe.py` read closely, the rest sampled). Prior reviews and `AUDIT_v53H.md` were skimmed to extend, not repeat, them.

## Verdict

GO WITH CONDITIONS, structural, not cosmetic. One person plus AI help can still change this codebase, but only because that person holds the load order, patch order and state map in his head and in handoff documents. The code does not carry that knowledge. The next big bug will not come from a wrong formula. It will come from an edit that is locally correct and globally wrong: a renamed global that the build does not check, a wrapper patch applied in the wrong order, a new field on `RUN` that `normalizeRun` and the simulator never learned about, or a hull asset that exists on one machine and not in git. The project already knows this. `BACKLOG.md` section 4c says the first job is to "make the code reviewable by other AIs: split the giant files, break up the 1,000+ character one-line functions" because "Outside reviews keep half-reading the huge files." That self diagnosis is accurate and it is still unfixed. Until it is done, every new system adds risk faster than game.

What saves the project is that its safety nets are real where they exist: a seeded rules RNG, a paranoid save validator, a stall guard, a broad `smoke.py`, and a headless simulator sharing the actual rules files. The problem is coverage. Each net covers the last disaster, not the class of disaster.

## Findings (most severe first)

### 1. There are no modules. Load order is the API, and five mutable singletons are the coupling. OBSERVED

`build.py:8` builds the game by concatenating 18 files in a hard coded list, in this order: `meshopt3d.js, data.js, core.js, battle.js, scene3d.js, ships3d.js, fx3d.js, sfx_data.js, sfx.js, gfx3d.js, vfx3d.js, wfx3d.js, campaign_meta.js, campaign_run.js, ui3d.js, campaign3d.js, perf3d.js, main3d.js`. There is no import, export, namespace object or IIFE boundary around game code (the one IIFE in the set is the vendored decoder, `meshopt3d.js:4` `var MeshoptDecoder = (function () {`). Every top level `function`, `const` and `let` in every file becomes one shared global scope inside a single `<script>` block.

State ownership is five globals that any file may read or write. `G` is defined once at `scene3d.js:4` as one giant object literal holding engine, scene, camera, quality, views map and bounds. `B` is `let B=null` at `battle.js:5`. `RUN` is `let RUN = null` at `core.js:125`, `META` at `core.js:74`, and `SETUP` at `ui3d.js:13`. Reference counts across the JS show the coupling plainly: `G.` about 1,705 hits, `B.` about 1,325, `RUN.` about 511, `META.` about 182. Nothing enforces who may mutate what. `sim3d.js` replaces `RUN` wholesale with a hand built literal (see finding 5), `main3d.js:11` rewrites `META.unlocked` and `META.admirals` at boot, and `campaign3d.js:34` sets `B=null` inside a title screen wrapper. A change to the shape of any of these objects is a change to every file at once, with no compiler, no type checker and no search that can prove completeness, because access is dynamic as well as direct (for example `G.scene`, `B.units`, bracket access in telemetry and profiling code).

For a solo plus AI workflow this is decisive: an AI reviewer cannot determine the blast radius of an edit from the edited file. Prior reviews repeatedly needed "Not checked" sections for exactly this reason.

### 2. Cross file monkey patching is a load bearing technique, and it is invisible at the definition site. OBSERVED

At least 20 production wrappers replace a function defined in an earlier file with a wrapper defined in a later file, using the `const _x = x; x = function` pattern.

In `campaign3d.js` alone: line 10 wraps `show` to add the fleet showcase on map screens, line 31 wraps `mapScreen`, line 34 wraps `titleScreen` (disposing views, clearing overlays, setting `B=null`, injecting two menu buttons), and line 99 wraps `newShip` so a reserve captain silently takes command of a newly built ship, with a `setTimeout` toast as a side effect.

In `perf3d.js`, a file whose name suggests measurement, lines 31 to 113 wrap eight production functions: `battleScreen` and `ACT.c3skirmish` gated behind `whenHullsReady`, `tel` rewritten to inject profiler data, `FRAMES.reset`, `endBattleFlow`, `settingsHtml` (splicing a row in by string position), `ACT.c3opt`, `disposeAllViews` and `buildBattleEnv`. Performance work here is not an observer. It changes when battles start, what telemetry says and what settings contains.

`sim3d.js` does the same thing for instrumentation at lines 355, 453 to 455 and 554 to 559, wrapping `fireWeapon`, `useAbility`, `hitChance`, `applyHit` and `swarmPhase`. Some wrappers are installed inside test functions and restored by hand, for example the `stallGuard` swap at `sim3d.js:244`.

None of this is discoverable from the original definition. `function battleScreen(cfg)` at `campaign3d.js:47` does not say that the shipped behaviour is the `perf3d.js` wrapper. Stack traces, searches for callers, and AI reviews all see the wrong function first. Reordering two files in the `build.py` list, or moving one wrapper, silently changes game behaviour with no parse error and no duplicate name error, because each wrapper is a legal assignment. This is the single most likely source of the next "works on my build, broken in the publish" bug.

### 3. The build has guards, but they guard the last failure, not the namespace. OBSERVED

`build.py` is 19 lines and does three things: pick a Babylon source, stamp a `BUILD_ID` from the clock and short git hash, and concatenate. Its v41 guards at `build.py:11` to 15 check two things: duplicate top level function names via the regex `^(?:async\s+)?function\s+([A-Za-z_$][\w$]*)`, and that the concatenated script parses under `node --check`.

What it does not check is larger. Duplicate `const`, `let`, `var` and `class` names are not checked, yet in a single script scope a duplicate `const` is a hard `SyntaxError` that `node --check` would catch only as an opaque parse failure, and a duplicate `let` redeclared through a wrapper assignment is legal and silent. `smoke.py` has a broader duplicate check (it scans `function` plus `const|let|var|class`), but `smoke.py` uses its own file list at `smoke.py:6` with only 14 files. It omits `meshopt3d.js`, `gfx3d.js`, `vfx3d.js` and `wfx3d.js`, which `build.py` includes. So the stricter check runs on a different, smaller program than the one that ships. Two lists, maintained by hand, already out of step: that is the finding in miniature.

Nothing checks the CSS. `head.html` line 138 opens a second `#app{` block that is never closed on its own; the following rules, including a redefined `body{...}` at the next lines, are nested inside it until a later stray `}` around the modal section restores the cascade. Browsers recover, which is precisely why it survived. Earlier UI review work flagged the same unclosed block, and it is still there at this commit, because no tool in the repo parses `head.html` as CSS.

Test and publish also run different Babylon builds. `build.py:3`: test mode loads `node_modules/babylonjs/babylon.js`, any other mode loads `https://cdnjs.cloudflare.com/ajax/libs/babylonjs/8.20.0/babylon.js` from a CDN. Version is pinned by URL for publish and by `package.json` (`"babylonjs": "^8.20.0"`, a floating caret range) for test. A caret update in `node_modules` can therefore make the tested engine differ from the shipped engine, and the committed `voidsworn-3d.html` (1.4 MB, tracked in git) can differ from both. There is no lockfile discipline beyond a 492 byte `package-lock.json`, no hash of inputs, and the output file name depends on a string argument that defaults to `test`, so a bare `python3 build.py` produces `index_test.html`, not the publish artifact. `AGENTS.md` tells agents the build is `python3 build.py`, full stop.

### 4. The files are too dense to review, and the project has already paid for that. OBSERVED

Line counts understate it, because this codebase packs whole functions onto single lines. `battle.js` is 1,143 lines, `ships3d.js` 983, `ui3d.js` 724, `scene3d.js` 684, `fx3d.js` 625, `sim3d.js` 575. Longest ordinary lines run 900 to 1,979 characters (`sim3d.js:565` at 1,979, `campaign_meta.js:158` at 1,549, `fx3d.js:76` at 1,521, `ui3d.js:63` at 1,498), excluding the two generated monsters: `sfx_data.js:2` at 482,079 characters (one line of base64 audio) and the vendored `meshopt3d.js` at 13,627 characters on one line. `disposeAllViews` at `fx3d.js:76` is a single 1,521 character line that disposes textures, glow lists, trails, dead lights, debris, views, hulks, projectiles, torpedoes, DOM plates and the model cache. A reviewer who misses one clause misses a leak.

Density has a measured cost. `AUDIT_SYNTHESIS.md` records that one of three outside audits was "low on facts" with headline bugs "false against the real code", and its drop in code was not merged. `BACKLOG.md` section 4c makes reviewability the first health pass item. Knowledge lives in overlapping prose (`PROGRESS.md` 533 lines, plus `HANDOFF.md`, `NEXT.md`, `AGENTS.md`, `CLAUDE.md` kept in step by hand), not in a module map the code enforces.

### 5. Testing is real but lopsided: a strong simulator and smoke suite, no unit layer, no CI, and a harness that drifts from the game. OBSERVED

There is no test directory, no test runner in `package.json` (which declares one dependency and no scripts), no lint or type config anywhere in the repo root, and no `.github` CI configuration. Nothing runs automatically on a push. Every check is a script a human or agent remembers to run.

What exists deserves credit (see below), but its shape is the risk. `sim3d.js` runs headlessly by `eval` of only three files at `sim3d.js:3` (`data.js`, `core.js`, `battle.js`) plus hand written stubs (its own `animMove`, `animWeapon`, `animExplode`, fake `CLOCK`). Rules code that moves into `scene3d.js`, `ui3d.js` or `campaign_run.js` silently leaves the simulator's world. The simulator also builds its own short `RUN` literals in `sim()` and `match()`, while production `RUN` comes from `runDefaults()` in `core.js` with roughly 28 fields (`heat`, `reserve`, `seenEvents`, `curNode`, `reinf`). The sim bypasses `normalizeRun`, so a rule reading a newer field reads `undefined` in the sim and a real value in the game, and balance diverges with no failure. Prior review work already found the sim's player bot weaker than the game's enemy default.

Below that there is no unit layer for the pure core: hex maths, `derive()`, `genSector`, migration and `normalizeRun`. Those deterministic functions, exactly where save and balance regressions hide, are only exercised end to end through a browser at minutes per run (full smoke about 4 minutes on the PC, over 25 in the sandbox, per `HANDOFF.md`).

### 6. Determinism is well designed at the centre and leaky at the edges. OBSERVED, with one INFERRED consequence

`core.js:2` to 8 implements a seeded mulberry32 RNG with the stated contract that "Each battle reseeds from B.seed, so a seed plus the same moves replays a fight" and that "Cosmetic effects keep Math.random." Rules files honour it remarkably well: `battle.js`, `data.js`, `campaign_run.js` and `campaign_meta.js` contain zero `Math.random` calls, and `core.js` itself uses it once, to seed `RNG_S` at line 4 before any battle reseeds it.

The edges leak in ways that matter to replay and to testing. `campaign3d.js:35` picks the title showcase factions with `Math.random()`, and `campaign3d.js:112` picks a skirmish faction from a pool with `Math.random()` before calling `startBattle`. Those picks decide which fleet a battle is fought with, so they are setup, not cosmetics. `ui3d.js:38` shuffles captain name order with `sort(()=>Math.random()-.5)`, which is both unseeded and a biased shuffle. `newId` in `core.js` builds ship ids from `Date.now()`, so two runs with the same seed still produce different unit ids, and anything keyed by id (telemetry joins, save diffs, replay comparisons) cannot be matched across runs. INFERRED: a strict "same seed, same fight" replay test would fail on ids and on any showcase or skirmish path, even though in battle rolls are clean. The claim in the comment is therefore true for battle resolution and not yet true for the whole game, and no automated check enforces the boundary. A single new `Math.random` in a rules path, added by an AI contributor who did not read the comment at `core.js:3`, would break replays silently. That is a lint rule waiting to be written: forbid `Math.random` outside an allowlist of effects files (`fx3d.js` 47 uses, `vfx3d.js` 27, `wfx3d.js` 27, `scene3d.js` 8, `gfx3d.js` 8, `sfx.js` 4 are all plausibly cosmetic).

### 7. Save discipline is the best engineered part of the game, and it is still one bad field away from trouble. OBSERVED

Credit first: `core.js` has `SAVE_VERSION=2`, `saneMeta`, `saneRun` and `saneSave` validators, a `runDefaults()` that is described at `core.js` as "the one place that knows every field a RUN carries", `normalizeRun` backfilling arrays and captain objects, a `.bak` fallback for a damaged local save, unknown content ids logged once and skipped via `unknownId` instead of throwing, and `Persist.save({meta:true})` separating meta stamps from run stamps so "a purchase or a report on one device never rolls back a newer run from another".

The fragility is structural. Version is a single integer at 2 while migrations are a growing pile of one off flags inside `migrateMeta` (`backfilled`, `wonFix41`), each re parsing the telemetry log to recover mastery, favour and won factions. Every new persistent feature adds another flag and another replay of history, and there is no fixture suite of old saves to prove the chain still works. `saveRun` at `core.js` deep copies by `JSON.parse(JSON.stringify(RUN))`, which silently drops functions, `undefined` and any future non serialisable field with no warning. Cloud sync in `Persist.connect` resolves conflicts by comparing `META.updated` and `META.runAt` timestamps from two devices, so clock skew is a correctness input. And boot itself undermines the economy the save protects: `main3d.js:11` grants every `LEGACY` and `ADMIRALS` unlock unless `META.opts.unlockAll===false`, which prior campaign review work found leaves the purchase handlers with no live render site. A progression system whose unlock gate is bypassed in the boot sequence is a bug magnet: testers and players see different economies depending on one option flag.

### 8. Error handling favours never crashing over ever knowing. OBSERVED

There are about 252 occurrences of the exact swallow `catch(e){}` in the game JS, plus many more catches that only `console.warn`. Some are correct (optional visual effects should not kill a battle, and `boonFx` at `battle.js:475` wrapping a floating text call is a fair example). As a default style, though, it means whole subsystems can fail permanently and invisibly.

The reporting path caps itself. `reportError` at `campaign3d.js:5` starts with `if(++ERRS>5) return;`, so after five errors nothing further is reported, including a sixth, different and fatal one. The `error` and `unhandledrejection` listeners at `campaign3d.js:6` to 7 feed that counter, and `frameError` in `scene3d.js` throttles further. The mitigation that works is `stallGuard` in `battle.js` (around line 813), which races async steps against a visibility aware timer, telemetres the stall and skips ahead. But recovery by skipping converts real bugs into "orders lost in interference" log lines, and with the cap at five a session can absorb a recurring fault all evening and report almost none of it.

### 9. Assets live in git without LFS, the built file is tracked, and generated data ships as code. OBSERVED

There is no `.gitattributes` and no Git LFS configuration. The working tree carries `hulls/` at about 31 MB (108 files), `hulls_hi/` at about 79 MB (108 files), `rocks/` at about 11 MB and `rocks_hi/` at about 28 MB: roughly 149 MB of binary assets, all tracked as ordinary git blobs (216 tracked paths under `hulls/` alone, individual webp maps up to 2.9 MB). `.git` is about 144 MB in pack size. `AUDIT_SYNTHESIS.md` already records the pipeline finding that "Ship assets aren't versioned: the hull files exist only on the PC and in the published artifact. Store them with a manifest", and `BACKLOG.md` section 2 still lists "Ship files in GitHub large-file storage with a manifest (owner pick)" as undone. `AUDIT_v53H.md` separately found "About 9.2 MB of unreferenced hull meshes ship with the game: 15 files in hulls/ and 15 in hulls_hi/ from earlier concept rounds, plus a stale hulls/index.json". So the repo is simultaneously too heavy (binaries in history forever) and incomplete (the newest `.vsm` meshes are not in it at all: `git ls-files` shows zero `.vsm` files, while `docs/ship_pipeline/README.md` step 9 says the game loads `hulls_hi/CODE.vsm` on desktop). A fresh clone cannot reproduce the shipped game. That is the worst of both options.

Generated data as source compounds it. `sfx_data.js` is 482 KB in 2 lines, base64 audio parsed as code on every load. The tracked `voidsworn-3d.html` output (1.4 MB) means reviewers keep reading a stale second copy of the whole game. Reproducibility rests on `HANDOFF.md` prose about sidecar uploads, not on a verifiable manifest.

### 10. Tooling sprawl: 40 Python scripts in the root, 84 more files under tools/, no shared harness. OBSERVED

The repo root holds 40 `.py` files. Categorised by reading their headers: one build script (`build.py`), one real gate (`smoke.py`, 94 lines), a handful of behavioural checks that `smoke.py` shells out to (`softlock.py`, `step2test.py`, `striptap.py`, `cmdui.py`, `yardcheck.py`, `healtest.py`, `bosscheck.py`), two near duplicate debug variants (`smoke_dbg.py`, `smoke_dbg2.py`), one large asset gallery (`gallery.py`, 419 lines), one load profiler (`loadprobe.py`), and the remaining two dozen plus are single purpose screenshot scripts (`artshot.py`, `boardshot.py`, `closeshot.py`, `cmdshot.py`, `fxshot.py`, `intentshot.py`, `losshot.py`, `motionshot.py`, `recapshot.py`, `shapeshot.py`, `ux4shot.py`, `worldshot.py`, `wshot.py` and others). Under `tools/` there are a further 84 files: Blender pipeline scripts, PC runner jobs (`.bat` files named per attempt, such as `c19_10_kitdark_probe3.bat` through `c19_14f_probe.bat`), ComfyUI helpers and bake scripts.

Almost every root script re implements the same Playwright boilerplate (launch Chromium, serve or `file://` the test page, wait for the title menu, evaluate JS, screenshot) with its own flags, its own environment variable names and its own timeout. There is no shared Python helper module in the root. Drift is already visible: `overlapprobe.py:3` hard codes `PAGE='file:///home/claude/v3d/index_test.html'`, a path from another machine's sandbox, and `camtest.py:7` and `smoke_dbg.py:22` hard code the same foreign path, so those scripts cannot run from a fresh clone at all. `HANDOFF.md` documents the PC runner's sharp edges at length (never write `job.bat` mid run, unique staged names or stale jobs re run, CRLF, `cd` back or the job repeats). None are encoded in a tool. Screenshot scripts also mostly assert nothing: they produce pictures for a human verdict, which fits an owner who judges by screenshots, but gives almost no regression protection per file maintained.

### 11. Dead generations of code are kept alive beside their replacements. OBSERVED

`AUDIT_v53H.md` section 0 states it directly: "Effects went through three generations and all three are still in the code" (v42 shaders in `gfx3d.js`, v44 sprite pool in `vfx3d.js`, original paths in `fx3d.js`), with "a dozen effects never moved to a pool" still allocating per call. The same audit lists ownerless dead code (hidden 2D title loop, `drawShipShape`, `runDemo`, `loftMesh`, `flashers`, `hexTex`, the `quality==='low'` branches) and measures the procedural ship build run in full then thrown away by `applyAIHull`: about 3.3 seconds and 2 million vertices for 27 classes. Keeping three generations means every change must be made and reviewed in up to three places, and with no dead code check, dead code is indistinguishable from live code.

## What is genuinely well built

The seeded RNG contract in `core.js` is clean, documented at the top of the file, and actually obeyed by every rules file. That one decision is what makes the simulator, the fuzz mode and mid battle reload replay possible at all.

`Persist` in `core.js` is thoughtful: schema sanity checks before trusting a save, a one step behind backup copy, graceful degradation when cloud sync is unavailable or malformed, separate meta and run timestamps, and unknown content ids skipped with a single warning instead of a crash. Many shipped commercial games do less.

`stallGuard` plus the global error listeners in `campaign3d.js` show real reliability thinking for a phone game: async steps get time budgets that pause while the tab is hidden, stalls are telemetred, and the player is told their campaign is saved. The boot sequence in `main3d.js` is similarly defensive: the texture cache gets a 3 second race so it can never block boot, WebGL failure gets a human readable message, and the loading veil is removed on scene ready or after 12 seconds "regardless".

`smoke.py` is a serious pre publish gate. It rebuilds, parse and duplicate checks, boots to the title with zero console errors, plays a round with the `tbot3.js` bot, checks texture counts across three battles, enforces a scene budget, verifies effect shaders are warmed, walks a full campaign loop, checks telemetry and save version, then runs six regression scripts covering end cards, enemy turn recovery, frame errors, phone lock stalls, hung volleys, real taps, Command charging, shipyards for every faction, broken mesh healing, reload replay and the boss transition. Each check is named after a bug that actually happened.

The simulator's fuzz mode checks invariants a designer would want (no overlaps, nothing on blocking terrain, no NaN health, nothing off board) across randomised matchups, and `gallery.py` seeds both RNGs so visual output is deterministic per seed. `perf3d.js`, whatever its patching sins, has a real frame budget system and gated hull loading. `BUILD_ID` in every telemetry event (`campaign3d.js:16`) is exactly right for a game debugged from field reports.

## Top 3 recommendations

1. Do `BACKLOG.md` section 4c first, before altitude bands or career mode. Split the five worst files (`battle.js`, `ships3d.js`, `ui3d.js`, `scene3d.js`, `fx3d.js`) by system, break single line functions over roughly 300 characters, and publish a one page system map (system, file, entry functions, which singleton fields it owns). Promote the wrapper patches into an explicit hook registry in `core.js` where `campaign3d.js` and `perf3d.js` register `beforeBattle`, `onTel`, `onTitle` and similar hooks in declared order. This makes every later AI review cheaper and more accurate.

2. Make the build and the checks one program with one file list. Generate the file list once (a manifest in `build.py` that `smoke.py` imports or reads), extend the duplicate guard to all top level names (`function`, `const`, `let`, `var`, `class`), add a CSS parse of `head.html` that would have caught the unclosed `#app{` block, forbid `Math.random` outside an effects allowlist, and pin the test engine to the same Babylon build that publish loads. Then run `build.py` plus a fast subset of `smoke.py` plus the simulator's invariant fuzz in CI on every push, even a simple one. Add the missing unit layer underneath for `core.js` pure functions (hex maths, `derive`, `genSector` invariants, `normalizeRun` and migration fixtures built from real old saves). None of this needs a framework swap or modules on day one. It needs the existing good checks to run automatically, on the same artifact that ships.

3. Fix asset provenance and prune the tooling fleet. Move the hull and rock folders to Git LFS or versioned external storage with a checked in manifest (code, file, size, hash, tier) that `build.py` verifies before publish, delete the 30 unreferenced hull files `AUDIT_v53H.md` identified, stop tracking the built `voidsworn-3d.html`, and ship `sfx_data.js` as fetched data, not base64 code. Collapse the 40 root Python scripts onto one shared harness module, archive one off probe and shot scripts into `attic/`, and delete the hard coded `/home/claude/v3d` paths. End state: one gate, one simulator, one gallery, one load probe and a small set of named regression scripts, each runnable from a fresh clone.

## Not checked

The PC runner and Blender and ComfyUI pipeline under `tools/` were counted and sampled, not audited line by line. Babylon internals, meshopt decoding and shader compilation were taken as given. No builds, smoke runs or simulator runs were executed for this lens, so behavioural claims rest on code reading plus recorded results in `PROGRESS.md`, `AUDIT_v53H.md` and prior reviews. The cloud backend behind `window.claude.use('db')` is not in the repo and was assessed only from client code. Balance, fun, visuals and rule correctness belong to the other four lenses, except where a structural flaw makes their conclusions less trustworthy. The published artifact was not fetched, so the fresh clone claim rests on the absence of `.vsm` files in git plus the pipeline docs, not on a failed rebuild.
