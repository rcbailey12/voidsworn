## Verdict: GO WITH CONDITIONS (one blocking follow-up)

1. (BLOCKING) auto_pr.yml rewrites closing words only for the branch's own issue, in both the create path and the new refresh path. A runner commit message carrying a closing word for a different issue survives into the PR body untouched, and GitHub acts on any closing word in a body at merge. The case that matters: a codex/, muse/ or work/ branch for another issue whose commit message says "Closes #256" (or a future standing issue) would close the standing issue on merge, through the very workflow this PR hardened against that accident. Both legs found it independently; the chair's own read of the workflow agrees (the sed pattern is anchored to #$n in both paths, and the refresh path's standing test fires only when the branch's own number is 256). The fix is small: apply the closing-word rewrite for every issue in the standing list, in both paths. Until then the standing issue's protection is complete only for its own branches.
2. (NOTE) The refresh replaces the whole body of a runner-branch PR with the newest commit message. Two live consequences: anything a human wrote into such a body between pushes is erased, and a small fixup push replaces a fuller first-run report with the fixup's text (recoverable from history, but the standing body goes thin). This is the intended trade for the PR 543 stale-report problem; the Board should simply know the cost is paid on every refresh, not only on rerun reports.
3. (NOTE) The standing list exists twice: STANDING="256" in the create path and a hardcoded case " 256 " in the refresh path. When a second standing issue appears, both must change together or one path silently loses the protection.
4. (NOTE) Smaller workflow asymmetries the legs found: the refresh never updates the title (the create-time title comes from the issue, so this is cosmetic); the trigger list excludes partial branches only for codex/ and work/, while muse/ and opus/ partials rely on the in-script guard (which does catch them, so this is tidiness, not exposure); and an opus/ PR's body is built from its first commit message at create and never refreshed, so its quality is fixed by that first message.
5. (NOTE) The Node guards' one soft spot: run_all_checks.js checks the version only when run as the main module, so a future entry point that requires it as a library would run unguarded. No such consumer is in evidence. package.json's engines line is advisory, as both legs note; the real guards are the five entry scripts.
6. (NOTE) work_issue.bat's new .import restore discards every tracked .import modification before the commit, deliberate edits included. That is R144's intent (capture runs re-save them), and the Board should hold it as a standing discard rule rather than a capture-only one.
