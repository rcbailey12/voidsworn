## Seat verdict

The port's engineering is better than its paperwork, and the program steers by the paperwork (Rey). The migration's central guarantee, parity against a pinned oracle, currently rests on two oracle copies that disagree with each other (chair verified below), while the documents tracking that risk report no divergence and list already-fixed defects as pre-cutover work. At the same time, the scariest claims in this seat's pack (a process-wide race, a non-atomic save write, silenced trap warnings) are pre-fix states that the pin code has already repaired. Both directions of staleness are the same disease: syntheses lag the code, and anything routed by them inherits the lag.

## Claims register: disposition

1. **Oracle integrity: BROKEN as documented, chair verified with numbers.** Three distinct copies of battle.js and of data.js exist in the clone (root at the pin, godot/rules/test/oracle/, godot/campaign/test/oracle/), all pairwise different. battle.js: root vs rules oracle 34 changed lines, root vs campaign oracle 38, the two oracles vs each other 4. data.js: root vs either oracle about 394 to 405 changed lines (older pinned data, expected churn), the two oracles vs each other 45. core.js is identical in all three places. The synthesis-grade facts: the oracle-vs-oracle mismatch is real, nothing automatically checks any of the copies, and the two parity suites therefore certify against different snapshots of the game. Argon finding 6's framing ("both pin c7b1a78") is imprecise: both READMEs document later re-pins and c7b1a78 is a history entry, not the current state. The fix is cheap and all three prongs name it: a hash comparison inside both parity runners, failing loudly.
2. **Concurrency findings (Argon finding 1, DeepSeek finding 3): REFUTED at the pin on their stated mechanisms, chair verified.** Both legs report a shared static 8-byte scratch buffer in jsm.gd and step() as the only locked method in battle_api.gd. The pin code says otherwise. jsm.gd allocates a fresh 8-byte buffer per call (_pb8()), and its header states why: the old static buffer was a data race, fixed per the Oct 26 review. battle_api.gd:17 holds a recursive mutex that every public function wraps, and godot/rules/test/thread_test.gd exists. The legs were reading the Oct 26 synthesis's pre-fix descriptions in the pack, not the current files. What survives is narrower: golden parity is single-threaded by construction, so threaded play is covered only by thread_test.gd, and whether that test exercises threat_map()'s cache clearing under concurrency is unverified by any prong. That is a verification task for Opus, not a live race.
3. **Warning suppression (Argon finding 4): REFUTED at the pin on the trap classes, chair verified.** The leg charges that @warning_ignore_start in the rules files silences integer_division and narrowing_conversion. The jsm.gd header states the opposite and the ignore list confirms it: those two classes (plus unsafe_property_access) stay ON and give 0 warnings, checked by turning them into errors; the silenced classes are the untyped-shape warnings. The documented JS-port traps are guarded, not suppressed.
4. **Non-atomic Godot save write (DeepSeek finding 1, Argon finding 2): REFUTED at the pin, chair verified.** campaign.gd:384 implements _write_atomic (temp file, flush, rename), used for both the main save and the .bak refresh at lines 382 to 383. The migration review's "copy to .bak, then overwrite in place" describes a superseded state.
5. **CUT/SOLID hash coverage: SETTLED, covered; the divergence is closed.** The pack carried this as an unresolved document divergence. The Rey leg read the writer, and the chair confirmed: golden.js:145 builds the hashed state with cut and solid sorted arrays inside the canonical string. Terrain state is in the hash. Strike the phantom pre-cutover task from the books, and record that a coverage doubt hung over a sound mechanism because nobody read one line of the golden writer.
6. **Oct 26 music blocker: STALE, all three prongs concur.** music.json, the tracks, and CREDITS.md exist in godot/music/ at the pin (the audio seat verified 24 tracks against CREDITS.md). The migration synthesis's file-existence verdicts need re-checking against the pin before any of them drive cutover work (DeepSeek finding 10, Argon finding 7).
7. **Migration synthesis headline ("only one item is player-visible"): OVERTURNED by its own evidence (Argon finding 3, DeepSeek finding 4).** The same document's area breakdowns list NOT PORTED clearing and playing a partially computed batch in live battles, ResourceLoader.exists soft dependencies that can ship the facts-and-buttons fallback campaign UI with no error, fx_stub.gd running beside the real fx, and the ship_view.gd BoxMesh fallback. Four player-visible silent degradations, none of which any test treats as an error. The cutover build can pass a smoke check while showing fallback UI and stub effects.
8. **Saves BLOCKER vs R33: the seat's largest unmanaged risk, and it is a contradiction, not a task.** The register carries "saves BLOCKER without the importer (fixtures now built and filed)" and 26 fixture files exist to test that importer. The target code states the opposite policy twice: campaign.gd:201 ("R33: old saves are not migrated") and campaign.gd:354 ("browser saves are not carried over, R33"), and no importer code exists anywhere in the godot/ tree. No ruling document in the evidence records R33; it lives in code comments. One story must win before cutover planning is honest, and the choice is Ryan's (below). DeepSeek finding 1 and Argon finding 2 also confirm the transport gap independent of the policy: the fixtures test in-memory transformation, and no browser-to-desktop transport (export path, cloud bridge, or file import) exists in either build.
9. **Telemetry: spec filed, instrumentation absent, all three prongs in substance.** The Godot campaign's tel() call sites cover picks and outcomes (run_start, battle_end, boon_pick, shop, and similar) but none of the events the three revisit-with-data rulings actually need: no nemesis_meeting, nemesis_adaptation, weakness_revealed, regroup_open, regroup_choice, xp_grant, level_up, tree_pick, and no boon_offer (picks are logged, never the offer set and rarities the Q7 analysis needs). The events that exist are thin (run_start logs faction and admiral where the spec requires a meta snapshot; battle_start logs seed, objective, kind, faction where the spec requires both fleets and CP totals). The log is a ring capped at 600 entries embedded in the save file, which overwrites early runs during exactly the long playtest sessions the rulings need.
10. **Chair-owned defect, telemetry spec amendment (from Argon finding 8).** The filed telemetry spec's clash audit joins nemesis_adaptation to the SAME run's weakness_revealed events. Weaknesses are also inherited across runs through the Q5 loss debrief, so the join as written produces false negatives on exactly the Q4 clash rule it exists to audit. AMENDMENT, to be applied to the spec: the clash-audit join runs across the run lineage (every run in the same campaign generation chain), not the single run. The spec is a chair document already on main; this synthesis is the amendment's record until the spec file is revised in a batched push.
11. **Clean checkout cannot build the shippable game: UPHELD, 3 of 3.** godot/gen/ is gitignored and absent on main; build_assets.gd falls back to engine-test inputs outside the project (asteroids and sky), and ship_view.gd falls back silently to a plain BoxMesh. The build works on one PC because that PC holds the off-repo inputs and the generated files. No test covers .pck export contents, so test trees and oracle files can leak into the package unchecked (Argon finding 10, DeepSeek finding 2).
12. **The C# to GDScript trade is undocumented (Rey finding 9, DeepSeek finding 8).** The port plan chose C# for the rules body for type safety, with GDScript only as a spike-rejected fallback; the shipped port is GDScript throughout, untyped Dictionaries with JS field names by design, and no evidence records the spike rejecting C# or anyone accepting the residual risk. The mitigations are real and verified above (jsm.gd reproduces JS numeric semantics exactly; the trap warnings stay on). What is missing is the decision record. RESULTS.md, the enginetest gate the plan said must land before execution, is likewise absent from the evidence.

## New findings, ranked

1. **Data-integrity tooling lives outside the build's own test trees (Rey finding 7).** Three silent weapon deletions were all found by audit reads. The validators that catch this class (table cross-reference, naming lint) live in contrib/muse/tools, which no build step runs; the Godot test trees test rules parity, not data-table integrity against the rule that every variant carries a real trade and deletions are disclosed. As long as the check is external, the class recurs and is found late, at audit prices.
2. **The findings ledger is the real cutover gate and is wired to nothing (Rey finding 8).** 40 reproduced defects with tests live under contrib/muse/tools/findings_tests/; the Godot runners (run_parity.sh, run_sweep.sh) know nothing about it. Cutover can be declared on parity evidence while 40 known defects ride along uncounted, unless the ledger is named in the cutover criteria.
3. **The Godot save format has no fixture discipline of its own (Rey finding 10).** The strongest persistence tooling the project has (the fixture set, the saneSave pipeline) is aimed at a browser-to-Godot import the code has cancelled under R33, while the format players will actually live on, Godot v1 (campaign.gd:370), has no fixture set. When Godot v2 is needed, migrations for the only surviving format will be improvised.
4. **Hand-copied render and world constants have no comparison check (Argon finding 10).** FAC3D, AI_HULLS, CLS_LEN, FINISH, BIOMES, ROCKS, PLANETS are manually synced copies with no automated diff, while the generated tables are checksum-locked. Hull lengths, AI hull mappings, and faction visuals can drift silently into the export.
5. **ui_info() and view() do uncached work per call (Argon finding 9).** ui_info computes per weapon against every living enemy without the eval caching its sibling methods use (90 LOS calls where 15 would do on a 6-weapon ship facing 15 enemies), and view() rebuilds full state per call. Under phased activation at 20-plus ships, with players cycling units and previews, that is main-thread stutter in the exact interaction the ruling multiplies.

## Ranked actions: Opus lane (technical)

1. Add an oracle hash check to both parity runners: the two vendored copies and the root source, compared on every run, failing loudly. Then re-pin both oracles to the same snapshot deliberately.
2. Make silent fallbacks fail loudly in test and export builds: NOT PORTED batches, the facts-and-buttons fallback UI, fx_stub beside real fx, and the BoxMesh hull should each be a hard error in any build meant to be played, and a .pck contents test should assert what ships.
3. Close the build reproducibility gap: generated assets and the A4 ship sources get an in-repo or scripted-fetch home, build_assets.gd loses its engine-test fallbacks, and a clean-checkout build becomes a checklist item with a named owner.
4. Implement the telemetry event set the rulings need (Nemesis, regroup, XP, offer sets) as a standalone JSONL log outside the save ring, with the amended lineage join from item 10 of the claims disposition.
5. Confirm thread_test.gd covers threat_map() cache behaviour under concurrency, or add the case; single-threaded goldens cannot see this class and the seat should not have to take it on faith.
6. Wire the findings-to-tests ledger into the cutover criteria by name, and move (or mirror) the data-table validators into the Godot test tree so variant deletions fail a build step instead of waiting for an audit.
7. Give the Godot v1 save format its own fixture set now, while v1 is young; seed it from the browser fixture discipline.
8. Add a comparison check for the hand-copied constants (FAC3D, AI_HULLS, CLS_LEN, FINISH, BIOMES, ROCKS, PLANETS) against data.js, and cache ui_info()/view() behind the existing eval_begin/eval_end pattern.
9. Write the missing decision records: the GDScript-over-C# acceptance with its residual risk, and the enginetest gate outcome. One page each; the next audit should not have to excavate them.

## Ranked actions: Ryan lane (human direction)

1. **R33: does cutover carry browser progression, or does everyone start over?** Story: the claims register and 26 fixture files assume an importer carries browser META into the Godot build. The Godot code states the opposite twice (R33, in comments at campaign.gd:201 and :354): old saves are not migrated. No ruling document records R33; it may be an implementer default that hardened into policy. Stakes: in a generational game, META progression (unlocks, mastery, renown) is the product of the 80 percent loss rate; wiping it at cutover deletes the thing the losses were buying. Keeping it costs the importer plus a transport that does not exist yet (the browser build has no export path), and a decision about the unlockAll grant baked into current browser profiles (the QA seat shows imports would arrive fully unlocked). Cost, honestly framed: right now the only browser profiles in existence are your own test profiles, so deciding no-migration today costs almost nothing in player terms; deciding it after any external player touches the browser build costs their progression. The expensive version of this decision is the undecided one, because the fixture set and the code are currently building toward opposite answers. Full treatment in the final synthesis.
