# Red team audit: Software engineer seat (Rey leg, blind)

Seat: architecture and cutover risk. Method note: in addition to the pack evidence, I read the game code directly in the local clone (pin 264f441d state) and verified or refuted pack claims against it. Code citations are file and line in ~/workspace/voidsworn-fresh. Findings are ranked by severity for this seat.

## Findings

### 1. The two parity oracles disagree with each other and with the live game, today (OBSERVED)

The migration synthesis says the two vendored oracle copies (godot/rules/test/oracle/ and godot/campaign/test/oracle/) have no automated comparison, and comforts itself that "No leg found a live divergence." That is no longer true. MD5 sums at the pin: the rules oracle's battle.js (a161e192...), the campaign oracle's battle.js (655081cc...), and the live battle.js (904e6dee...) are three different files. data.js is likewise three different files (5fbcf894..., 82dca494..., bb00d51c...). Only core.js matches across all three. Cost: the parity program's whole authority rests on "Godot matches the oracle," but there are two oracles and they test different versions of the game. A rules fix or a break-fix applied to one copy, or to the live source only, silently changes what "parity" means for one stream. Until a hash check runs in both parity runners, every green parity result needs a footnote naming which oracle it was green against.

### 2. The filed syntheses lag the code: at least four "additions before cutover" are already done (OBSERVED)

The Oct 26 migration synthesis lists pre-cutover work that the pin code already contains. Atomic save write, its item 6: campaign.gd:377-388 implements _write_atomic, temp file, flush, rename, with the comment "Atomic: the new save is written whole to a temp file". The jsm.gd shared static scratch buffer, called a data race: jsm.gd now allocates per call, "a fresh 8-byte buffer per call, never a shared static one", and its header cites the Oct 26 review as the reason. Threading, rated NEEDS WORK because only step() was locked: battle_api.gd:17 and 24-25 now wrap every public function in a recursive mutex ("Every public function is a thin wrapper: lock, run the body"), and godot/rules/test/thread_test.gd exists. The warning-suppression finding said the port silences the two JS-port trap warning classes: rules.gd and jsm.gd headers document that integer_division and narrowing_conversion stay ON with 0 warnings, "integer_division and narrowing_conversion (the JS-port number traps)". Music, where the synthesis said music.json, tracks and CREDITS.md "do not exist": all exist in godot/music/ at the pin, with 11 track files. Cost: the program is steering by documents that describe a tree that no longer exists. Every synthesis-derived priority list, including this audit's pack, inherits the staleness, and effort can be spent re-fixing fixed defects while live ones (finding 1) sit in a "no divergence found" sentence.

### 3. The pack's CUT/SOLID hash claim is false at the pin (OBSERVED)

The pack and the migration synthesis carry a "document divergence" over whether the canonical golden hash covers CUT and SOLID module state, with the earlier sprint synthesis supporting exclusion. The code settles it, against the pack. godot/rules/test/node/golden.js:145 builds the hashed state with gl={cut:CUT?[...CUT].sort():null, solid:SOLID?[...SOLID].sort():null, uid:UID} inside the canonical string, and its own comment matches the README: "the board cut-outs, the set-piece hexes that block sight". Terrain state is in the hash. Cost: a phantom pre-cutover task ("a scenario exercising terrain state into the hash belongs before cutover") is on the books, and worse, a parity-coverage doubt was left hanging over the one mechanism that is actually sound. Whoever acts on the pack without reading golden.js will spend time proving a covered case.

### 4. The importer contradiction: R33 in the code cancels the fixtures' reason to exist (OBSERVED)

The claims register lists "saves BLOCKER without the importer (fixtures now built and filed)". The fixtures README describes 21 fixtures built so an importer can carry browser saves into the Godot build. But the target codebase states the opposite policy in two places: campaign.gd:201, "a Godot profile never had a browser log (R33: old saves are not migrated)", and campaign.gd:354, "browser saves are not carried over, R33". A grep of the godot/ tree finds no importer code anywhere. So one of two things is true, and the evidence never reconciles them: either R33 is the decision, in which case every browser player's META progression dies at cutover by policy, the BLOCKER label in the register is a product decision wearing an engineering costume, and the fixture set is dead weight; or the blocker is real, in which case R33 must be reversed in the code before cutover and the importer is unbuilt critical path. Cost: cutover planning cannot be honest until this is one story. This is the single largest unmanaged risk in the migration.

### 5. Telemetry: the spec is filed, the instrumentation is not there (OBSERVED)

The telemetry spec exists so three rulings can be revisited "with actual play data": regroup tension (Q-A), Nemesis snowball (Q-B), generational payoff (Q-C). The Godot campaign's actual tel() calls (campaign.gd, grep of all call sites) number 18 event names: run_start, run_end, battle_start, battle_end, node, shop, boon_pick, boon_decline, reward_pick, prize_pick, salvage_pick, variant_buy, field_repairs, reinforced, aspect_pick, arc_unlock, nem_signature. Missing entirely: nemesis_meeting, nemesis_adaptation, weakness_revealed, regroup_open, regroup_choice, xp_grant, level_up, tree_pick, boon_offer (only picks are logged, never the offer set and rarities Q7 analysis needs), debrief_shown. The events that do exist are thin: run_start at campaign.gd:1166 logs only fac and admiral, where the spec requires a meta snapshot including unlock state; battle_start at campaign.gd:2388 logs seed, obj, kind, fac, where the spec requires both fleets, CP totals and fleetPower. And the log itself is "a slim run log (events only), kept with the save; not part of parity" (campaign.gd:61), capped at 600 entries (campaign.gd:155-156), embedded in the save file. Cost: Q-A and Q-B are unanswerable from this log at all, Q-C only in fragments, and a 600-entry ring inside the save overwrites early runs during exactly the long playtest sessions the rulings need. The spec was merged Oct 29; the build does not implement it, and nothing in the evidence tracks that gap.

### 6. Asset pipeline: a clean checkout still cannot build the shippable game (OBSERVED)

The Oct 26 NEEDS WORK on reproducibility stands unrefuted at the pin. godot/.gitignore excludes gen/, and no gen/ directory exists in the clone. godot/render/build_assets.gd still falls back to engine-test inputs outside the project: line 59 tries repo.path_join("contrib/opus/enginetest/assets/env/asteroids.json") and lines 477-478 do the same for the sky. godot/render/ship_view.gd:95 still constructs a plain BoxMesh as the fallback hull. Cost: the build works on one PC because that PC has the off-repo inputs and the generated files; the repository alone does not define the game it ships. Any machine change, disk loss, or second builder turns "rebuild the game" into archaeology, and the silent BoxMesh fallback means a missing-asset build can look merely ugly instead of failing.

### 7. Data-is-code has no in-repo guard, so silent content deletions are found by auditors, not tooling (OBSERVED in pack, INFERRED for the pipeline point)

The register records a third silent weapon deletion, b_razor_s dropping the base hull's bioplasma without disclosure, found Oct 30 by an audit read. That makes three instances of one defect class: a variant in data.js silently losing a weapon, in a file where data and code are the same artifact. The validators that could catch this class (table cross-reference, naming lint) live in contrib/muse/tools, outside both builds' own test trees; the Godot test trees (rules/test, campaign/test) test rules parity, not data-table integrity against the design rule "every variant carries a real trade and deletions are disclosed". INFERRED: as long as the check lives in contrib tooling that no build step runs, the class will keep recurring and keep being found late, by reading, at audit prices.

### 8. The 40 failing findings-tests are the real release gate, and they live outside the game's test structure (OBSERVED in pack, INFERRED for the gating point)

The register reports findings-to-tests at 8 PASS / 40 FAIL at the pin, with the failures described as correct regression tests against unfixed defects. Taken at face value, that is a ledger of 40 known, reproduced defects, each with a test that will go green when fixed. That ledger, not the parity suite, is the honest cutover checklist for the browser-side defect backlog. But it lives under contrib/muse/tools/findings_tests/, written by the audit program, while the Godot tree's own runners (run_parity.sh, run_sweep.sh) know nothing about it. INFERRED: unless the findings ledger is wired into the cutover criteria by name, cutover can be declared on parity evidence while 40 reproduced defects ride along uncounted.

### 9. The port quietly abandoned the plan's type-safety rationale, and the trade is undocumented (OBSERVED)

The engine port plan synthesis records both legs choosing C# for the rules and campaign state, because it is the "largest and most type-sensitive body of code" and integer combat math must match the Node oracle, with GDScript as a fallback only "if the spike rejects C#". The shipped port is GDScript throughout: rules.gd:1 describes objects staying "Dictionaries with the JS field names", untyped by design, and the warning headers in rules.gd and jsm.gd are the record of managing that choice. The mitigations are real (jsm.gd reproduces JS numeric semantics exactly; the trap warning classes stay on). But no evidence in the pack records the spike rejecting C#, or anyone accepting the residual risk: a 245,969-byte rules body in an untyped language, where a misspelled dictionary key is a runtime null, not a compile error. Cost: INFERRED, this is the port's largest compounding-debt decision, and it was made invisibly. Every future rules change pays the untyped tax, and parity tests, which only exercise scenario paths, are the only net.

### 10. Two persistence lineages now version independently, with the migration discipline on the wrong one (OBSERVED)

The browser envelope is SAVE_VERSION 2 with a documented migrate, repair and sanity pipeline, and 21 fixtures pinning its load behaviour. The Godot campaign writes {"format": "voidsworn-godot-campaign", "v": 1, ...} (campaign.gd:370) and explicitly declines the browser's migration markers: campaign.gd:201 notes the back-fill of old run logs "is not carried". The Godot loader itself is good (keep-the-sound-half fallback to .bak, campaign.gd:397-418). But the fixture discipline, the strongest persistence tooling the project has, is aimed at browser-to-Godot import, which finding 4 shows the code has cancelled, while the format that will actually live or die by migrations, the Godot v1 format, has no fixture set of its own in the evidence. Cost: INFERRED, when Godot v2 is needed, the project will improvise migrations for the only save format its players still have, having spent its fixture effort on a format it decided to abandon.

## Verdict

Verdict: the port's engineering is better than its paperwork, and the paperwork is what the program steers by. The single most important attack: the parity oracles have already diverged (finding 1), so the migration's central guarantee currently rests on two different copies of the game, while the documents meant to track that risk report no divergence and list already-fixed defects as pre-cutover work.
