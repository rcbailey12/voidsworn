Every expected value below is exact (source named), derived (arithmetic shown) or INFERRED (labelled). ## Gaps and conflicts, with exact proposed edits

G1 (Issue 120, Done-when, migration clause; gap). The clause "old saves migrate (an existing RUN.nem becomes the SP-current entry)" does not say how the remaining story point entries of RUN.nemAssign are produced for a migrated run: drawn at load, drawn lazily at each sector, or left unset. Every reading passes the clause as written, and they differ observably (a tool or panel reading the full assignment at load sees different state). Proposed edit: replace "old saves migrate (an existing RUN.nem becomes the SP-current entry)" with "old saves migrate (an existing RUN.nem becomes the SP-current entry, and the remaining story point entries are drawn at load from the run RNG under the same no-consecutive-repeat rule, with the migrated hunter fixed in the current story point's slot)". If the owner prefers lazy fill, see owner question Q2; the checks in 120-7 and 120-8 pin the current entry either way.

G2 (Issue 121, Done-when, attachment clause; gap). "weaknesses, scars, epithets and debrief lessons attach to the commander" names storage for the first three by inheritance from the current commander object, but lessons have no existing home: the current code teaches weaknesses on a loss (nemAfterBattle, campaign_run.js:306) and keeps no lesson record, and issue 122's panel clause ("that commander's scars and lessons") depends on this storage existing. Proposed edit: replace "debrief lessons attach to the commander" with "debrief lessons are recorded on the commander met, as a per-commander list of the lessons taught by lost meetings against that commander, holding the NEM_VOICE lesson text for the weakness taught".

G3 (Issue 122, Done-when, counters clause; gap). "a run-level escape counter and a per-commander compounding counter" does not say which behaviours the compounding counter counts. The synthesis (section 4) names only Chorus growth as commander-specific compounding; riches (Hullbreaker) and honed (Glasswright) already exist as per-commander fields in NEM_CARRY. Proposed edit: replace "a per-commander compounding counter" with "a per-commander compounding counter where the behaviour compounds (the Chorus fed counter, capped at 8); factions without a compounding behaviour carry no such counter, and the existing per-commander riches and honed fields are not re-counted".

G4 (Issue 121, Done-when, clock clause; ambiguity against the code facts). The clause says "one run-level clock paced by the active commander's beh.clock", but the shipped implementation stores the clock on the commander object (campaign_run.js:280; NEM_CARRY at :256), and the clause does not state where the run-level clock lives or who resets it. Without that, two different storages both claim the clause (see Coverage note item 2). Proposed edit: replace "one run-level clock paced by the active commander's beh.clock" with "one run-level clock, stored on the run and not on any commander, paced by the active commander's beh.clock; a meeting resets it to 0 and clears any pending strike, whoever the active commander is". G5 (Issues 121 and 122, wording; ambiguity the pack's own trap flags). Both issues say "the active commander" without pinning the index, while the assignment is indexed by story point and the runtime state is keyed by RUN.sector. The synthesis (section 2) pins it as sector k to RUN.nemAssign[k-1], and check 120-6 tests exactly that, but the issue texts should carry the pin so the build cannot drift from the checks. Proposed edit: in issue 121's Done-when, replace the first occurrence of "the active commander" with "the active commander (the registry entry for RUN.nemAssign[RUN.sector - 1])", and in issue 122's Done-when, replace "the current sector's assigned hunter" with "the current sector's assigned hunter (RUN.nemAssign[RUN.sector - 1])".

No other conflicts found: the three Done-when blocks are consistent with R85 (draw, per-commander adaptations reset at run start, lessons per commander, run 5 finale on the same SP3 draw, one run-level clock), with R101 (NEM_VOICE into data.js in issue 121, fall_final included, lessons pronoun-free, adaptation lines through nemSay), and with R106's sequencing (120, then 121, then 122; the checks are written to be consumed in that order).

## Traps

Pack traps and the checks that catch them:

- RNG stream coupling (the draw consumes run RNG at run start; downstream canonical outputs shift even when behaviour is correct). Caught by design, not by a single check: every scenario check above states its behavioural invariant first (revive once, death in sector 3, feeding cap at 8, fields preserved across migration), and the parity checks (120-10 step 1 and step 5, 121-14, 122-8) forbid re-pinning a golden or a canonical line unless the invariant checks have passed. A build that only matches re-pinned lines while breaking an invariant fails.
- Lazy creation order (identity rolls consume RNG when a commander is first resolved, not at run start). Caught by 120-5, which asserts the registry is empty at run start and grows by exactly one entry per new faction resolved, and by 120-6's foes[3] control block.
- The draw itself (an implementation that excludes both previous hunters at SP3 passes marginals and kills the return rate). Caught by 120-3, which measures Pr(H3 = H1) and the distinct-hunter split directly, and by 120-5's return block, which uses a seed with H3 = H1 taken from the enumeration output: under a without-replacement draw no such seed exists.
- Sector versus story point indexing. Caught by 120-6 (sector k resolves to nemAssign[k-1], exact, three sectors) and pinned in the issue texts by proposed edit G5.
- Old saves (a current-build save has RUN.nem and nothing else). Caught by 120-7 (mid-run save with persona, clock part-full at 2.5, adaptations present) and 120-8 (the pre-persona shape already on file), plus the round trip for new saves in 120-9.
- Parity drift (oracle copies are copies, not links). Caught by the explicit re-copy and file-diff steps in 120-10, 121-14 and 122-8, ordered before the parity run so a stale oracle fails as a diff, not as a mysterious parity mismatch.
- Text (nemSay swaps male pronouns only; Chorus lines carry no gendered pronouns and no song or choir words; Eclipse flee is empty and its code path unreachable). Caught by 121-10, 121-11 and 121-12. The unreachable-path half is covered indirectly: the Eclipse blocks in 121-13 and 122-2 script flagship destructions and flights are never offered as an Eclipse outcome; a build in which the Eclipse commander fled would fail the revive and death invariants in those blocks (his state would show the fled branch's scar and signature instead of the revive state).

Additional traps found by this leg:

- The battle snapshot's derived met (nemBattleCfg at campaign_run.js:291 derives met as beaten + scars > 0, meaning "has ever met") versus the met-this-sector flag (N.met >= RUN.sector at campaign_run.js:290). If the redesign wires the once-per-sector test to the derived snapshot value, a returning commander who was beaten or scarred in sector 1 reads as already-met in sector 3 and the return meeting never happens, silently breaking the SP1-return design. Caught by the negative control in 121-2.
- Registry keyed by faction means a run holds at most one commander per faction: with H3 = H1 the run has exactly 2 commander objects, not 3. Any check, panel code or telemetry that assumes one object per story point will either duplicate the returning commander (losing his scars, which breaks R85's return fiction) or read the wrong object. Caught by 120-5 (identity and scars preserved on the return entry) and 122-5.
- Half-step clock arithmetic (campaign_run.js:280 rounds at half steps and clamps): paces of 0.5 and 1.5 produce half-integer clock values, so a check or a port that assumes integer clock values false-fails on Eclipse and Crusade, and a port that rounds differently drifts from the JS canonical lines. Caught by 121-3's exact half-step sequences, which the Godot twin must reproduce line by line under 121-14.
- The signature list cap (40, oldest dropped, campaign_run.js:273) means telemetry history is lossy per commander: a check that counts signatures over a long run and expects the full history will false-fail. Caught by the cap block in 122-1, which pins the lossy behaviour as the expected result.

## Owner questions (three, with chair picks)

Q1. Should the full enumeration in 120-1 (120,000 run starts) gate the PR for issue 120, or run once as a recorded verification with only the exact-constraint checks (120-2, which hold at any run count) plus a reduced statistical subset in the PR gate? Chair pick: run the full enumeration once as a recorded verification for issue 120, and gate the PR on 120-2 plus the scenario suite. Reason: a statistical tolerance inside a merge gate invites flaky blocks, while the structural constraints (no own faction, no consecutive repeats) are exact at any sample size. Cost of the other option (full enumeration in the gate): the enumeration driver pays 120,000 title-flow run starts on every push (per-run minutes on every PR iteration, INFERRED as the dominant runtime of the check suite), plus a standing flake risk from the INFERRED tolerances in 120-1 and 120-3.

Q2. For a migrated legacy save, should the non-current story point entries be drawn at load (proposed edit G1) or left undrawn until each sector begins? Chair pick: draw at load. Reason: it keeps one invariant ("RUN.nemAssign is complete from the moment a run exists, new or migrated") that 120-4 style checks and any panel or telemetry reader can rely on, instead of a second fill path with its own timing. Cost of the other option: one extra fill path in the build, extra scenario blocks at each sector boundary of a migrated run (a one-time test build on top of 120-7 and 120-8), and every reader of the assignment must tolerate holes until the last sector starts.

Q3. Should the per-commander compounding counter be scoped to the Chorus fed counter only (proposed edit G3), or should riches and honed also be re-expressed as compounding counters for uniformity? Chair pick: Chorus fed only, per synthesis section 4, which names Chorus growth as the commander-specific compounding behaviour; riches and honed already persist per commander through NEM_CARRY and are shown by the panel. Cost of the other option: a wider telemetry schema and extra counter cases in 122-3 and 122-9 (a one-time test build plus longer scenario runs per iteration), spent on re-counting state that already exists, with no ruling behind the wider scope.
