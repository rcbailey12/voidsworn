## Verdict: GO WITH CONDITIONS

The rollout's substance holds: the moved readers return what the screens read before, the capture mode is properly fenced off from a normal game, and the 16 layout changes match the rules they cite on the evidence available. Two claims in the PR are stronger than the code, and both should be reconciled before groups 2 to 4 build on them.

## The Board's four questions

1. **Does campaign_view.gd only read, and return what the screens showed before?** In its own text, yes: nine static functions, no writes, no actions, and the moved readers (header, purse, admiral, fleet rows, hold, aspect, fight cards) return the fields the screens computed inline before, verified function by function against the diff by three legs. One path breaks the file's own guarantee. fight_cards computes each card's nemesis flag with C.nemNodeIs(n), for every card kind; nemNodeIs (campaign.gd:2049) calls nemActive() first, and nemActive (campaign.gd:1945) is not a read: it runs nemMigrate() and, when the assignment slot names a faction with no record, creates one (reg[fac] = newNemesis(fac)) and writes RUN["nem"]. So a render call can migrate or create the run's Nemesis record. In the ordinary flow the map has resolved the Nemesis before these cards draw, so the practical effect is normally nil, and the write is the campaign's own lazy resolution rather than new behaviour; but the file header promises "Nothing here writes to the campaign, draws a random number or keeps state, so calling a view never changes a run, a save or parity", and the PR body repeats "It only reads (a ui check enforces no writes and no actions)". Both statements are false on this path, and the shape is the one the #343 ledger just recorded as lost (nemActive's lazy creation letting render paths mutate run state). Whether newNemesis draws a random number could not be verified from the pack; the RNG question is the same one left open there.
2. **Can the capture mode run in a normal game?** No. The rollout mode in campaign_scene.gd is reached only when OS.get_cmdline_user_args() starts with "rollout", the same gate as the pre-existing shots, mapshots and bot modes; a normal launch supplies no user args and falls through to the title path. The mode uses its own save path (user://ui344_rollout_save.json), and the chair verified the remaining gap the legs flagged: persist_on defaults to false (campaign.gd:59) and is set true only on the normal path, so a rollout run cannot write any save. Inside, the run is honestly played (seed 344, the campaign's own actions, no hand-typed page state), and reached.txt discloses the two pages not reached.
3. **Do the 27 tests test behaviour or strings?** Strings and structure, by the file's own header ("These are code-structure checks, not numeric gates"). The new checks are regular expressions over source text: palette provenance, the fin( occurrence count as a proxy for "every dialog finishes on the one slab", the view offering the named functions, the side panel calling the view. A few older checks in the same file parse numbers and one scan asserts its own row count so a broken scan fails loudly; those have structural teeth. None of the 27 executes the view against a fixture run. That division of labour is fine, with one exception: the check described as enforcing the view's read-only property (ui_spec_tests.js line 91) greps campaign_view.gd's own text for assignment patterns and C.act, so it passes while the question 1 path writes one call away. As written it enforces the file's spelling, not the property it names.
4. **Do the 16 layout changes match the cited rules?** On the evidence in the pack, yes for fifteen, with the rule texts themselves taken from the PR's citations (the spec documents were not in the pack; three legs verified the code against the descriptions and found no contradiction): the side panel order per ui_style 7, the finish slab per R148, danger words and the Easy band's move to FRIEND mint per ui_spec 5.1 and 5.2, the hover card's faction colour per 5.4, the text floor, the orphan colours, the restored glyph chips. The exception is claim 4, "every line over the 3D map sits on a backing". The chair verified DeepSeek's counterexamples in map3d.gd at the head: the stop name rides a strip and the tags ride chips, but the secondary label lines under a stop (the board shape and modifier line, map3d.gd:717, and the reward label line, :727) are drawn with plain _text and no backing, as is the "IN FLIGHT" line (:736). These are detail lines shown on hover, focus or zoom, over the dark map; ui_style's locked rule is that every line of text sits on a solid backing, so the claim overstates what shipped.

## Conditions

1. **Reconcile the view's purity claim with the nemNodeIs path before merge.** Any of: pass the nemesis flag into fight_cards from a caller that already resolved it; split nemActive's query from its ensure-and-create half and let the view call only the query; or name the exception in campaign_view.gd's header and in the test, with the Board ruling the lazy resolution acceptable on render paths. What cannot stand is the current trio: the header's promise, the PR's "a ui check enforces" sentence, and a check that cannot see the write. Groups 2 to 4 will copy this pattern, so the guarantee has to mean something before it spreads. (All four legs found the path; Qwen's condition 1, Grok's finding 1, the blind leg's headline.)
2. **Reconcile layout claim 4 with map3d.gd's unbacked detail lines.** Back the shape-and-modifier line, the reward label line and the IN FLIGHT line the way the name and tags already are (a chip or tag treatment fits the existing vocabulary), or narrow the claim in the PR and ui_style to the lines it covers. The chair's read: backing them is the spec-compliant route and the cheaper sentence to keep true for group 2. (DeepSeek, chair-verified at map3d.gd:717, :727, :736.)

## NOTEs

- **The fight card dedupe key changed, undisclosed.** The old preview loop keyed on enc, reward, type, arch, mod; the view keys on type, name, reward, arch, mod and fac (chair verified in the diff). Two otherwise identical fights against different factions showed as one card before and show as two now. Arguably more correct, since each card names its faction, but it is a behaviour change inside a "moved reader" and the Board should rule it intended rather than discover it later. The sector flagship card is the disclosed addition and is fine.
- **The ui_style.md section 5 rows for the new constants (BLUE, DANGER, STOP, ROUTE, SHADE) should land with or before this merge.** The PR leaves them to the Board and LOOP records the same plan; at this head the code leads the spec by one step, and the spec is the record the next group will read.
- **The 27 tests should be cited as structure checks** wherever the rollout is summarised, not as behaviour coverage; the parity evidence for this group is the campaign parity suite and the captures, as the PR's own checks section shows.

## Dissent

DeepSeek returned NO-GO, on the ground that the question 1 path violates finding 12's central requirement and the test gives false assurance. The chair does not adopt the NO-GO: the write is the campaign's pre-existing lazy Nemesis resolution, idempotent, on a path the map already travels before these cards render, so no run changes behaviour because of this PR; what the PR adds is a false sentence about it, which condition 1 corrects. The dissent is recorded because its premise (the claim and the check both overstate) is the chair's own condition.
