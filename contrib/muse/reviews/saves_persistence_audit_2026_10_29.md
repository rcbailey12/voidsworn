# Save and persistence audit (chair code audit, Oct 29, 2026)

Scope: the browser build in ~/workspace/voidsworn-fresh (core.js, campaign_run.js, campaign_meta.js, campaign3d.js, main3d.js, ui3d.js), read as the oracle for the Godot port, plus the Godot save code it would cut over to (godot/campaign/campaign.gd, godot/main/main.gd, godot/scenes/battle/battle.gd, godot/story/career.gd). Code reads only; nothing was run. Claims are marked OBSERVED (read in code) or INFERRED (follows from two or more read facts). Faction ids are data ids; display names follow the rename map (voidsworn is the Sunward Crusade, ithar is The Glasswrights, deathless is Eclipse, corsair is Ashfall Hullbreakers).

## What is saved, where, in what format

OBSERVED. One envelope holds almost everything. Persist.saveLocal() writes JSON.stringify({meta:META, run:SAVED_RUN}) to localStorage key voidsworn.v1 (core.js:48, core.js:118-120). The previous parseable value is first copied to voidsworn.v1.bak, one save behind (core.js:119). A second key, voidsworn.tel.v1, holds a duplicate of the telemetry log so events from a frozen battle survive a reload (campaign3d.js:15-19). A third key, voidsworn.v1.repaired, receives a raw copy of any save that needed repairs or failed to load, written once and never overwritten (core.js:117; also campaign_meta.js:49). The generated-texture cache in IndexedDB (scene3d.js:139-140) is art caching, not save data.

OBSERVED. META is the profile object: renown, unlocked (Legacy doctrines), admirals (unlocked admirals), fallen captains, stats (runs, best, wins, wonFacs), opts (settings), tel (last 600 events, campaign3d.js:16), updated and runAt stamps, mastery, favour (core sync), variants, heatBest (core.js:50). There is no separate settings store: settings live in META.opts and are written by saveOpts() (ui3d.js:543). RUN is the in-progress campaign: faction, foes, admiral, credits, cpCap, sector, relics, inventory (refits in the hold), fleet (each ship: uid, tpl, name, mk, hp, mods, cap with xp, rank, perks, pending), pos, the whole sector map (RUN.map from genSector, core.js:251-296, assigned at core.js:338), stats, fallen, boons, patrons, aspect, flagUid, heat, the Nemesis object, the pending reward object, and about a dozen more fields enumerated in runDefaults() (core.js:66-67, core.js:322-341).

OBSERVED. The write path is saveRun(): SAVED_RUN becomes a deep JSON clone of RUN (or null when RUN.over) and Persist.save() stamps META.updated (and META.runAt unless the write is meta-only), writes local storage, and pushes to the cloud mirror (core.js:343, core.js:155). The cloud mirror is the same {meta, run} JSON at data/users/<uid>/save, reconciled on connect by separate updated and runAt stamps so meta and run resolve independently (core.js:122-152). The load path is Persist.loadLocal() at boot (main3d.js:11): parse voidsworn.v1, sanity-check it, fall back to .bak, keep whichever half (meta or run) is sound, then migrate (core.js:112-117). Continue clones SAVED_RUN into RUN and resumes any pending reward (campaign_meta.js:42-43).

## Findings

1. [NOTE] OBSERVED. The local save is a single JSON envelope with a one-step backup and a raw repaired copy, so the common failure modes (corrupt write, malformed half) degrade instead of bricking: saneSave, saneMeta and saneRun gate trust (core.js:102-104), a bad main value falls back to .bak (core.js:113), and if neither is sound the sound half is kept and the other nulled (core.js:114). A run the game still cannot open gets a player-facing escape that keeps progression (campaign_meta.js:43-49).

2. [FIX] OBSERVED, with INFERRED consequence. Settings writes bypass the stamping and cloud path. saveOpts() merges into META.opts and calls Persist.saveLocal() only (ui3d.js:543), while Persist.save() is the only writer that stamps META.updated or runAt and pushes to the cloud (core.js:155). INFERRED: a session that only changes settings (quality, sound, camera, AI level) never syncs those settings to the cloud mirror, and a second device resolving by stamps cannot see them until some unrelated saveRun or purchase happens to call Persist.save().

3. [NOTE] OBSERVED. Versioning is shallow by design. SAVE_VERSION is 2 (core.js:49). migrateMeta and migrateRun handle only the v1 to v2 step (adding tel and opts to meta; stats and fallen to a run) plus generic default filling for any missing field, including a one-time telemetry backfill of mastery, favour and up to 60 renown, and a wonFacs recovery pass (core.js:52-64). normalizeRun fills every missing RUN field from runDefaults() (core.js:68-72). There is no chain of per-version transforms, so a future field rename has nowhere to hook except these two functions.

4. [NOTE] OBSERVED. Renamed or removed ids are dropped silently at load, with safe fallbacks, by repairRunIds (the keep mechanism, core.js:76-100). keep() filters relics, inventory, heat, boons (by b.id), patrons, fleet ships (by s.tpl), each ship's mods, each captain's perks, and the pending reward's prizes and offers against today's tables (core.js:77, core.js:81-88, core.js:92-98). Fallbacks instead of drops: an unknown faction resets to voidsworn (core.js:78), an unknown admiral is replaced by the first admiral of the same faction, or vex (core.js:79), an unknown aspect or giftBoon is nulled (core.js:83-84), an invalid ship hp becomes 1 (core.js:88), NaN credits become 0 (core.js:91), a flagship uid pointing at a dropped ship is nulled (core.js:90), and an invalid reward stage is forced to promo (core.js:94). Each unknown id is logged once per session through unknownId (a Set plus console.warn plus an unknown_id telemetry event, core.js:106).

5. [FIX] OBSERVED, with INFERRED consequence. The drop in finding 4 is silent in the data and only partly surfaced to the player. Repairs accumulate in r._repairs (last 20) and r._shipsDropped (core.js:99-100); on Continue the player gets one toast summarising counts and is told a copy of the old save is kept, and the _repairs fields are then deleted and the repaired run re-saved (campaign_meta.js:46-48). INFERRED: a renamed hull id therefore deletes that ship, its captain, its perks and its fitted refits from the run with no per-ship record anywhere except the raw .repaired JSON, which no UI reads back. Id stability is load-bearing for this save format; display renames are safe (names live in data tables, not in the save), id renames are not.

6. [FIX] OBSERVED, with INFERRED consequence. The unlockAll boot grant persists by side effect and cannot be cleanly revoked. At boot, if META.opts.unlockAll is anything other than false (including never set), main3d.js sets every LEGACY key in META.unlocked and every admiral in META.admirals (main3d.js:11). That line does not itself save, but the mutated META is what every later saveRun and Persist.save serialises (core.js:118, core.js:155), so INFERRED the grant becomes a permanent part of the stored profile on the first save of the session. The only toggle handler flips META.opts.unlockAll and grants when turning on, but never removes already-granted unlocks when turning off (campaign3d.js:119), and the settings panel HTML has no unlock row at all (campaign3d.js:115-118), so in the shipped UI the grant is effectively always on and irreversible without editing storage. This matches the known state (the grant is a leftover from testing, confirmed Oct 28), and it means any save written by the current browser build carries a fully unlocked META into whatever reads it next.

7. [NOTE] OBSERVED. Mid-battle state is never saved; battle integrity is replay based, not resume based. saveRun clones RUN only (core.js:343); the battle object B is not serialised anywhere, and the pagehide handler for a battle left mid-fight only logs a battle_abandon telemetry event and calls Persist.saveLocal() (main3d.js:19-20). What makes that safe is the per-node seed: each fight node gets a seed stored inside RUN.map, battleScreen seeds its pre-battle rolls from it, and the same saved run rebuilds the same battle from the start (campaign_run.js:34; campaign3d.js:44-47). Hull damage from an unfinished battle is not applied, because ship hp is written back only in finishBattle (campaign3d.js:84).

8. [FIX] OBSERVED, with INFERRED consequence. Mid-reward resume is the strongest part of the layer, with one silent-skip edge. rewardFlow banks the node first (completeNode inside the same call) and stores the whole pending chain in RUN.reward: kind, node, rw, relic choices, wrecks with yields, prizes, stage (prize, salvage or pick), and null offer slots (campaign_run.js:414-417). Offers are then fixed into the save as they are rolled (modOffer at campaign_run.js:483, boonOffer at campaign_run.js:488), prize picks persist in RUN.reward.prizeSel (campaign_run.js:462-463), and the boon reroll flag rides in RUN.reward.rerolled (campaign_run.js:498-500). resumeReward rebuilds the window state from RUN.reward and dispatches on stage, including relic and promo (campaign_run.js:525-530), and Continue calls it whenever RUN.reward exists (campaign_meta.js:42-43). Repair also validates the reward object (core.js:92-98). The edge: repair forces an unrecognised stage to promo (core.js:94), and resume falls through to promotionsStep when the stage's payload was filtered empty (for example stage prize with all prize hulls dropped, campaign_run.js:528-530), so INFERRED a damaged or id-shifted reward can silently skip unclaimed prize, salvage or pick stages; the node is already banked, so the lost rewards are not recoverable.

9. [BLOCKER] OBSERVED. The Godot cutover drops browser saves entirely, by decision recorded in the Godot code: the campaign save is a fresh format and browser saves are not carried over (godot/campaign/campaign.gd:354). The Godot campaign writes its own JSON (format voidsworn-godot-campaign, v 1, with meta, run and tel in one object) to user://voidsworn_campaign.json (godot/campaign/campaign.gd:60, godot/campaign/campaign.gd:369-370), its loader reads only that path and its .bak (godot/campaign/campaign.gd:415-418), and no GDScript in the tree references the browser key voidsworn.v1 (grep over godot/**/*.gd, Oct 29). The browser build offers no export path either: the Copy report feature emits a diagnostic snapshot (build, opts, a run summary, last 200 events), not an importable save (campaign3d.js:22-26). What is lost at cutover unless an importer is built: all of META (renown balance, Legacy unlocks, admiral unlocks and mastery, core sync favour, hull variants, Heat bests, fallen captains, stats) and any in-progress RUN including its map, fleet, captains and pending reward.

10. [NOTE] OBSERVED, with INFERRED consequence. An importer is nevertheless cheap, because the Godot port mirrors the browser layer field for field. Godot campaign.gd has its own defaultMeta, migrateMeta, migrateRun, saneMeta, saneRun and saneSave with the same field names and the same repair approach (godot/campaign/campaign.gd:198-216, godot/campaign/campaign.gd:340-351), and its run and meta dictionaries carry the same keys as the browser objects, so a converter only has to read the voidsworn.v1 JSON ({meta, run}), pass it through the Godot migrate and repair functions, and write it in the Godot envelope. Two Godot-only stores have no browser source and need no migration: shell settings in user://settings.json (godot/main/main.gd:15, godot/main/main.gd:155-171) and battle options in user://battle_opts.json (godot/scenes/battle/battle.gd:3076-3090), plus the Godot-only career profile in user://voidsworn_career.json (godot/story/career.gd:3-13). One caution for any importer: because of finding 6, an imported browser META will usually arrive fully unlocked; the importer is the last clean place to decide whether that stands.

## Not checked

- The Godot battle scene's own mid-battle persistence (battle.gd writes only options; whether the Godot campaign host saves anything on battle exit was not read).
- Cloud conflict behaviour beyond the stamp comparison in Persist.connect (no live sync was exercised; code reads only).
- Whether any contrib or test harness writes saves in other formats (contrib tooling was out of scope).
- Save size growth: META.tel is capped at 600 events (campaign3d.js:16), but RUN.map, fleet and fallen growth across a long run were not measured.
- The .repaired copy is write-once (core.js:117); whether a second, different repair event later in the profile's life is therefore left without a raw copy was noted but not traced through every write path.
