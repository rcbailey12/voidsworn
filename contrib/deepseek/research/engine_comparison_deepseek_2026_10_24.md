# Engine comparison for Voidsworn: graphical future research brief (DeepSeek independent leg)

This brief compares four engine paths for Voidsworn, a 3D turn-based fleet-tactics roguelite with about 20 detailed ships at battle zoom, bursty shield, beam, torpedo, boarding, destruction, and reanimation effects, a kit-based ship art pipeline, and a strict colour law. All findings are leads from live web search. Every claim is marked OBSERVED (with a source URL) or PROPOSED (my inference). Nothing here is a verdict; the coder decides from code and measurement.

## 1. Staying on Babylon.js

### Performance headroom for this exact shape

The Babylon.js community position is that Babylon is not a natural choice for "fast-paced first person shooters with AAA graphics," but it is "feature rich and extremely capable" for many 3D projects, and the main constraints compared with a native engine like Godot are "interpreted JavaScript and single-threaded" execution. OBSERVED: https://forum.babylonjs.com/t/performance-compared-to-godot-and-other-engines/59731 (lines 20-27, 47-48).

For a 20-ship scene, the likely bottlenecks are not draw-call count in the range that would trouble a desktop GPU. Babylon's own documentation and community optimisation material treat 1,500 draw calls as a desktop threshold, with CPU draw submission becoming the concern above that. OBSERVED: https://www.babylonjs.com (engine overview) and https://doc.babylonjs.com (Optimizing Your Scene tutorial), surfaced in search at cursor 0. PROPOSED: 20 ships plus effects should sit well below that ceiling unless the kit system produces many unique material permutations per ship. The more credible risks are JavaScript-side per-frame work (animation, transform updates, effect parameter feeding), shader-program count and state changes when each ship carries multiple kit materials, and GPU fill rate from overlapping transparent shield bubbles and beam quads. Babylon's WebGPU snapshot rendering and thin instances reduce CPU overhead only when draws repeat unchanged frame after frame; they do not help with scenes whose draw list changes through culling or depth sorting, or with GPU-bound frames. OBSERVED: https://webcodingcenter.com/webgpu/indirect-drawing-and-render-bundles--when-render-bundles-help-and-when-they-do-not.html (lines 10-16).

No source states a frame time for 20 detailed ships in Babylon. Any specific millisecond figure for Voidsworn's exact shape would be invented and is not presented.

### Effects and shader capability

Fresnel rim shields, beams, and particle systems are first-class in Babylon. The engine ships CPU and GPU particle systems, solid particle systems, particle flow maps, particle attractors, WGSL core shaders, node material, and a Fresnel term for diffuse, opacity, emissive and reflection. OBSERVED: https://www.babylonjs.com (engine specifications, surfaced at cursor 5, lines 5-13). The FresnelBlock returns the facing term pow(bias + |dot(v, n)|, power), so its complement is 0 facing the camera and 1 at grazing angles, which is exactly the rim behaviour a shield bubble needs. OBSERVED: https://webcodingcenter.com (Fresnel Rim Light, Node Material Editor), surfaced at cursor 5, lines 14-19.

Progressive damage states are a material and mesh-swap problem, not a shader-capability problem. PROPOSED: Babylon's custom material and custom shader support makes multi-pass or mask-driven damage straightforward, but the kit system will need a disciplined material budget: each unique baked finish map combination can create a shader program variant, and shader-program competition for the frame budget is a documented concern. OBSERVED: search result at cursor 0, lines 21-26 (Chinese Babylon.js article on moving compute to GPU and shader-program bottlenecks).

### Asset pipeline fit

Babylon loads glTF, OBJ, STL, and its native .babylon format, with an asset manager. OBSERVED: https://doc.babylonjs.com (Importing Assets), surfaced at cursor 25, lines 27-31. A kit system built as glTF assemblies with baked maps is compatible. PROPOSED: The kit workflow is likely to be more manual than in a dedicated editor: assembling mixed-shape plating and swapping damage states will be driven by code or a custom tool rather than a scene editor's prefab system. Babylon's template repositories and NPM-based workflow support a code-first pipeline, but they do not provide a Godot-style visual kit assembly editor. OBSERVED: https://doc.babylonjs.com (Babylon.js Template Repositories), cursor 25, lines 11-16.

Portrait art is a 2D UI concern and is not engine-constrained in any of the options.

### Migration cost from the current Babylon codebase

Zero engine migration. PROPOSED: The real cost is the cost of not switching, which is the continued cost of building editor and kit-assembly tooling in a code-first web engine and accepting JavaScript single-threaded overhead. If the current game logic is already separated from Babylon render calls, a later switch remains possible; if it is entangled with Babylon scene graph and material objects, the effective migration cost to any other engine rises substantially. No source gives a migration percentage for Babylon-to-X, and none is asserted.

### Solo or small-team fit

Babylon is strong for a solo coder who is already fluent in TypeScript and wants code-first iteration. The community explicitly notes that Babylon is awesome when you want to "leverage your existing web stack skills." OBSERVED: https://forum.babylonjs.com/t/performance-compared-to-godot-and-other-engines/59731 (lines 30-32). The Inspector has a performance tab and scene statistics, but iteration on kit assembly and damage-state authoring is likely to be slower than in an editor with prefabs. PROPOSED: For a solo developer already productive in Babylon, staying is the lowest-friction path unless measurement shows a specific bottleneck that cannot be engineered around.

### PC distribution

Babylon can be shipped to PC through Electron, Tauri, or Babylon Native. Electron packaging for web games typically downloads a 120 to 160 MB runtime per OS. OBSERVED: https://www.npmjs.com/package/gameshipper (cursor 21, lines 4-7). Deskifier notes that a 3D web game headed for Steam "usually ends up in hand-rolled Electron, with a native Steamworks binding, a build per OS, Mac signing and upload scripts to maintain." OBSERVED: https://www.deskifier.com (Babylon.js Games on Steam and Desktop), cursor 21, lines 14-18. PROPOSED: PC distribution is solved but carries ongoing packaging maintenance that a native engine export path avoids.

## 2. Moving to Godot 4

### Performance headroom for this exact shape

Godot's documented 3D optimisation guidance is that each MeshInstance3D node is submitted to the GPU and drawn individually, and that MultiMesh is much faster because it draws thousands of instances with a single draw call. OBSERVED: https://docs.godotengine.org (Optimisation GPU, MultiMesh), surfaced at cursor 1, lines 11-15 and 21-24. The community optimisation material gives a concrete CPU cost: "10,000 trees x 0.02 ms per draw call = 200 ms CPU overhead," exceeding a 16.67 ms budget by 12 times, and instancing reduces 10,000 draw calls to 1, saving 199 ms. OBSERVED: https://github.com/raduacg/game-mechanics-optimizations/blob/main/19_geometry_instancing.md (lines 14-18).

For 20 detailed ships, draw-call submission is not the bottleneck at that count. PROPOSED: The relevant Godot risks are per-ship material and shader complexity, transparency sorting for overlapping shields, and the cost of many small mesh instances if the kit system is naively assembled as separate MeshInstance3D children. MultiMesh is the obvious mitigation for repeated kit pieces, but it requires identical geometry and allows only per-instance transforms, colours, and custom data; mixed-shape plating may resist full instancing. OBSERVED: https://github.com/raduacg/game-mechanics-optimizations/blob/main/19_geometry_instancing.md (lines 19-25).

No source states a frame time for 20 detailed ships in Godot 4. A community post on a different 3D game reports "smooth 60 FPS gameplay at native 1080p on an RTX 3060" after a custom occlusion system, which is context, not a direct measurement for Voidsworn. OBSERVED: https://daily.dev (Custom Occlusion System For Supernatural Indie Game), cursor 17, lines 17-22.

### Effects and shader capability

Godot 4 has a rich public shader ecosystem for exactly these effects. Fresnel shield, beam, bubble, and magic shaders are available as drop-in spatial shaders with a fresnel function and noise-driven rim. OBSERVED: https://godotshaders.com/shader/glowing-shield-beam-buble-dark-magic-fresnel/ (lines 3-22). A shield with multiple impacts is implemented by passing a uniform array of Vector4s (impact xyz and age w) and decaying the age outside the shader, with a loop over up to 16 tracked impacts. OBSERVED: https://godotshaders.com/shader/shield-with-multiple-impacts/ (lines 5-16). A Vav Labs tutorial covers a reactive energy shield with local-space impacts, multiple hits, sustained beams, particles, and positional audio, noting that beams, particles, and sound must agree on the same collision point. OBSERVED: https://vav-labs.com (cursor 3, lines 21-26).

Progressive damage states are a material or mesh-swap concern. PROPOSED: Godot's StandardMaterial3D and shader parameters make mask-driven damage easy, and the editor's material preview speeds authoring. The harder part is the same as in any engine: keeping the kit's baked finish maps consistent across damage states without exploding the material count.

### Asset pipeline fit

Godot imports GLB natively (drag the file into the FileSystem dock), and GridMap is a built-in node for assembling levels from modular blocks on a 3D grid. OBSERVED: https://bitsoulhosting.com (Modular Prop Kit Design in Blender), cursor 26, lines 26-30; https://cadmus.page (GridMap, modular levels), cursor 26, lines 9-13. Texture atlasing for modular kit pieces is handled through MultiMeshInstance3D and shared StandardMaterial3D resources, and lightmap baking automatically picks up channel 2. OBSERVED: https://bitsoulhosting.com (Texture Atlasing for Game Assets), cursor 26, lines 4-8; https://superhivemarket.com (Godot Pipeline), cursor 26, lines 20-24.

PROPOSED: Godot's editor is a genuine advantage for a kit system. Assembling mixed-shape plating as scenes, saving damage-state variants as inherited scenes, and previewing material swaps visually is faster than code-first assembly. Baked maps and portrait art are ordinary import workflows.

### Migration cost from the current Babylon codebase

No source gives a percentage. PROPOSED reasoned range: Pure game logic (turn resolution, hex grid coordinates, fleet state, roguelite progression, damage tables, AI scoring) is language- and engine-agnostic and should port with translation effort only. Engine-locked code (Babylon scene construction, mesh and material creation, particle system calls, camera and picking, shader wiring, asset loading through Babylon's loader) must be rewritten against Godot nodes and resources. The migration cost is therefore not a single number but a function of how cleanly the current code separates simulation from presentation. If the current codebase already has a headless or near-headless simulation layer, the cost leans toward the lower end of "substantial but tractable for a solo developer"; if Babylon objects are the data model, the cost leans toward "a partial rewrite of the rendering and scene layer." This is a reasoned range, not an observed percentage.

### Solo or small-team fit

Godot is repeatedly characterised as the pragmatic choice for solo and small-team indies. One 2026 comparison states: "Godot is still the better engine for most indie developers because it helps you start, test, and ship without arguing with your tools," and "Choose Godot if you need to make the game real this month." OBSERVED: https://engineranked.com/article/bevy-vs-godot-systems-heavy-2d-2026 (lines 11-13, 24-25). A separate review notes that Godot has a real editor and ships faster for most indie projects. OBSERVED: https://www.strayspark.studio/blog/bevy-rust-game-engine-2026-indie-guide (lines 6-9). The editor, GDScript iteration, scene system, and built-in UI and animation tooling are consistently cited as the reasons. PROPOSED: For a solo developer who is not already a Rust expert, Godot has the lowest expected time-to-productive-iteration of the non-Babylon options.

### PC distribution

Godot exports native Windows, Linux, and macOS executables. The exporter creates a data.pck alongside the executable, and Steam distribution is supported through the standard export presets and GodotSteam. OBSERVED: https://docs.godotengine.org (Exporting for PC), cursor 20, lines 4-10; https://flockbay.com (Port a Godot Game to Steam), cursor 20, lines 43-46. PROPOSED: This is a cleaner PC distribution story than Electron packaging, with no per-OS web runtime to maintain.

## 3. Moving to Rust with Bevy

### Performance headroom for this exact shape

Bevy's performance case rests on native Rust compilation, ECS parallel system execution, SIMD-optimised vector operations, and memory layout optimisation. OBSERVED: https://deepwiki.com/bytemeadow/godot-bevy/6.2-performance-comparisons (lines 35-40). In a boids benchmark comparing Godot GDScript and Bevy Rust, Bevy maintains 144+ FPS consistently up to 10,000 entities and shows only gradual degradation at 20,000+, while Godot GDScript falls to 6.2 FPS at 10,000. OBSERVED: https://deepwiki.com/bytemeadow/godot-bevy/6.2-performance-comparisons (lines 20-24, 40-42). That benchmark is for a simulation-heavy boids workload, not 20 detailed ships with bursty effects, and it compares GDScript with Rust, not Godot's C# or C++ paths. PROPOSED: The benchmark is evidence that Bevy has high headroom for simulation logic, not evidence that Voidsworn's rendering and effects workload would be faster in Bevy than in Godot. For 20 ships, neither engine is likely to be entity-count-bound; the bottleneck will be per-ship material and effect complexity and the cost of the renderer's handling of transparency and shader permutations.

Bevy's renderer is wgpu-based and targets Vulkan, Metal, D3D12, OpenGL, and WebGPU. OBSERVED: https://www.strayspark.studio/blog/bevy-rust-game-engine-2026-indie-guide (lines 30-31). Deferred rendering and HDR are present in the 0.17/0.18 line. OBSERVED: same source, lines 45-46.

### Effects and shader capability

Bevy supports custom shaders and wgpu pipelines. PROPOSED: Fresnel rim shields, beams, and particle systems are all implementable, but the ecosystem does not offer the same density of drop-in Godot-style shader examples for these exact effects. The coder would be writing more shader and render-graph code directly. Progressive damage states are again a material and mesh-swap concern, and Bevy's asset pipeline supports glTF with KTX2 textures and offline asset processing for baked, runtime-ready forms. OBSERVED: https://factory.com (bevy_asset), cursor 27, lines 24-27; https://github.com/DGriffin91/bevy_bistro_scene (KTX2 texture conversion), cursor 27, lines 18-23.

No source surfaces a Bevy-specific Fresnel shield or multi-impact shield implementation comparable to the Godot shader library. That is an absence of evidence, not evidence of impossibility; it is a signal that the coder would be building more effect infrastructure.

### Asset pipeline fit

Bevy's asset pipeline 2.0 stabilised the asset system rewrite, with async loading, dependency tracking, hot reloading, content hashing, and first-class KTX2 support. OBSERVED: https://www.strayspark.studio/blog/bevy-rust-game-engine-2026-indie-guide (lines 42-45). glTF loading is supported, and community tools exist for baking glTF assets with compressed textures. OBSERVED: https://brainxx.site (Bevy and glTF: Efficient Asset Loading), cursor 27, lines 31-36.

PROPOSED: The kit system is the weak point. Bevy has no mature visual editor for assembling kit pieces. The official Bevy Book states plainly: "Bevy does not currently have a graphical editor," and "You need to make a lot of game content" is listed as a reason not to use Bevy. OBSERVED: https://bevy.org/learn/book/is-bevy-right-for-your-project/ (lines 18-31). A 2026 community comment puts the tooling cost in concrete terms: "you will probably spend hundreds of hundreds of hours building tooling," and "the toughest thing is having to spend 10+ hours massaging asset packs to proper formats and into my custom pipeline." OBSERVED: https://safe.search.brave.com/goggles?q=best%20games%20to%20win%20real%20money (r/rust_gamedev discussion), cursor 33, lines 10-19. For a kit-based ship art pipeline that needs mixed-shape plating and baked finish maps swapped visually, this is a direct workflow cost.

### Migration cost from the current Babylon codebase

No source gives a percentage. PROPOSED reasoned range: The simulation layer (turn logic, hex grid, fleet state, damage and status rules) is portable in concept but must be rewritten in Rust, which is a larger language and ownership-model shift than translating JavaScript to GDScript or C#. The rendering and scene layer is a full rewrite against Bevy's ECS, render pipeline, and asset system. The migration cost is therefore higher than Godot for the same codebase, and the risk is not only translation volume but the absence of an editor for kit assembly, which shifts content-authoring work into custom tooling. This is a reasoned range, not an observed number.

### Solo or small-team fit

Bevy's own project book is candid: "You should not use Bevy if you need a stable, mature tool," and "Bevy iterates quickly, and ships breaking changes approximately once every four months." OBSERVED: https://bevy.org/learn/book/is-bevy-right-for-your-project/ (lines 18-23). A 2026 review notes that Bevy "breaks almost every convention that Unity and Godot established" and "has no visual editor." OBSERVED: https://engineranked.com (Bevy Engine 0.15 Review), cursor 6, lines 31-35. Another comparison puts it directly: "In Bevy, even minor presentation work can push you back into code and custom tooling." OBSERVED: https://engineranked.com/article/bevy-vs-godot-systems-heavy-2d-2026 (lines 13-15).

The countervailing community evidence is that Bevy is enjoyable for developers who want a code-first ECS and are prepared to build tooling. A Reddit commenter says: "For people like me, who would otherwise be building their own game engine from scratch, Bevy is very fun." OBSERVED: https://www.reddit.com/r/rust/comments/1niyavg/community_reflection_on_bevys_fifth_year/ (lines 22-25). But another commenter notes: "compile times are just terrible, my laptop is in constant boiling mode, and the rigidity of Rust makes prototyping painful and refactorings long." OBSERVED: https://p.jlai.lu (Bevy Game Engine Explained Visually), cursor 18, lines 46-49.

PROPOSED: For a solo developer whose priority is ship kit iteration, damage-state authoring, and effect tuning, Bevy imposes a tooling tax that Godot does not. It becomes defensible only if the coder is already fluent in Rust and values ECS architecture over editor speed, or if measurement shows a simulation bottleneck that Godot cannot handle at the 20-ship scale. The boids benchmark does not establish that Voidsworn has such a bottleneck.

### Brief note on Fyrox, Macroquad, and custom wgpu

The evidence does not warrant treating these as primary alternatives for Voidsworn. PROPOSED: Fyrox has a scene editor and Rust-native workflow, but no search result surfaced credible evidence of a kit-heavy 3D tactics game or a comparable effects ecosystem. Macroquad is a lightweight 2D-oriented framework and does not fit a 3D kit-based ship game. Custom wgpu is a renderer-level choice, not an engine path, and would impose the largest tooling and effects-infrastructure cost of any option. None of these is recommended on the evidence found.

## 4. Other credible PC 3D option: Unity

Unity is included only because the evidence genuinely surfaces it for this game shape. A solo developer built a space strategy game in Unity 6 URP using ECS for large-scale space battles and A* pathfinding for fleet movement, explicitly choosing ECS "to handle multiple ships, resources, and colonies efficiently." OBSERVED: https://www.reddit.com/r/Unity3D (Dynasty Protocol, cursor 28, lines 11-16). Unity's C# is compiled to native code with IL2CPP for release builds, and the engine has a mature editor, prefab workflow, and asset pipeline. OBSERVED: https://scriptsforunity.com (Unity vs Unreal for Indie Developers in 2026), cursor 28, lines 41-46.

PROPOSED: Unity is credible on performance and effects capability, and its prefab system would suit a kit-based ship pipeline. The reasons it does not dominate the recommendation are cost and fit: Unity's licensing and runtime-fee history create uncertainty that Godot and Bevy do not, and the migration from Babylon to Unity is a larger language and API shift than Babylon to Godot for a solo developer already working in TypeScript. The evidence does not show a Unity-specific advantage for 20-ship turn-based tactics that would justify the switch over Godot. Unreal Engine 5 is not included as a primary recommendation: the search evidence shows solo developers using it, but the performance and tooling overhead are oriented toward higher-fidelity production than a 20-ship stylised tactics game, and no source surfaced a specific advantage for this shape.

## 7. Summary: which option the evidence leans toward, and what to measure before any switch

### What the evidence leans toward

The evidence leans toward Godot 4 as the strongest alternative to staying on Babylon, and toward staying on Babylon as the lowest-friction path if measurement does not show a concrete, unengineerable bottleneck. Godot has the clearest solo-developer fit: a real editor, fast first playable, a dense Fresnel shield and beam shader ecosystem that maps directly onto Voidsworn's effects, native GLB import and GridMap for a kit-based pipeline, and native PC export without an Electron wrapper. The 20-ship scale does not create a draw-call problem for Godot, and MultiMesh provides a mitigation if the kit system produces repeated geometry. The migration cost is real but bounded by how cleanly the current simulation layer separates from Babylon objects.

Bevy is not supported by the evidence as the primary choice for this game. Its performance advantage is demonstrated on a simulation benchmark that is not representative of Voidsworn's rendering and effect workload, and its tooling and editor gap is a direct cost against the kit-based ship art pipeline. It becomes defensible only if the coder is already Rust-fluent, values ECS architecture over editor iteration, and accepts the tooling burden. Unity is credible on capability but does not show a specific advantage over Godot for this shape that would justify the larger migration and licensing uncertainty. Unreal is not warranted on the evidence found.

### What the coder must measure or decide before any switch

The first decision is not engine, it is code architecture. The coder must determine how much of the current Babylon codebase is simulation and how much is Babylon objects. PROPOSED: If turn resolution, hex coordinates, fleet state, roguelite progression, damage rules, and AI scoring can run headless, the migration cost to Godot is materially lower than if Babylon meshes and materials are the data model. A practical measurement is to attempt a headless run of the current simulation with rendering disabled; if that is straightforward, the portable fraction is high.

The second decision is a concrete performance measurement on the current Babylon build at the exact target shape: 20 ships with all kit pieces, all shields active, beams and torpedoes firing, destruction and reanimation effects running, at the intended battle zoom on the design-floor desktop GPU. PROPOSED: The coder should record frame time, GPU time, JavaScript CPU time, draw calls, shader-program switches, and transparent overdraw in the Babylon Inspector. If JavaScript CPU time or shader-program competition is the dominant cost, Godot's native rendering and editor-driven material control become more attractive. If GPU fill rate from shields and particles is dominant, the engine choice matters less than effect authoring and overdraw control.

The third decision is kit-authoring throughput. PROPOSED: The coder should time how long it takes to assemble one ship from mixed-shape plating, apply baked finish maps, and produce three damage states in the current Babylon workflow. If that time is acceptable, staying is defensible. If it is a bottleneck, Godot's scene and prefab workflow is the evidence-backed remedy. Bevy should be tested only if the coder is prepared to build the equivalent tooling and has measured a simulation bottleneck that Godot cannot meet.

The fourth decision is distribution and maintenance appetite. PROPOSED: Electron or Tauri packaging is solved but carries per-OS build scripts and a large runtime. Godot's native export removes that maintenance. This is a secondary factor, not the primary one, but it compounds over a solo project's lifetime.
