Finding 6: Sort stability, comparator float-truncation hazard, and untied sorts in battle.js (OBSERVED at battle.js:569, 864, 1052, 1073 and API.md; INFERRED comparator/insertion-order risks)

What: Godot's built-in Array.sort() and Array.sort_custom() are unstable (OBSERVED). godot/rules/API.md specifies that all rules sorts go through JSM.ssort (a stable merge sort in godot/rules/jsm.gd). Four known sorts in godot/rules/test/oracle/battle.js have missing or partial tiebreakers (OBSERVED from Section 3B): battle.js ~line 864: AI target sort (no full tiebreak). battle.js ~line 1073: Activation order sort (no tiebreak when units have equal speed and equal squadron status). battle.js ~line 569: Partial-tiebreak sort. battle.js ~line 1052: Partial-tiebreak sort. Because those four sorts lack deterministic final tiebreakers (such as unit id or (q, r)), they depend entirely on (a) JSM.ssort being used at every call site, (b) the comparator preserving exact float sign without integer truncation, and (c) the pre-sort array having the exact same insertion order as in V8.

Where: JS oracle side: godot/rules/test/oracle/battle.js:569, battle.js:864, battle.js:1052, battle.js:1073. GDScript side: godot/rules/jsm.gd (ssort implementation, line UNSURE), godot/rules/rules.gd and godot/rules/battle_api.gd (all sort call sites and comparator lambdas, lines UNSURE).

Why it could make parity pass while behaviour differs: Comparator return type trap (INFERRED): In JS, arr.sort((a, b) =&gt; a.score - b.score) returns a float (for example, -0.35). If JSM.ssort or any ported comparator in rules.gd types the comparator return value as int (or converts via int(a.score - b.score)), any non-zero float difference in (-1.0, 1.0) truncates to 0, causing JSM.ssort to treat distinct float scores as a tie and preserve insertion order instead of sorting them! Pre-sort array order from Dictionary iteration (INFERRED): In V8 JS, integer-like string keys ("0", "1", "2") in an object are iterated in ascending numeric order first, whereas negative or non-integer keys ("-1,2", "x01") are iterated in insertion order. In GDScript Dictionary, all keys are iterated strictly in insertion order. If any unit list, hex neighbor list, or target candidate list is gathered by iterating a Dictionary with integer-string keys before being passed to JSM.ssort at battle.js:569, 864, 1052, or 1073, tied elements will appear in a different order than in V8.

What check would close it: Run grep -rnE "\.sort(_custom)?\(" godot/rules/ to confirm zero calls to built-in .sort() or .sort_custom() exist outside jsm.gd. Check JSM.ssort in godot/rules/jsm.gd to confirm it compares comparator return values against 0.0 as a float (or &lt; 0 / &gt; 0 without int casting). Inspect the four call sites in rules.gd corresponding to battle.js:569, 864, 1052, and 1073 to verify how the input arrays are constructed and ensure their pre-sort element order cannot depend on non-matching dictionary key order.

Finding 7: GDScript vs JS semantic traps (Dictionary == vs is_same, int / int truncation, JSON float keys, builtin math/method name collisions) (OBSERVED language rules; INFERRED port risks; exact lines UNSURE)

What: Seven specific GDScript language behaviors in Section 3D-3F can silently diverge from V8 on edge inputs not hit in s1 to s5: Dictionary == vs is_same() (OBSERVED trap): In GDScript, dict_a == dict_b, arr.find(dict_a), arr.has(dict_a), and arr.erase(dict_a) compare dictionaries by deep content equality rather than reference identity (=== in JS). For unit dictionaries that always carry a unique "id" ("x01", "x02"), == happens to agree with is_same (though slower). However, for any dictionary without a unique ID (such as status effect entries, terrain cell objects, squadron wing descriptors, projectile/volley records, or AI candidate move dictionaries), == or arr.erase(d) will match the wrong object whenever two instances share identical field values! JSON numbers loading as float and string key formatting (OBSERVED trap; INFERRED hex-key hazard): JSON.parse_string() in Godot loads every number in tables.json and scenarios.json as a 64-bit float. In GDScript, str(10.0) evaluates to "10.0", whereas in V8 JS String(10) evaluates to "10". If any coordinate q or r loaded from scenarios.json or tables.json remains a float (10.0), building a hex-grid lookup key via str(q) + "," + str(r) produces "10.0,5.0" instead of "10,5", silently failing dictionary lookups against integer-formatted keys! Integer division truncation (int / int) (OBSERVED trap): Whenever two operands in rules.gd are GDScript int (for example, recovered integer stats, hex axial coordinates (q1 + q2) / 2, or hull ratios hp / max_hp), GDScript / truncates toward zero unless explicitly cast to float. Builtin math and Object.tr name collisions (OBSERVED trap): Bare calls to sin(), cos(), atan2(), atan(), exp(), hypot(), or round() inside rules.gd or battle_api.gd invoke Godot's C math builtins instead of JSM.*, and any helper named tr collides with Object.tr(). Even a 1-ULP difference in C atan2 (which differs from V8 fdlibm on ~21% of inputs) or round(-0.5) (-1.0 in GDScript vs -0.0 in V8) can flip a .5 hex facing or rounding boundary. Float remainder (% vs fmod) (OBSERVED trap): GDScript % throws a runtime error if either operand is a float. Any modulo on angles, facings, or turn counters where an operand arrived from JSON as a float (or from JSM.round if it returns float) will crash or require fmod(). Long decimal literals (OBSERVED trap in test/README.md): Godot's parser corrupts long decimal literals by up to 1 ULP (and parsed one fdlibm constant as 0). While test/README.md notes the 13 fdlibm constants in jsm.gd were fixed to IEEE hex words, any decimal literal with more than 7 digits left in rules.gd (for example, PI / 3, sqrt(3), or AI heuristic weights) can differ by 1 ULP from V8. Canonical state writer float formatting (INFERRED trap): If parity_main.gd formats floats with str() instead of raw 64-bit IEEE hex words (decode_u64 / hex), compare.js must either parse them back or fail on "10.0" vs "10".

Where: godot/rules/jsm.gd, godot/rules/rules.gd, godot/rules/battle_api.gd, godot/rules/test/parity_main.gd (exact lines UNSURE).

Why it could make parity pass while behaviour differs: In s1 to s5, 243,721 math inputs and 5 battles pass, proving jsm.gd itself is accurate. However, a single unprefixed round( or atan2(, an int / int division in an unreached ability/tick (like tidal or ionpulse), or an arr.erase(status_dict) when a ship has two identical status ticks will only fail when a battle hits that exact branch or input value.

What check would close it: Grep godot/rules/rules.gd and godot/rules/battle_api.gd for bare (?&lt;!JSM\.)\b(sin|cos|atan2|atan|exp|hypot|round|tr)\s*\(. Grep for all / operators and % operators in rules.gd and battle_api.gd; verify float casting on / and fmod on floats. Grep for ==, !=, .find(, .has(, and .erase( on dictionary objects and replace identity checks with is_same() (or explicit .id comparison). Verify in jsm.gd and rules.gd that all non-integer float constants are loaded via IEEE-754 hex words (bytes_to_var / decode_double), with zero long decimal literals remaining.
