## 1. Hover freeze
**OBSERVED, high.** Mouse motion calls `hud.show_tip(_tip(), p)` even on the same hex (`godot/scenes/battle/battle.gd:3354-3368`). The tip calls the join before answering; the join executes `WorkerThreadPool.wait_for_task_completion(_threat_tid)` without testing completion (`godot/scenes/battle/battle.gd:3782-3785,1047-1054`). It can charge the entire remaining worker time to one input event. The unmodified CPU probe timed 24 calls over six scenarios: 146 to 412 ms; s13: 322, 282, 283, 296 ms. These are rules times, not frame times. Probe and version-changing moves: `contrib/opus/reviews/council_1120/fable/probes/time_threat.gd:4-21`. Earlier s13 placeholder run: worst frames 232, 255, 162, 158 ms (`contrib/opus/reviews/council_1120/fable/legs/fable_godot_dev.md:43-49`).

**Follow-up run with real hulls:** on this PC the same four s13 moves succeeded. Worst mouse handlers: 316, 317, 190, 190 ms; worst frame intervals: **330, 327, 201, 203 ms**, one blocking join per move. Headless CPU, no graphics driver or laptop measurement. Used the published input loop (`contrib/opus/reviews/council_1120/fable/probes/hover_probe.gd:22-53`), which quits directly; it also logged dummy-window negative rectangles and resources in use on exit. Those are not evidence of a three-sector leak.

**Smallest fix:** keep the per-version calculation; the map is already cached and invalidated on version change (`godot/rules/battle_api.gd:614-625`). A rules client should exclusively own the API and both task IDs. Reads return immutable last-published view/UI data or "pending", never access the live API while a worker owns it. Poll completion, reap once, publish only for the same battle and version, then refresh the stationary pointer, badges and overlays. Queue a command once and revalidate it against current state before dispatch; today even a click can be discarded while the worker runs (`godot/scenes/battle/battle.gd:2516,3371-3375`). Retain all demand sources: tip, fleet danger, selected ship and explicit map (`godot/scenes/battle/battle.gd:2746-2760,3798-3799,4329,4646`); completion already refreshes UI and overlay (`godot/scenes/battle/battle.gd:3016-3036`). Do not optimize by updating only the moved ship: other enemies' reachable end states and line of sight contribute too (`godot/rules/battle_api.gd:637-655,662-683`). Revisit incremental work only if pending-result latency still hurts after input no longer waits.

One reason to audit every API read, not just calls named `_api_join`: the scene comment says only `step()` locks, but the API actually locks `_enter()` / `_leave()` around both `threat_both` and `can_command` (`godot/scenes/battle/battle.gd:973-976`; `godot/rules/battle_api.gd:87-101,459-462,614-616`). The C-key handler reads `api.can_command()` directly (`godot/scenes/battle/battle.gd:3169-3172`). Deleting a join but reading the live API would merely move the stall to its mutex.

## 2. Cold battle load
**OBSERVED, high.** Under the cover, `board.build(api)`, `world.build(vb, world_opts)` and the loop over `_make_view(u)` all precede `await _warmup()` (`godot/scenes/battle/battle.gd:498-503,555-557,576-586,637`). A view includes synchronous resource load, instantiation, surface overrides and FX registration, not just file IO (`godot/render/ship_view.gd:123-142,156-162,176-187`; `godot/scenes/battle/battle.gd:824-842`).

**Real-hull CPU test, fresh process/profile each time, not a cold disk or a GPU frame:** 24-unit s25, stopwatch around `start_default()` up to its return, subclass timed each `super._make_view(u)`. Default headless (cuts inline): 26,873 ms uninterrupted, 25,927 ms in views, longest view 5,876 ms. Repeated with the windowed `defer_initial_cuts` flag set just before each view: **6,075 ms**, 5,065 ms in views (83%), worst view 679 ms; scene `_ready` separately 1,118 ms. World's own counters printed 181 ms for the rock/world stage and 192 ms for living terrain (`godot/world/world.gd:166-168,260-273`); board and all other work combined cannot exceed the 1,010 ms outside views in that run. Yes, over five seconds in a single CPU call even with cut work deferred. This does not show Windows ghosting, split disk load from setup, or establish an exported client's frame time.

**Smallest fix:** request distinct manifest resources as soon as the roster is known, poll for loaded status before getting them; yield to draw the cover between views, with a count of views ready. Keep scene attachment, overrides and FX registration on the main thread. One view can itself take hundreds of ms here: time load vs instantiate vs registration next, then slice the biggest remaining stage. Do not remove the later reinforcement/FX warm-up (`godot/scenes/battle/battle.gd:769-798`).

## 4. Other GPUs and bake fallback
**OBSERVED, high for the missing branch; hardware outcome unknown.** Windows requests Vulkan with D3D12 fallback (`godot/project.godot:42-45`); preset `application/export_d3d12=0` is Automatic, not Disabled (`godot/export_presets.cfg:43-45`; council correction `contrib/opus/reviews/council_1120/draft_ranked_list.md:147-149,206`). A windowed non-Compatibility job sets `compute` before it knows whether the worker can create a local device. On a disk miss it calls `_compute`; null device, compiler error and short readback can return no image. The main thread requires `not job.compute` before trying raster, so precisely that failure skips recovery (`godot/world/world_bake.gd:81-87,93-110,157-175,352-365,393-397`). The sky then returns without enabling its map (`godot/world/world.gd:515-520`). Driver selection and success of a *second*, local device on a worker are separate questions.

**Smallest fix:** for a non-authored, non-headless job with no valid image, run `_canvas` once, guarded by `raster_done`; check the finalizer thread start result so waiters always complete (`godot/world/world_bake.gd:96-104,113-120,402-438`). Record a device-level failure once per session; for a shader-specific failure suppress only that variant. Keep the cheap disk hit. Test a forced local-device failure on the normal renderer, then the exported game on Intel integrated and a machine where Vulkan actually fails: log chosen driver, successful local-device readback or raster recovery, nonblank sky and second load from disk. Item 3 found no separate D3D12 baked shaders. A headless start, or even forcing D3D12 on a working Vulkan PC, would not prove automatic fallback on either target.

## 6. Peak graphics memory at 4K Max
**OBSERVED allocations; INFERRED pressure, medium. No 8 GB spill demonstrated.** The earlier real 4K sweep reported 3.61 GiB at 4x MSAA, 3.24 at 2x, 2.85 off (`contrib/codex/perf_1118/README.md:22`), not a peak across a campaign on an 8 GB card. Max selects 4x and sets a 4096 directional shadow atlas (`godot/render/look.gd:110-114`; `godot/scenes/battle/battle.gd:358-365`). Do not multiply all hull textures by four: MSAA samples the render attachments.

**Cause:** the world cache is bounded by *entries*, not bytes. `ImageTexture.create_from_image(img)` is kept alongside the CPU Image; both references are evicted at 24 entries (`godot/world/world_bake.gd:6-20,45-61`). A 4096x2048 RGBA8 bake with a mip chain is about 42.7 MiB (4096 x 2048 x 4 x 4/3); 24 such entries would be about **1 GiB CPU plus roughly 1 GiB of texture payload** if all uploaded, before driver overhead. This is a scenario, not a measured total or an upper bound on live scene references. Sky sets one texture, planets two, and moons can be smaller (`godot/world/world.gd:504-520,667-677`; `godot/world/world_bake.gd:10-11,174-175,393-397`). The 500 MiB *disk* limit does not cap RAM or VRAM.

**Smallest fix:** first record a high-water mark per stage (title, map, load, 24 ships, multi-kill, next sector), using the three separate monitors already in `godot/bench/scene_gate.gd:864-866`; correlate against Windows dedicated/shared usage and worst frame on an actual 8 GB adapter. If retained map bytes dominate, evict by measured bytes, and release CPU copies after upload where disk can restore them. If attachments dominate, offer lower MSAA or render scale instead. No performance default should be chosen from a headless renderer's memory counters.

## 7. Leaving during an enemy turn
**OBSERVED non-reproduction; INFERRED lifecycle risk, medium.** Real quick battle s13: waited until the turn worker was actually outstanding (`think_tid=36 worker_live=true phase=enemy`), sent the real `to_title` HUD action, waited 120 frames: `freed=true title_live=true`, no coroutine script error. The process later reported 16 ObjectDB instances and eight resources at shutdown; this probe does not identify their owners. An earlier attempt never reached an enemy worker and is excluded. Quit-to-title is offered only in external, non-campaign battles; it sets `ended`, emits `finished`, and main queues the battle for deletion (`godot/scenes/battle/battle.gd:4074-4079,4211-4217`; `godot/main/main.gd:388-406`).

**Cause/risk:** `_runner` checks tree membership at loop entry but not inside `while _threat_busy:` or between awaiting a batch and `_sync`; `_think` polls across frames. Exit joins both IDs and resets them, but does not clear `_threat_busy`; the threat waiter detects changed ID and returns without `_threat_done` (`godot/scenes/battle/battle.gd:906-932,936-953,1057-1065,3016-3028`). This does not prove a freed object resumes. The more plausible window is a *still live*, queued or detached node continuing a stale operation. Also, normal commands already serialize thought vs threat (`godot/scenes/battle/battle.gd:956-976`). **Smallest fix:** mark retiring before emitting `finished`, invalidate a battle-generation token, reject post-await work if stale or queued, and reset busy flags on retirement after safe draining. Check this separately during animation and loading; do not file a proven crash or remove exit synchronization on this evidence.

The scene gate and look bench explicitly disable V-Sync and set `Engine.max_fps = 0`, but some captures only disable V-Sync (`godot/bench/scene_gate.gd:118-119`; `godot/bench/look_bench.gd:104-105`; `godot/world/world_shots.gd:71`). A global project cap is therefore **not** universally safe. Give timing jobs explicit uncapped precedence; keep player-path recordings on player defaults (`godot/main/main.gd:203-215`).

## Whole-codebase shipping pass

**W1. The hidden campaign map keeps animating during combat. OBSERVED, high.** The host does `ui.visible = false` before awaiting a battle, then shows it after (`godot/main/campaign_host.gd:168-180`). Battle pages can keep the map locally visible as a backdrop (`godot/ui/campaign/campaign_ui.gd:377-386`); its guard reads `if not visible`, not effective tree visibility. It advances flight, moves the camera, loops over stops/lights/patrols and updates the wake (`godot/ui/campaign/map3d.gd:839-853,861-904`). Reproduced on a real sector by toggling the host's UI visibility: local=true, in-tree visibility=false; the map clock advanced 0.833 s over 120 hidden frames. This is CPU work behind combat, not evidence that the GPU still draws the subviewport. **Fix:** suspend map presentation when the host hides it (start with an effective-visibility guard); leave rules, pending load completion and the *visible* fleet/shipyard backdrops alone. Verify hidden clock stays still and map input resumes after battle.

**W2. The Windows download carries two routes to ship geometry. OBSERVED contents, high; exact removable bytes not yet proven.** The preset uses `export_filter="all_resources"` (`godot/export_presets.cfg:9-12`). Build-time code converts source GLBs into generated ship/damage/wreck scenes and records their paths (`godot/render/build_assets.gd:339-366`); the battle loads those manifest paths (`godot/render/ship_view.gd:120-142`). Counted in the mounted release PCK: 77 imported GLB scene destinations under the ship source tree total **371,550,675 bytes** alongside the generated assets. That is about 354 MiB of candidates, not 354 MiB of proven savings. In particular, the generated A16 scene *does* list seven original JPG paths as dependencies; cutting the whole source tree would strip its paint. The wing selector also reads the original manifest (`godot/render/squadron_wing.gd:108-115`). **Fix:** exclude only build-input GLBs with verified generated counterparts and no runtime dependency; keep their referenced maps, manifests, scripts and fallback models. Re-export and compare PCK size, load every manifest row including wreck/damage, then smoke the release. The existing check looks for the `gen` directory and selected scripts, not every row (`godot/main/main.gd:131-149`).

**W3. Closing the window bypasses the game's clean-quit route. OBSERVED routing, high; driver crash INFERRED, not reproduced.** The title Quit button calls `main.quit_clean()` (`godot/main/title.gd:162`); that function frees scenes, waits two frames and calls `clear_all()` before ending the process (`godot/main/main.gd:29-39`). The cache registry explains why late release previously crashed Windows (`godot/render/static_caches.gd:2-6,28-35`).
