# Audit Report: Dead Code, Outdated Instructions, and Conflicting Guidance

## Proof of Reading

Sections read: EVIDENCE PACK title line ("dead code, outdated instructions, and conflicting guidance audit...main 264f441d"); THE COMMISSIONER'S QUESTION; CHAIR CENSUS; WHAT TO JUDGE (five numbered prompts); and all ten slices (NEXT.md 1-10, CLAUDE.md 1-14, PROGRESS.md 1-10, main3d.js 9-14, scene3d.js 4, scene3d.js 52, campaign_meta.js 13-17, campaign3d.js 116-119, battle.js 531-537, data.js 20-29, ui3d.js 642-652).

Overall verdict: DRIFTING. Two hard pivots (PC-only Oct 24; Godot freeze Oct 26) were declared in guidance docs but the code, data tables, and older docs still carry live-executing mobile logic, a silent unlock grant, stale numbers in comments, and retired-target text that the Godot oracle will inherit unchanged.

## Findings (most severe first)

### 1. [BLOCKER] unlockAll silently grants every LEGACY unlock and admiral at boot

READ. main3d.js: "if(o.unlockAll!==false){ for(const k in LEGACY) META.unlocked[k]=true; for(const k in ADMIRALS) META.admirals[k]=true; }". The census confirms this is "a testing leftover" with "buy handlers...fully implemented with no UI call sites", and the Oct 28 admirals redesign "replaces the ladder concept entirely." The default path (no saved option) executes the grant every boot. The settings toggle in campaign3d.js (k==='unlock') can flip it, but no visible settings row in the sliced settingsHtml() exposes it - the row list jumps from 'tips' to the Done button. INFERRED: a player who never touches a debug flag will never encounter the economy as designed; the Godot oracle copies this logic and will replicate the free-unlock behaviour unless the port team notices and strips it.

### 2. [BLOCKER] Torpedo design comment contradicts live constants on three numbers

READ. battle.js 531-535 comment: "10 harder 1 hex off, 25 harder 2 hexes off...Range 6". battle.js 536 constants: TORP_RING=[0,5,15], TORP_STRAY=10; weapon range in data.js is r:5. The comment's penalties (10/25) disagree with the ring values (0/5/15); the stated stray penalty (implied 10) matches TORP_STRAY but the hex-off penalties do not; range is 5, not 6. The Godot oracle directory (godot/rules/test/oracle/) copies browser files for parity checks. INFERRED: a port developer reading the comment will implement wrong to-hit math and file a parity bug against correct code, or implement the comment and break parity.

### 3. [BLOCKER] Mobile adaptation layer still executes and is inherited by the Godot oracle

READ. scene3d.js line 4 defines G.mobile from pointer-type and screen-size; line 52 runs frame-skipping gated on it; main3d.js defaults quality to 'medium' when G.mobile; campaign_meta.js rewrites all instruction text via touchWords and repositions tips "never under the finger." Census: "grep counts 22 references to mobile in scene3d.js alone." The PC-only ruling was Oct 24. INFERRED: any user on a touchscreen laptop, a small-window browser, or a tablet triggers the mobile path - reduced quality, halved frame rate, rewritten UI text - despite the target being retired. The Godot port, if it mirrors scene3d.js logic, inherits a branch that should not exist.

### 4. [FIX] Counted-flash merge window stated three ways

READ (census): "0.12 s in code, 0.33 s in a comment, 0.12 s in the doc; the chair's audit recommendation had been 0.33 s." Three sources, two values, and the recommended value is the one not in the code. INFERRED: a builder tuning flash timing will pick 0.12 from code or doc, or 0.33 from the comment, and produce different behaviour; the Godot port must pick one and the disagreement propagates.

### 5. [FIX] NEXT.md body still contains phone-era build gates

READ. NEXT.md header: "Superseded Oct 24 2026...Phone and Pixel gates below are retired (PC-only)." But the body at line 8: "one battle on the Pixel for anything visual" remains in the v53 gate list. The file is "kept for history and for the per-weapon effects brief." INFERRED: a new builder (human or model) scanning the gate list without internalising the header will attempt a Pixel test that no longer applies, or will treat the file as authoritative for build order when the approved plan is contrib/opus/go-forward-plan.md.

### 6. [FIX] PROGRESS.md references a dead environment and a mobile-era status line

READ. PROGRESS.md: "Live artifact: https://claude.ai/artifact/QZ7pVvYuupUHFZkFGwxsaH", "Working dir: /home/claude/v3d", status line "Last published build: Veteran AI, mobile map, onboarding". The census notes it "references a claude.ai artifact URL and a /home/claude working directory." INFERRED: a model agent following PROGRESS.md will try to read a non-existent artifact, cd into a path that doesn't exist on the current machine, and believe the latest build has a mobile map. None of this is true post-pivot.

### 7. [FIX] touchWords and phone tip-placement logic serve a retired target

READ. campaign_meta.js 13-17: touchWords rewrites "Click to fire" -> "Tap again to fire", "Hover" -> "Tap", etc.; showTip repositions cards "never under the finger" when G.mobile. The base TIPS array (ui3d.js 642-652) uses "Hover a gold hex", "click to fire", "Hover one for hit odds". INFERRED: on PC these strings are correct; the rewrite layer is dead weight. But if G.mobile triggers spuriously (Finding 3), players see "Tap" wording on a mouse-driven UI. In the Godot port the entire touchWords approach is irrelevant - Godot has its own input mapping - yet the oracle copies the source.

### 8. [NOTE] ARC_NAME defines a Rear arc no weapon uses

READ. data.js: ARC_NAME = {...,'R':'Rear'}. Census: "no weapon uses" it; "standing rule that guns never face backward." INFERRED: dead but harmless in isolation; however it is copied into the Godot oracle and could tempt a port developer to implement rear-facing arc logic that the design forbids.

### 9. [NOTE] startorp carries evMult:2 that is overwritten in live play

READ. data.js: startorp:{...evMult:2}. Census: "the Ithar weapon trait overwrites in live play, so the value only exists in no-trait simulations." INFERRED: dead in any real session; only surfaces in automated sim tests that strip traits. If the Godot port's parity tests run no-trait sims, they will validate a value that never reaches a player.

### 10. [NOTE] Naming drift between code ids and display names in comments/docs

READ. CLAUDE.md: "ids never change: voidsworn = Sunward Crusade...deathless = Eclipse." Census: "code ids and many comments use the pre-rename faction names." INFERRED: not a code bug (ids are frozen by rule), but comments and older docs that say "Voidsworn" or "Deathless" without the display-name gloss will confuse a new contributor or a model agent generating player-facing text.

### GODOT CONSEQUENCE

Threats to the in-flight port (must fix before or during porting):

- Torpedo constants/comment (Finding 2): oracle copies battle.js; wrong comment will mislead parity-test authors. Fix the comment and confirm the constants are the truth before the port's torpedo module lands.
- unlockAll grant (Finding 1): if the oracle copies main3d.js boot logic, the Godot test harness may run with all content unlocked, masking progression bugs.
- Mobile layer (Finding 3): if the port mirrors scene3d.js quality/frame-skip logic, it inherits a dead branch. The Godot renderer has its own pipeline; the mobile branch should not be ported.
- ARC_NAME Rear and startorp evMult (Findings 8-9): these are in the data oracle. A parity test that iterates all arcs or all weapon fields will validate dead values.

Browser-only residue the port can safely ignore:
