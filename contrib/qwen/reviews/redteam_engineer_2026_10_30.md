Red Team Audit: Software Engineer, Architecture and Migration

Findings

1. Save write is non-atomic; cutover removes the only fallback
OBSERVED. The Godot campaign save path copies to a .bak file, then overwrites in place. The migration review names this directly: "the one clear defect is the non-atomic write." The chair's own cutover list item 6 reads: "Save-loss reports land in the first week after cutover, when there is no other build to fall back on." The browser build's localStorage write is also a single JSON.stringify call to one key (core.js:118-120), but the browser at least has the .bak key and the .repaired key as prior-generation copies. The Godot path has the .bak step but no atomicity guarantee: a crash between the copy and the overwrite destroys both. After cutover there is no browser build to reinstall and no prior Godot save to fall back to. Every player profile and in-progress run is one power-cut from gone. This costs the game its entire player base in the first week.

2. The importer BLOCKER is not resolved by fixtures
OBSERVED. The claims register states "saves BLOCKER without the importer (fixtures now built and filed)." The parenthetical implies mitigation. The pack contradicts that reading. The fixtures README says: "Fixtures for building and testing an importer that carries browser saves into the Godot build." The Godot campaign code "states browser saves are not carried over" (campaign.gd, persistence section header). The fixtures are 21 input/output pairs for a tool that does not exist yet. No importer code appears anywhere in the godot/ tree listing. The BLOCKER stands exactly where it stood before the fixtures were filed. What the fixtures do is make the eventual importer testable; what they do not do is carry one player's 40-hour META progression across the engine boundary. Until the importer is written, passes all 21 fixtures field-for-field, and is exercised in a real cutover dry run, every existing save is a dead file. This costs the game every returning player at the moment of transition.

3. Forty regression tests FAIL at the pin; the framing buries the risk
OBSERVED. The claims register reads: "findings-to-tests 8 PASS / 40 FAIL at the pin (failures are correct regression tests against unfixed defects)." The parenthetical does rhetorical work: it reframes 40 known, reproduced, test-pinned defects as a healthy testing outcome. From an architecture seat, the correct reading is the opposite. The findings-to-tests ledger holds 48 regression tests. 40 of them fail because the underlying defects are unfixed in the browser build. The browser build is frozen to break fixes only since Oct 26, 2026. Those 40 defects are therefore frozen into the shipped build and will be ported into Godot unless each is individually addressed during the rewrite. The parity oracle tests against the frozen browser code, so a "PASS" on parity means the Godot build faithfully reproduces 40 known defects. This costs the game a migration that is technically correct and mechanically broken in 40 places.

4. Shared mutable state across threads with no API enforcement
OBSERVED. The migration review states: "threat_map() runs eval_begin() on a worker thread and clears the six shared eval caches over live units." It further states: "jsm.gd:15 keeps one static 8-byte scratch buffer behind every float-word conversion in the process." The review's own bar is explicit: "an area is SOUND only if a future ordinary change cannot silently produce wrong behaviour that no existing test would catch." Threading is rated NEEDS WORK, and the review adds: "Single-threaded parity cannot see any of this." No test covers "threading overlap" or the specific scenario of "threat_map during a worker step." The safety today rests on "a stated scene convention, not by API enforcement." A convention is one refactor away from a data race. After cutover, "race bugs have no browser build to bisect against." This costs the game intermittent, unreproducible battle corruption that surfaces in player runs with no diagnostic path.

5. CUT/SOLID hash coverage is a document divergence that blocks parity confidence
OBSERVED. The pack and all three external legs state that the canonical hash excludes CUT and SOLID module state. The Rey audit found that rules_test_README.md:34 describes each golden record as holding "the board cut-outs, the hexes that block sight" plus a SHA-256 of that state. The chair marks this "carried as UNSURE for Opus to settle" and notes: "One of the two documents is wrong." If the pack is right, "a terrain-state bug class is invisible to parity." The golden writer code (golden.js, parity_main.gd) "was not fetched by any input." This is not a minor documentation nit. The parity harness is the single most important correctness guarantee in the entire migration, and one of its two foundational documents contradicts the other on what state is actually hashed. Until one line of code settles it, every parity PASS is conditional on an unverified assumption about terrain. This costs the migration its core correctness claim for any bug that touches hex cut-outs or line-of-sight blocking.

6. A clean checkout cannot build the shippable game
OBSERVED. The migration review states: "godot/gen/ has zero files on main, the A4 ship sources live off-repo on the build PC." It further states: "sky and asteroid inputs fall back to contrib/opus/enginetest/" and "ship_view.gd falls back silently to a plain BoxMesh." The verdict is direct: "The PC workflow functions; a clean checkout cannot build the shippable game." Freshness is "keyed to a hand-bumped GEN_VERSION plus file existence only." The export preset work is listed as an addition before cutover, and no export-content check "runs on the built .pck." From an architecture seat, this means the build is not reproducible, not verifiable in CI, and depends on one developer's local machine state. If that machine is unavailable, the cutover cannot produce a binary. This costs the project its ability to ship on schedule and its ability to let any second person verify the build.

7. Third silent weapon deletion: b_razor_s drops bioplasma undisclosed
OBSERVED. The claims register records: "third silent weapon deletion found Oct 30 (b_razor_s drops bioplasma undisclosed)." This is the third instance of the same defect class. The browser build's data.js holds all game data inline ("Data is code; several audits turned on that," per the code inventory). A weapon silently vanishing from a ship's loadout means the parity oracle, the importer fixtures, and the Godot data pipeline all inherit the deletion as ground truth. No error is raised. The player sees a ship with fewer guns than the design specifies. In a fleet-tactics game where loadout composition is the core tactical decision, silent weapon loss corrupts the design contract. Three occurrences of the same class means the pipeline has no guard against it. This costs the game tactical fidelity and player trust, and it will recur in the Godot data tables unless a structural check is added.

8. fx_stub.gd and NOT PORTED paths degrade silently in live play
OBSERVED. The migration review flags: "fx_stub.gd still runs beside the real fx" and "NOT PORTED clears and plays a partially computed batch in live battles." The shell and glue area is rated SOUND WITH RISKS, held back by "silent degradation." ResourceLoader.exists soft dependencies "can ship the facts-and-buttons fallback campaign UI with no error anywhere." The cutover list demands fx_stub be retired and "core soft dependencies converted to hard loads or explicit CLI-gated fallbacks." Until then, a player can be in a live battle where visual effects are stubs, weapon batches are partially computed, and the campaign UI is a fallback, with no log line, no warning, and no error surface. The game appears to work. It does not. This costs the game a cutover where the first players experience a degraded product that reports itself as healthy.

9. Warning suppression silences the exact JS-port trap categories
OBSERVED. The migration review corrects the original claim: 6 of 17 warning classes are actually suppressed, not 17. But the correction sharpens the finding: "the suppression silences exactly the classes the project deliberately left on." Two of the six, "integer_division" and "narrowing_conversion," are identified as "the documented JS-port trap categories." The rules port is the largest and most type-sensitive body of code in the migration (245,969 bytes across four files). Integer combat math must match the Node oracle exactly. Suppressing the compiler warnings that catch integer division truncation and narrowing conversion in the very code where those bugs are most likely means the type system is blind at the point of highest risk. This costs the parity effort its cheapest automated safety net for the two bug classes most likely to produce silent numeric divergence between the JS oracle and the GDScript/C# port.

10. Telemetry spec exists as a proposal; the three rulings it serves cannot be revisited without it
OBSERVED. The telemetry spec states its purpose plainly: "three designer rulings end with 'revisit with actual play data,' and play data does not exist unless the build logs it on purpose." The spec is dated Oct 29, 2026, and is described as "Chair proposal for Opus to verify and implement." It is not implemented. The godot/ tree listing shows no telemetry module. The browser build writes telemetry to voidsworn.tel.v1 (campaign3d.js:15-19), but that is the frozen build's local log, not the structured event stream the spec defines. The three rulings (Q-A regroup tension, Q-B Nemesis snowball, Q-C generational payoff) are settled as "ACCEPT AS IS FOR NOW" or "MEASURE FIRST," with the explicit condition that measurement follows. Without implementation in the Godot build before the first playtest, the playtest produces no data, the rulings cannot be revisited, and the design questions remain open indefinitely. This costs the game its only mechanism for closing three explicit design decisions that are parked pending evidence.

Verdict
SOUND WITH RISKS trending toward NOT READY FOR CUTOVER: the parity core is strong but the shell around it (saves, threading, build reproducibility, silent degradation, telemetry) has six items the chair itself lists as "additions before cutover," and the importer that resolves the single BLOCKER does not exist yet. The most important attack: finding 2, the importer. Fixtures without an importer is a test plan without a product. Every player save dies at cutover until that code is written and passes.
