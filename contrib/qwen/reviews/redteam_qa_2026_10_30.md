Red Team Audit: QA Engineer Seat (Defect Hunting and Release Readiness)
Auditor: QA / Defect Hunting / Release Readiness
Subject: Voidsworn, "Embers of the Hollow Sun," browser build at pin 264f441d and Godot migration tree
Date: Oct 31, 2026
Findings (ranked by severity for release readiness)
F1. [BLOCKER] The Godot cutover is a save-extinction event with no importer in the tree
The claims register states "saves BLOCKER without the importer (fixtures now built and filed)." I confirm this and sharpen it: fixtures being filed is not an importer existing. The Godot campaign loader reads only its own format: OBSERVED, "its loader reads only that path and its .bak" (godot/campaign/campaign.gd:415-418). OBSERVED, "no GDScript in the tree references the browser key voidsworn.v1" (grep over godot/**/*.gd, Oct 29). The browser build offers no export: the Copy report feature emits "a diagnostic snapshot... not an importable save."
What this costs: every player who ships hours into a run, accumulates renown, unlocks admirals, builds mastery and favour, loses all of it on the day the Godot build replaces the browser build. META and RUN are both gone. The pack notes the port mirrors fields closely enough that "a converter only has to read the voidsworn.v1 JSON... and write it in the Godot envelope," but that converter does not exist in the tree. Until it does, the cutover is not a migration; it is a wipe. This is the single highest-severity release blocker in the pack.
F2. [BLOCKER] 40 of 48 regression tests fail at the pin, representing 40 unfixed defects in shipped code
OBSERVED: "Totals at the pin: 125 findings, 48 tests, 8 PASS / 40 FAIL." The ledger is explicit: "a failing test here is a correct regression test, not a broken one. Tests were not weakened to pass." The claims register confirms: "findings-to-tests 8 PASS / 40 FAIL at the pin (failures are correct regression tests against unfixed defects)."
I attack the framing, not the verdict. The claims register presents 40 failures as a known state. From a release-readiness seat, 40 failing regression tests is not a status line; it is a release gate. The ledger itself says the file "exits 1 while any pinned defect is unfixed." Every one of those 40 tests names a defect still live in code at the pin. The browser build is frozen to break-fixes, but the Godot port inherits the same data file and the same parity oracle. These 40 defects travel. No release program can call itself ready while its own regression suite fails at 83 percent. The most important attack: there is no stated criterion for when a fix lands, who re-runs the suite, or what the target failure count is before cutover.
F3. [FIX] Third silent weapon deletion found; the pattern is systemic, not incidental
OBSERVED: the claims register logs "third silent weapon deletion found Oct 30 (b_razor_s drops bioplasma undisclosed)." The findings-to-tests ledger row ROS-2 FAIL lists "d_harvester_t, i_song_w, plus b_razor_s." Three independent discoveries of the same class of defect across separate audit waves means the data file has no integrity check that a hull's weapon list references only weapons that exist and are flagged. Each deletion is silent: the ship loads, the weapon is absent, no warning fires, no telemetry event marks it.
What this costs: players see a ship in the roster, buy it, fit it, and discover in battle that a weapon they expected is gone. There is no error, no log, no UI indication. INFERRED: the same mechanism that dropped bioplasma from b_razor_s can drop any weapon from any hull if a data edit or id rename lands without a corresponding sweep. The repairRunIds function drops unknown ids silently at load (core.js:76-100), which is the same class of silent loss. This is not three bugs; it is a missing validation layer.
F4. [FIX] The unlockAll boot grant poisons every save written by the browser build and will propagate into any importer
OBSERVED: "if META.opts.unlockAll is anything other than false (including never set), main3d.js sets every LEGACY key in META.unlocked and every admiral in META.admirals." OBSERVED: "the grant becomes a permanent part of the stored profile on the first save of the session." OBSERVED: "the settings panel HTML has no unlock row at all." The pack confirms Ryan flagged this as "a leftover from testing" on Oct 28.
The claims register and drift synthesis both note this. I confirm and escalate: the pack's own save audit warns, "an imported browser META will usually arrive fully unlocked; the importer is the last clean place to decide whether that stands." But the importer does not exist (F1). So the grant is not merely a browser defect; it is a data-poisoning event for any future migration. Every save written between now and cutover carries a fully unlocked META. The drift synthesis fork on remedy (turn off in browser, strip in Godot, or banner) is an Opus technical call, but from the QA seat, the defect is unambiguous: a testing override is live in production, has no UI toggle, and mutates persistent state irreversibly.
F5. [FIX] Mid-reward resume can silently skip unclaimed prize, salvage, or pick stages after id repair
OBSERVED: "repair forces an unrecognised stage to promo (core.js:94), and resume falls through to promotionsStep when the stage's payload was filtered empty." OBSERVED: "a damaged or id-shifted reward can silently skip unclaimed prize, salvage or pick stages; the node is already banked, so the lost rewards are not recoverable."
This is state corruption by design of the repair path. The repair function does its job (keeps the save loadable), but the downstream resume logic treats a filtered-empty prize stage as if it never existed. The node is completed, the reward is gone, and the player sees a promotions screen with no explanation. INFERRED: this edge fires whenever a hull id in a prize pool is renamed or removed between sessions, which is exactly the scenario the silent weapon deletion findings (F3) and the repairRunIds drop mechanism make likely. The pack notes the _repairs toast gives counts, but the toast fires on Continue, not at the moment the reward stage is skipped, and it does not name which prizes were lost.
F6. [FIX] Settings writes never reach the cloud mirror; a second device cannot see them
OBSERVED: "saveOpts() merges into META.opts and calls Persist.saveLocal() only," while "Persist.save() is the only writer that stamps META.updated or runAt and pushes to the cloud." INFERRED: "a session that only changes settings... never syncs those settings to the cloud mirror."
This is a save-integrity gap. The cloud reconciliation resolves by stamps. A player changes quality, sound, camera, and AI level on device A, then opens device B. Device B resolves by stamps and sees no settings change because no stamp was written. The settings are lost on device A the next time device B triggers a full Persist.save(). INFERRED: this is a silent data loss path for any player using the cloud mirror across devices, and it will persist into the Godot build if the Godot shell settings store (user://settings.json) inherits the same pattern.
F7. [FIX] The mobile detection layer fires on real desktop PCs and overrides accessibility defaults
OBSERVED: "The mobile flag derives from pointer type and window size, so a coarse-pointer PC in a small window qualifies." OBSERVED: "that path forces reduced-flash off when no explicit setting exists and forces quality to medium." The drift synthesis confirms this as "a live behavior defect for an edge class of desktop players" and notes it "overrides an accessibility default, which makes it the drift item's most serious single finding."
I confirm the severity. This is not dead code. It is a live branch that misidentifies hardware and applies wrong settings. The reduced-flash override is an accessibility regression: a player who relies on reduced flash for photosensitivity or vestibular reasons gets it silently disabled by a window-size check. INFERRED: this is a break-fix candidate under the browser freeze rule because it is a behavior defect, not a feature change, but the freeze ruling is Opus's call per the decision split.
F8. [FIX] The NOMIDFIRE brace bypass is a live code defect with no harness dependency
OBSERVED: "NOMIDFIRE appears exactly once in game code, at battle.js:1385, inside the guard that disables mid-move fire when the environment variable is set." OBSERVED: "No script, harness, test, config, or shell file in the repo assigns it." The pack concludes: "the brace bypass at battle.js:1385-1387 stands as a pure code defect, and the fix does not need to preserve a harness behavior nobody uses."
I confirm. The guard checks an environment variable that nothing in the repo sets, meaning the bypass path is unreachable in normal play but present in the code. INFERRED: if any external tool, browser extension, or test harness sets NOMIDFIRE in the future, mid-move fire silently disables brace for all units. The defect is not that it fires today; it is that it exists as a loaded gun with no owner. The pack's own language calls it "a pure code defect." The Godot oracle copies of battle.js carry the same reference, so the defect ports.
F9. [NOTE] The elite guarantee in column 4 breaks on 1.87 percent of sector maps
OBSERVED: "column 4 offers no elite" in 84 of 4,500 maps. OBSERVED: "the elite guarantee at core.js:268 looks for a battle or event node to convert and silently does nothing when none exists." The findings-to-tests row W3-1 FAIL confirms: "elite guarantee broke on 25 of 900 maps in the compact sweep."
I confirm the mechanism and note the design cost. This is not a softlock; the column still offers a fight. But the code comment promises an elite and the code does not deliver one. INFERRED: players who route through column 4 expecting an elite encounter (and the CP and loot elites carry) get a standard battle instead, with no indication the guarantee was supposed to fire. The fix shape is stated in the pack: "when no battle or event node exists in the column, convert a rest node instead of doing nothing." This is a one-line fix candidate for the Godot port's genSector.
F10. [NOTE] Module fit guard checks ability but not weapon kind; six module types can be fitted as silent no-ops
OBSERVED: "the guard keys on ability alone, no weapon-kind check exists anywhere, so a crystal, magazine, capacitor, regen, loaders, or flakplus module... can be fitted to a hull with no matching weapon kind and silently does nothing." The enforcement point is campaign_run.js:128. The pack corrects an earlier misfile: a guard exists for the hangar module's only field, but the weapon-kind dimension is missing.
INFERRED: a player buys a crystal module, fits it to a hull with no crystal weapon, sees no error, and gets zero benefit. The credits are spent, the module slot is consumed, and the module does nothing. There is no warning, no tooltip, no validation. The fix shape is named: extend the guard at campaign_run.js:128 with a weapon-kind compatibility test. This is a data-integrity and player-trust issue: the shop sells items that can be wasted with no feedback.
Verdict
NOT READY. The build has a release-blocking save-extinction event at cutover with no importer in the tree, 40 of 48 regression tests failing against live defects, and a systemic silent-deletion pattern in the weapon data. The single most important attack: the Godot cutover as currently coded destroys every player's progression with no migration path, no exporter, and no importer, and the pack's own fix estimate ("a converter only has to read... and write it in the Godot envelope") remains unbuilt.
